# 账号、提醒、分享与“我的”面板方案（V2 范围已批准）

> 状态：PARTIALLY APPROVED（账号、地图提醒与分享进入 V2 已确认；微信登录实现、账号标识分层、资料规则、提醒触发与分享路径为推荐基线，待 V2-00／V2-03 批准）
>
> 原因：用户确认账号系统在 V2 随地图贡献上线，用于把地图版面与提交者账号稳定关联；V2 不建设论坛或通用社群。

## 1. 建议的“我的”面板

首屏只保留用户身份，不放说明段落：

- 头像；
- 公开 ICHI ID（V1 为占位）；
- 账号状态（已登录／未登录）；
- 进入“账号管理”。

建议栏目：

| 栏目 | 内容 |
| --- | --- |
| 账号管理 | 微信登录／退出、头像、昵称、可复制的公开 ICHI ID、账号安全和删除账号 |
| 本地记录 | 当前设备上的全部记录；每条同时显示未核对／已核对与未上传／已上传状态 |
| 我的贡献 | 本地记录中上传状态为“已上传”的派生子集；显示地点、时间和点赞计数位置 |
| 提醒设置 | 地图目标 IP／系列、关注地点、半径、微信订阅许可、频率、静默和暂停状态 |
| 隐私与数据 | 数据来源、公开范围、照片保留、导出和删除账号数据 |
| 关于 ICHI | 版本、计算说明、非官方声明、反馈入口 |

不建议首屏增加排行榜、连续签到、勋章、消费统计或“距离目标还差多少”等容易把用户推向继续抽取的模块。累计花费只能在用户主动打开记录详情时查看。

V2 账号只承担登录、贡献归属、私有状态、撤回／删除和审计。明确不提供发帖、评论、关注、私信、群组、用户动态流或公开消费档案；已有点赞计数位置不代表 V2 必须开放真实点赞。

## 2. 记录的两种状态

过去讨论中的“分享地图”在 V2 正式命名为“提交贡献”，避免与转发地图详情／导出抽赏海报的“社交分享”混淆。提交贡献落成以下状态：

```text
本地草稿（Local Draft）
  只存在当前设备或账号私有空间，不进入地图，不代表公共事实
        ↓ 用户主动选择提交贡献、拍摄赏票、填写地点备注并提交核对
核对中（Verification Draft）
  私有初始版面 + 当前抽赏记录 + 赏票照片 + 地点 + 备注
        ↓ 后台 OCR 一致
待发布审核（Pending Review）
  已提交且核对通过，但尚未公开，不等同于地图事实
        ↓ 服务端审核通过
好版地图记录（Published Observation）
  才算一次可展示的真实贡献；可下线、删除和追溯
```

因此：

- 用户只抽、不提交贡献：记录以“未核对／未上传”留在“本地记录”，不会自动变成地图记录；
- 用户点击提交贡献但中途取消、照片不完整或 OCR 不一致：仍是本地草稿，或由用户删除；
- 用户完成拍摄、地点备注并提交核对：当前版面先显示已提交状态；核对及上传完成前仍只在“本地记录”显示为未核对／未上传，完成后同一 `recordId` 更新为已核对／已上传并自动出现在“我的贡献”；
- 审核通过后：才进入好版地图，并保留来源、时间、地点、证据和审核状态。

地图公开的是核对后的当前版面状态、授权展示的初始版面照片、地点、时间和备注；不公开用户逐抽记录、抽中赏级或赏票原图。完整状态与失败回退以 `docs/decisions/v2-contribution-verification-lifecycle.md` 为准。

## 3. 后端最小数据模型

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `Account` | `accountId`、创建时间、状态 | 内部不可枚举主键，不暴露给普通客户端 |
| `WeChatIdentity` | `accountId`、微信侧身份引用、绑定时间、状态 | 私有身份映射；客户端不能自报或读取微信侧稳定标识 |
| `Profile` | `accountId`、公开 `ICHI ID`、昵称、头像引用、更新时间 | ICHI ID 可复制但 V2 不可编辑；昵称与头像可编辑 |
| `Session` | `sessionId`、`accountId`、设备标识、创建／过期时间、撤销状态 | 服务端会话，不把长期密钥放进网页存储 |
| `LocalRecord` | `recordId`、`accountId`、版面摘要、抽赏记录、目标、更新时间、删除状态 | 账号私有同步草稿；没有公共影响 |
| `ContributionDraft` | `recordId`、初始版面引用、赏票证据引用、地点、备注、同意和核对结果 | 仅在用户主动分享流程中创建 |
| `Contribution` | `contributionId`、`recordId`、审核状态、公开字段、来源时间、删除状态 | 审核通过后才可被地图读取 |
| `AuditEvent` | 操作、主体、时间、结果、原因码 | 记录登录、删除、提交、审核和下线，不保存不必要的原图内容 |
| `WatchRule` | `accountId`、目标 IP／系列、关注地点、半径、筛选、启用状态 | 使用明确保存的地点，不持续后台追踪实时位置 |
| `NotificationDelivery` | 关注规则、版面版本、订阅许可状态、发送结果、时间 | 承担去重、频控、失败降级和审计 |

原始版面照片和赏票照片必须与公开地图字段分离，默认私有、最小保留、可删除。客户端不能直接写入公开地图。

`ContributionDraft` 和 `Contribution` 必须保存服务端从认证会话派生的 `ownerAccountId`。客户端传入的拥有者字段、六位辅助编码或 `boardId` 都不能改变归属；地图只展示隐私规则允许的最小贡献者标识。

## 4. 登录与账号管理边界

小程序主登录方式推荐采用微信登录：

1. 客户端调用 `wx.login` 获取一次性 code；
2. 服务端／云函数用 code 换取并校验微信身份；
3. 服务端把微信身份映射为 ICHI 内部 `accountId`，签发 ICHI 会话；
4. 首次建号时发放可复制的公开 `ICHI ID`，但不把内部主键或微信稳定标识暴露给客户端。

内部 `accountId` 永久不可编辑；公开 `ICHI ID` 在 V2 也不可编辑，以避免占号、冒用、旧链接失效和审核归属漂移。用户通过可编辑昵称表达身份，通过微信头像填写能力选择或更换头像；拒绝设置时使用默认资料。网页如何映射到同一账号、是否引入手机号／邮箱恢复，以及未来是否允许一次性修改公开 ICHI ID，留到 V2-00 评审，不影响小程序主登录。

登录门槛已经确认：浏览地图和继续本机抽赏不要求登录；任何可能进入地图的玩家、门店或店员提交，在创建服务端贡献草稿前必须登录。取消登录时保留本机草稿，不产生云端记录。

## 5. 实施顺序建议

1. 冻结微信身份、内部账号、公开 ICHI ID、资料、会话、关注规则、消息投递、私有记录、贡献草稿和审核状态的数据契约。
2. 完成微信登录、服务端会话、账号资料和私有记录存储。
3. 将当前本地记录迁移为“本机草稿”；只有用户主动走贡献取证流程才创建贡献草稿。
4. 地图发布后接入关注地点匹配和微信订阅消息，并保留应用内降级。
5. 完成地图详情原生转发与抽赏结果本地海报；微信图片面板负责好友／群和朋友圈，小红书等第三方平台走保存相册后手动发布；分享行为不改变贡献状态。
6. 真实地图接入仍遵守“最终确认 + 服务端审核通过后发布”。

## 6. V1 已确认的框架边界

- V1 网页先呈现头像、公开 ICHI ID 占位、账号状态、账号管理、本地记录、我的贡献、提醒设置、隐私与数据和关于 ICHI；
- V1 不接入真实登录、后端账号、云端同步或公共写入；未登录用户仍可继续本机抽取；
- 未分享内容显示为本地草稿，分享后的内容显示为待审核／已发布贡献状态，占位但不伪造成功；
- V2 直接复用 V1 的页面信息架构和状态命名接入真实服务。

## 7. 已确认与待确认

已确认：

- 真实账号在 V2 上线，不后置到 V3；
- 所有个人地图贡献必须绑定认证账号；
- V2 账号不包含论坛式社群能力；
- 未登录用户仍可浏览地图、使用本机抽赏并保存本机草稿。
- 账号、地图提醒与分享能力都在 V2 实现，不后置到 V3；
- V2 仍不建设论坛式社群能力。

待 V2-00 确认：

- 小程序微信登录、内部账号主键与公开 ICHI ID 分层的推荐方案；
- 公开 ICHI ID 可复制但不可编辑、昵称／头像可编辑的资料规则；
- 基于保存地点的地图匹配与微信订阅消息方案；
- 地图原生转发、微信图片分享面板和抽赏结果海报方案；
- 账号是否同步私人抽赏记录，还是只同步分享后的贡献记录；
- 地图公开系统生成的贡献者代号、昵称，还是昵称与头像；
- 网页端如何映射到同一账号，是否需要手机号／邮箱作为恢复方式；
- 可用的订阅消息类目、模板字段和一次性／长期订阅资格；
- 地图分享是否开放朋友圈入口，以及系统图片分享面板在目标基础库和真机上的可用范围；
- 删除账号时是否同时删除未分享草稿、贡献证据和已发布地图记录。
