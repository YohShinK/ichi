## 1. 开发顺序

V1-F 采用后端优先：先完成并验证仓库代码，再把后端部署到 CloudBase 环境；后端接口独立通过后，再接入小程序静默 Account bootstrap、用户主动触发的头像／昵称更新、动态 ICHI ID、每日配额分数环、耗尽弹窗、相机二次确认与本人记录。

首次打开时，小程序直接调用 `bootstrap-account`；云函数从 `cloud.getWXContext()` 取得微信验证过的 APPID/OPENID，经服务端 HMAC 映射并幂等建立内部 `accountId`，无需头像或昵称授权。新账号默认显示 `ICHI 玩家` 与包体默认头像。用户以后主动点击“我的”页头像或昵称时，才可选择头像或修改昵称；更新不会改变内部账号、ICHI ID、记录归属或配额。昵称、头像、ICHI ID 和六位码都不是身份凭证。

## 2. ID 如何连接

内部 `accountId` 是随机、不可公开的所有权主键。`profiles` 以 `accountId` 为主键保存当前规范 ICHI ID；`ichiIds` 以公开 ID 为主键反查同一个 `accountId`，并保存 active、alias、reserved 状态。因此内部 ID 和公开 ID 的联系是普通、可审计的一对一当前关系加历史别名，不需要把两个 ID 做成同一个值。

普通账号随机取得 `ICHI-` 加 5 位无歧义字符。`ICHI-001`—`ICHI-999` 永不进入随机池；`ICHI-001` 固定保留给创始人。特殊号更换不改变账号、配额、记录或所有权，旧号也不会转给别人。

## 3. 每日 5 次配额

`dailyQuotas` 使用 `accountId:北京时间日期` 作为主键。前端显示的进度来自 `get-quota-status`：`limit/used/reserved/remaining/dateKey/resetAt`。真正调用模型前必须执行 `reserve-recognition`；它在事务内检查配额与全局熔断，为幂等任务预占一次，并返回只对本任务有效的一次性令牌。`recognize-board` 必须先用令牌把任务原子抢占为 `processing` 才能调用模型；有效结构化结果返回时立即提交预占并扣一次，提供方未配置、超时或失败时立即释放，函数崩溃则由租约协调器回收。用户在识别结果页放弃确认不会退回已经实际发生的模型调用次数。赏票识别属于同一辅助抽赏会话，不额外占用一次版面识别次数，但仍记录模型成本。

## 4. 保存什么

后端只保存结构化信息：模型原始结构化草稿、用户确认快照、字段差异、中文主 IP、可选主题、位置、观察时间、版本、问题码、守恒结果、抽取历史、确认的赏票计数和确定性最终快照。仅上传版面的最终快照等于初始快照；辅助抽赏的最终快照等于初始余票逐级减去确认抽中数量。

所有 `A1/A2`、`B1/B2` 直至 `Z1/Z2` 都归并到基础字母赏；`SP1`—`SP4` 保持独立。未知赏级、负数、超额或总数不守恒都会失败闭合。

版面照片和赏票照片不长期保存。小程序把二进制照片短暂上传到私有 `recognition-temp/{jobId}/`，同步云函数事件只传与一次性任务绑定的 `fileID`；云函数生成短时 URL 供千问读取。成功、失败和超时后客户端与云函数都会尝试删除，本机临时文件同步释放；异常中断遗留由 COS 支持的最短 `1` 天过期删除兜底。CloudBase 数据库、日志、审计、备份和长期任务都不能出现 base64、图片 URL、文件 ID 或照片哈希。没有原图复核能力是有意识的成本与隐私取舍；无法由结构化溯源解释的记录只能降级或要求重拍。

传统模式云存储的客户端安全规则已于 2026-08-28 应用并 read-back；服务端云函数和控制台不受该客户端规则限制，因此仍可生成短时 URL 并执行兜底删除。规则允许 owner 客户端读写正式头像，只允许 owner 客户端写入／删除临时对象且禁止任何客户端读取临时图片，其他前缀默认拒绝：

```json
{
  "read": "auth != null && /^profile-avatars\\//.test(resource.path) && resource.openid == auth.openid",
  "write": "auth != null && auth.loginType != 'ANONYMOUS' && resource.openid == auth.openid && (/^profile-avatars\\//.test(resource.path) || /^recognition-temp\\//.test(resource.path))"
}
```

生产读取结果为 `CUSTOM` 且表达式与上方逐字一致。规则使用微信小程序登录态的 `resource.openid == auth.openid`，未加入无依据的 `auth.uid` 放宽；客户端权限矩阵已进入自动门。真实小程序跨账号交互仍属于 V1-F 总区块的人工验收，不再是 Storage 配置缺口。

底层 COS 已启用并读回 lifecycle `ichi-v1-recognition-temp-expire-24h`：Filter Prefix 为 `recognition-temp/`，Expiration 为最短 `1` 天，`profile-avatars/` 不命中。COS 生命周期按日异步扫描，因此不能承诺孤儿对象精确在 24 小时内消失。代码中的双删负责正常路径，生命周期只处理上传成功但登记前崩溃、断网、进程退出或平台故障造成的孤儿对象；仓库 `resources.json` 同步记录已验证的生产事实。

## 5. 云资源

仓库清单定义 13 个 ADMINONLY 集合：账号、微信身份、资料、ICHI ID、角色、每日配额、识别任务、观察候选、抽赏提交、六位码、删除任务、系统设置和审计事件。客户端没有业务集合直写权限；所有权由云函数从可信身份推导。

仓库交付 18 个 Nodejs20.19 私有事件函数：16 个生成函数覆盖账号、一次性资料绑定、配额摘要／预占、任务恢复、观察确认、抽赏差量、本人记录、删除、特殊号和维护入口；`recognize-board` 使用 `qwen3.7-flash + ichi-board-vlm-3.0.0-rc1 + board-provider-extraction-3.0.0-rc1`，关闭思考并在服务端校验／归一；`recognize-draw-tickets` 使用独立 `ichi-draw-ticket-vlm-1.0.0-rc1` 赏票协议。4 个维护入口绑定定时触发器。版面函数完成任务令牌门禁、单次抢占、成功扣次、失败即时释放和无图片结构化结果恢复；赏票函数按同一记录的严格递增版本保存累计证据，同版本重试幂等，旧结果不能覆盖新结果。

部署包由 `deploy/build-functions.mjs` 生成且不重复携带运行时依赖；所有函数绑定 `ichi-node-deps_cloud1-d7gxqfwv783a1f131` v1 Node.js 依赖层。CLI 更新必须在无空格暂存目录的具体函数目录中执行，然后以线上版本状态和反向下载内容核验，不把 CLI 上传返回当作部署完成。

目标云端实况为 13 个 ADMINONLY 集合、17 个业务索引、2 条非秘密种子、18 个事件函数、4 个定时触发器和 0 个持久云存储文件。管理详情接口曾在部署核验时回显函数环境变量值，因此相关服务器端密钥已立即全部轮换；后续核验只使用函数列表、黑盒调用、资源权限和存储清单，不再读取会回显秘密值的详情视图。

## 6. 部署停止条件

出现以下任一情况立即停止，不继续扩散：

- 环境不是 `cloud1-d7gxqfwv783a1f131`，或绑定 AppID 不一致；
- 环境不是 NoSQL，或已有同名资源与仓库职责冲突；
- 清单运行时不是目标环境实测支持的 Nodejs20.19；
- 任一集合无法设为 ADMINONLY；
- 任一密钥需要写入 Git、客户端或函数响应；
- 发现公共集合、公共发布接口或业务图片存储目录；
- 部署后资源、索引、函数、触发器与清单不一致。

## 7. 回滚

本次是空环境首次部署。部署失败时停止创建后续资源；已经创建但未写入真实用户数据的函数可删除，空集合可在确认无数据后删除。只要已产生真实账号或记录，就不执行破坏性批量删除，而是禁用识别熔断、保留私有数据并通过修订后的仓库清单向前修复。
