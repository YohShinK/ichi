# TASK22 地图首次打开与详情等待优化

日期：2026-10-04。活动区块仍为 V2-E/TASK22；本工作集 `MAP_FIRST_OPEN_AND_DETAIL_LATENCY_V1` 为 **PRODUCTION APPLIED + NATIVE VERIFIED / AWAITING_REVIEW**。没有解锁后续 Phase，也没有正式微信发布。

## 根因与处理

1. 地图公开查询原来在首次点击地图时才开始，初始请求直接落在用户等待路径。没有下一页的列表仍要执行分页快照事务及事务内四项控制检查；普通控制读取也逐项串行。这些是已确认的额外开销。
2. 详情每次读取都要完成账号、控制、频控和公开数据检查，旧完整卡片等响应后才出现；等待时只有一个小文字提示。实测首次详情请求约 7.1 秒。首次请求的初始化与网络开销有波动，未获得平台 ColdStart 信号，不能断言这些开销的具体占比。
3. 现在，首页账号真实就绪后预加载同一个公开查询。生命周期 generation 防止 hide/unload 后迟到账号回执启动预加载；复用现有 client，正在加载时不创建重复初始查询。只读公开列表，不定位、不读取详情、不在首页挂载或绘制原生地图。进入地图时复用两分钟内结果，过期刷新；身份未就绪产生的 UNAUTHORIZED 在账号就绪后恢复。原生真实视野变化仍可正常触发独立区域查询。
4. 无下一页的首屏不再持久化无用快照；有下一页仍保存快照并校验账号、视野、epoch、asOf、过期时间。事务外四项控制读取并行，末次账号和控制验证并行；初次仍先验证账号，事务内全部保持顺序，避免已有 CloudBase -501001 问题。
5. 点击 marker 立即显示同一公开列表中的版面名称、剩余抽数和骨架屏；详情请求仍读取最新公开投影，返回后填入各赏、头像、昵称、核验备注及上传时间。加载时不伪造这些详情，不启用无期限详情缓存。切换、关闭、隐藏和迟到响应继续由 selection generation 与现有不复活规则处理。首次列表加载改为顶部紧凑提示，原生地图可先浏览。

## 真实测量

默认首次列表是同一个上海初始视野，真实结果 EMPTY、公开数量 0；详情测量切到有真实公开记录的杭州区域。所有样本均为开发者工具连接正式接口，不是强制冷启动实验，也不能当手机端 P95 或固定时间保证。

| 项目 | 修改前 | 修改后 / 当前 |
| --- | --- | --- |
| 首个列表 RPC | 3804ms | 部署后首个 6605ms，后续观察到 818–1169ms，仍有更慢波动 |
| 预加载完成后，进入地图到公开结果状态 | 原先进入时启动查询，3851ms 到结果状态 | 48ms，随后原生地图 272ms 就绪 |
| 首个详情 RPC | 7140ms | 3350ms |
| 随后两个详情 RPC | 1232 / 1197ms | 651 / 695ms |
| 实际 markertap 到公开概要卡片 | 旧提示壳虽较快，但完整内容需等 RPC | 82ms；完整资料随后真实返回 |

首页预加载完成前立即进入地图，仍可能等待首请求；它会显示紧凑状态而不是承诺“首请求瞬时完成”。预加载回执中 phaseAtInstall=INITIAL_LOADING，就绪时页面仍是 start，没有原生 map、没有定位请求。两个端到端详情时间序列通过 `openSelectedMapLead` 固定入口测量，绕过了原生手势 guard，以确保前后路径一致；单独的 loading QA 使用真实 `onMapNativeMarkerTap`，验证了 82ms 概要显示。工具元素尺寸证明 DOM 已布局，不等于真机 GPU 每帧呈现。
