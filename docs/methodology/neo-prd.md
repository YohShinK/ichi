## 0. 项目使命

**为 AI 时代的产品经理创立一种新的产品交付方式。**

AI 降低了制作原型和编写代码的成本，却没有降低判断“什么值得做”的难度。当方案可以被迅速生成时，问题是否真实、证据是否成立、范围为何这样选择、风险如何控制，变得更加重要。

NEO PRD 因此把产品经理的交付从“功能文档”改写为“决策系统”：

~~~text
NEO PRD        = 方法
Product Atlas  = 新型 PRD 交付物
Cowart         = 当前主要承载画布
~~~

**Product Atlas** 不是把传统 PRD 画得更漂亮，而是把问题现场、证据、判断、体验、系统契约和验证结果组织成一套能被人理解、被 Agent 读取、被团队执行、被新证据更新的产品图纸。

## 1. AI 时代的五个产品转变

### 1.1 从“生产稀缺”转向“判断稀缺”

做出页面、原型和代码越来越快，但速度不能证明方向正确。产品工作必须先建立判断，再放大生产。

~~~text
发现真实问题
→ 判断是否值得解决
→ 比较多个方向
→ 收敛可验证的最小产品
→ 交付 Product Atlas
→ 开发、验证并根据证据更新
~~~

前一阶段没有达到退出条件，不用新增功能掩盖问题。

### 1.2 产品不是功能清单

产品是针对一类用户，在具体场景中解决真实问题并产生可观察变化的方案。功能只是实现价值的手段。

开始讨论功能前，先回答：

- 谁在什么场景被卡住？
- 他现在怎样解决？
- 问题造成了什么成本？
- 产品希望改变什么行为或结果？

### 1.3 用户说出的方案不等于需求

记录用户原话，但不把“我想要某功能”直接写入范围。继续寻找它背后的任务、动机、替代方案、限制条件和期望结果。

### 1.4 AI 不等于产品价值

NEO PRD 区分两件事：

- **用 AI 做产品工作**：Agent 帮助调研整理、发散方案、生成图纸、检查遗漏和维护依赖。
- **在产品中使用 AI**：只有当非结构化理解、归纳、生成或复杂判断确实优于确定性逻辑时才采用。

如果规则、公式或普通表单能更稳定地完成任务，就不为了“AI 感”使用模型。

### 1.5 AI 产品必须交付不确定性

当产品包含模型能力时，PRD 不能只描述理想流程，还必须明确：

- 输入是否合法、充分且可解析；
- 输出质量如何评价；
- 低置信度和错误输出如何呈现；
- 哪些步骤由确定性逻辑负责；
- 哪些步骤需要用户确认；
- 何时降级、转人工或拒绝处理；
- 产品明确不处理什么。

第一版优先让 AI 辅助判断，不默认追求全自动化。

## 2. Product Discovery Loop：交付之前先建立判断

Product Atlas 不是产品发现的替代品，而是发现过程的可执行记录。整个方法由七个阶段门组成。

~~~mermaid
flowchart LR
    G0["G0<br/>机会假设"] --> G1["G1<br/>证据发现"]
    G1 --> G2["G2<br/>机会筛选"]
    G2 --> G3["G3<br/>问题契约"]
    G3 --> G4["G4<br/>方向比较"]
    G4 --> G5["G5<br/>MVP 契约"]
    G5 --> G6["G6<br/>交付与验证"]
    G6 -->|新证据| G0
~~~

回环不代表每次从头重做。新证据应返回它直接影响的阶段，并通过依赖关系更新相关图纸。

### G0｜机会假设

调研前先声明假设，不把直觉包装成结论。

~~~text
观察到的用户：
发生问题的场景：
用户当前的做法：
猜测的核心卡点：
时间 / 金钱 / 机会 / 情绪成本：
可能的独特优势：
当前最大未知：
~~~

**退出条件：** 能指出具体用户和具体场景，而不是“所有人”“效率低”“体验不好”。

### G1｜证据发现

围绕“谁被卡住、卡在哪一步、现在怎么解决、为什么值得解决”收集证据。

| 证据项 | 必须记录 |
| --- | --- |
| 行为 | 用户实际做了什么 |
| 频率 | 问题多久出现一次 |
| 成本 | 时间、金钱、机会或情绪损失 |
| 替代方案 | 当前怎样解决，哪里不满意 |
| 强度 | 是否主动搜索、付费、求助或自建工具 |
| 原话 | 能反映问题、动机和目标的表达 |
| 反证 | 哪些观察不支持当前假设 |

**退出条件：** 至少存在真实行为、现有替代方案或其他可核验材料，不能只有团队想象。

### G2｜机会筛选

对候选问题进行比较。评分帮助讨论，不替代证据。

| 维度 | 核心问题 | 高价值信号 |
| --- | --- | --- |
| 痛点强度 | 不解决会怎样？ | 明显损失或决策压力 |
| 发生频率 | 多久发生一次？ | 能在短周期反复触达 |
| 方案优势 | 为什么由本产品解决？ | 现有替代方案明显不足 |
| AI 优势 | 是否真的需要模型？ | 涉及非结构化理解、归纳或生成 |
| 结果清晰度 | 如何知道有效？ | 行为或结果可以观察 |
| 风险可控度 | 出错会怎样？ | 可确认、可降级、可撤回 |

**退出条件：** 能解释为什么现在选择这个问题，也能解释为什么暂不选择其他问题。

### G3｜问题契约

问题定义必须可以被验证：

~~~text
对【哪类用户】，在【什么具体场景】下，
因为【什么卡点】，希望得到【什么可观察结果】。
~~~

同时检查：

- 不是同时覆盖多个阶段的“太大”问题；
- 不是只有“优化一下”的“太空”问题；
- 不使用“更好”“更智能”等“太泛”结果；
- 卡点描述问题，不预设功能；
- 支持证据和反对证据可以被定位。

**退出条件：** 协作者对用户、场景、卡点和期望结果没有明显歧义。

### G4｜方向比较

至少提出三个方向，再选择一个进入 MVP。不能把最先想到的方案直接当成答案。

| 方向 | 解决哪段问题 | 即时价值 | 要验证的假设 | 主要风险 | 实现成本 |
| --- | --- | --- | --- | --- | --- |
| A |  |  |  |  |  |
| B |  |  |  |  |  |
| C |  |  |  |  |  |

**退出条件：** 选择依据与被放弃方向都已经记录。

### G5｜MVP 契约

MVP 是最小可学习闭环，不是功能少但无法验证价值的简陋版本。

~~~text
我们相信【目标用户】在【场景】中需要【核心价值】。
我们将通过【最小产品形态】验证。
如果观察到【行为或结果】，假设得到初步支持。
如果没有观察到，将根据【可区分的失败原因】决定调整或停止。
~~~

MVP 同时维护：

- 本期做；
- 本期不做；
- 成功信号；
- 失败信号；
- 停止条件；
- 获取证据所必需的反馈与记录方式；
- AI 失败时所必需的确认和兜底。

**退出条件：** 一次完整体验既能让用户感知核心价值，也能让团队获得指导下一步的证据。

### G6｜交付与验证

Product Atlas 进入设计和研发后仍然是活的决策系统。每轮验证记录实际行为，而不是只问“喜不喜欢”。

~~~text
日期 / 用户类型 / 触发场景
完成的任务 / 实际行为 / 卡住的位置
对结果的理解与信任
是否采取下一步行动
支持或推翻了哪个假设
下一轮只改变什么
~~~

每轮只能作出三种决策：

- **继续**：核心价值得到支持，主要问题在体验或质量；
- **调整**：问题真实，但用户、场景、方案或交付方式需要改变；
- **停止**：问题不痛、难触达、没有独特优势，或风险成本不值得承担。

已经投入的开发成本不能成为默认继续的理由。

## 3. NEO：Product Atlas 的叙事层

Discovery Loop 负责建立判断，NEO 负责让判断可以被理解。

~~~mermaid
flowchart LR
    N["N · Narrative<br/>问题与证据"] --> E["E · Experience<br/>方案与系统"]
    E --> O["O · Outcome<br/>验证与决策"]
~~~

### N｜Narrative：进入真实问题

交付人物、时间、地点、触发事件、已知信息、未知信息、限制条件、当前替代方案与后果。场景必须可观察，不写成广告故事。

### E｜Experience：体验产品怎样介入

交付用户输入、系统理解、状态变化、反馈、异常路径和下一步行动。优先使用分镜、流程、界面状态、数据图表与可运行 HTML。

### O｜Outcome：知道如何验证和决策

交付价值指标、质量标准、风险护栏、成功/失败/停止条件，以及下一轮继续、调整或停止的依据。

NEO 不是线性汇报模板。三层之间必须能够双向追踪：

~~~text
场景中的一个卡点
↕
体验中的一个产品节点
↕
结果中的一个验证信号
~~~

## 4. Product Atlas：新型 PRD 的图纸系统

### 4.1 默认图纸目录

Product Atlas 使用模块化图纸，不强制固定页数。默认核心由八张图纸组成：

| 图号 | 图纸 | 必须回答的问题 |
| --- | --- | --- |
| A00 | Product Thesis | 为什么现在值得处理这个问题？当前决策状态是什么？ |
| A01 | Situation | 谁在什么时候、什么地方、什么限制下被卡住？ |
| A02 | Evidence Map | 哪些行为、替代方案、成本和反证支持或挑战判断？ |
| A03 | Problem Contract | 选择了哪个问题？为什么暂不选择其他问题？ |
| A04 | Direction & MVP | 比较过哪些方向？第一版验证什么、明确不做什么？ |
| A05 | Experience Workflow | 用户、系统、AI 和确定性逻辑如何完成关键任务？ |
| A06 | System Detail | 输入输出、规则、状态、Bad case、确认和兜底如何工作？ |
| A07 | Validation & Next | 如何衡量、何时停止、最新证据要求下一步做什么？ |

复杂项目可以增加：

- Dxx：核心交互或规则详图；
- Exx：证据附件；
- Vxx：验证批次；
- Rxx：风险与边界专题。

### 4.2 阅读路径

~~~mermaid
flowchart LR
    A00["A00<br/>产品命题"] --> A01["A01<br/>问题现场"]
    A01 --> A02["A02<br/>证据地图"]
    A02 --> A03["A03<br/>问题契约"]
    A03 --> A04["A04<br/>方向与 MVP"]
    A04 --> A05["A05<br/>体验工作流"]
    A05 --> A06["A06<br/>系统详图"]
    A06 --> A07["A07<br/>验证与下一步"]
~~~

### 4.3 一张图纸只回答一个主问题

每张图纸必须能用一句问句概括。信息优先级为：

~~~text
真实场景 / 行为证据 / 可运行体验
    > 分镜 / 图表 / 关系图
    > 标注和短句
    > 段落文字
~~~

规则：

- 一个标题只表达一个判断；
- 一个说明段不超过三行；
- 一张图纸只保留一个核心结论；
- 一张卡片最多三层文字层级；
- 无法一句话解释的图表必须重新设计；
- 视觉不能代替证据，交互不能掩盖规则。

### 4.4 场景是最小产品单位

一个完整场景包含：

| 字段 | 要回答的问题 |
| --- | --- |
| Person | 谁遇到问题？此刻是什么状态？ |
| Place | 问题发生在哪里？环境怎样影响行为？ |
| Time | 什么时候发生？是否存在时间压力？ |
| Trigger | 什么事件触发问题？ |
| Known | 用户掌握哪些信息？ |
| Unknown | 哪些关键信息不可见或无法判断？ |
| Current Action | 用户现在怎样解决？ |
| Decision | 用户必须做出什么选择？ |
| Consequence | 不解决会产生什么后果？ |

任何功能都必须回答：

> 它解决 A01 中的哪个瞬间，并用 A07 中的什么证据判断有效？

无法连接场景与验证信号的功能，不进入核心范围。

## 5. Evidence & Decision Graph：让判断可以追踪

Product Atlas 不只组织页面，还组织产品判断之间的依赖。

### 5.1 内容状态

| 标签 | 含义 |
| --- | --- |
| OBSERVED | 来自实际观察或行为 |
| REPORTED | 用户或社区成员的主观陈述 |
| CALCULATED | 由明确数据或模型计算 |
| ASSUMED | 尚未验证的假设 |
| DECIDED | 当前主动选择 |
| UNKNOWN | 已知存在但尚无答案 |

### 5.2 假设生命周期

~~~text
UNKNOWN
→ ASSUMED
→ TESTING
→ SUPPORTED / REFUTED
→ CONTINUE / ADJUST / STOP
→ 新证据触发重新打开
~~~

“得到支持”不等于永久事实。每个判断都应保留证据来源、时间和适用范围。

### 5.3 最小决策对象

重要判断使用稳定 ID：

~~~yaml
id: DEC-MVP-001
claim: 第一版优先验证手动录入后的概率与成本判断
status: ASSUMED
evidence:
  - EVID-RESEARCH-003
contradictions:
  - EVID-OBS-006
affects:
  - A04
  - A05
  - D01
validation_signal: 用户能在可接受时间内完成录入并据此改变行动
next_review: 下一轮任务测试后
~~~

当证据变化时，Agent 应能定位受影响的场景、功能、流程、指标和图纸，而不是重写整份 PRD。

## 6. 产品系统契约

### 6.1 基础契约

每个核心体验至少交付：

- 用户输入；
- 系统输出；
- 主流程与关键状态；
- 规则与计算逻辑；
- 异常路径；
- 用户确认点；
- 验收标准；
- 明确不处理的范围。

### 6.2 AI 能力契约

只有产品确实包含模型能力时才填写；否则标记 AI_PRODUCT_ROLE: NONE。

| 契约项 | 必须说明 |
| --- | --- |
| Input | 数据来源、格式、合法性、完整性与隐私 |
| Output | 结构、用途以及禁止用途 |
| Model Role | AI 在哪一步负责理解、归纳、生成或判断 |
| Deterministic Role | 哪些公式、校验和业务规则不能交给模型 |
| Quality Rubric | 正确性、完整性、一致性、可解释性如何评价 |
| Confidence | 低置信度如何识别和呈现 |
| Bad Cases | 典型失败输入、输出与高风险误用 |
| Confirmation | 哪些结果必须由用户确认 |
| Fallback | 降级、重试、人工处理或拒绝策略 |
| Boundary | 隐私、安全、合规和明确不处理的内容 |

### 6.3 人、AI 与确定性逻辑的分工

~~~text
人：目标、事实确认、价值判断、高风险决定
AI：非结构化理解、比较、归纳、生成、提出反例
确定性逻辑：公式、权限、校验、状态机、硬性业务规则
~~~

Agent 可以起草、查漏和提出反例，但不能替人确认事实、伪造证据或默认扩大范围。

## 7. 验证与度量

### 7.1 四层指标

| 层级 | 回答的问题 | 示例 |
| --- | --- | --- |
| 价值指标 | 用户是否获得预期变化？ | 是否更清楚并采取下一步行动 |
| 行为指标 | 用户是否完成关键行为？ | 完成率、用时、放弃位置 |
| 质量指标 | 系统输出是否可靠？ | 正确率、完整率、确认修改率 |
| 护栏指标 | 是否产生不可接受代价？ | 严重误导、隐私风险、投诉率 |

指标必须连接某个假设，不能因为“常见”就加入。

### 7.2 验证记录

~~~yaml
validation_id: VAL-001
scenario: A01
hypothesis: HYP-003
actual_behavior:
friction:
understanding_and_trust:
next_action:
supported:
refuted:
decision: CONTINUE | ADJUST | STOP
next_change:
~~~

### 7.3 更新规则

- 新证据出现时，先更新假设和问题定义，再调整功能；
- MVP 变化时，同时更新“做 / 不做”、验收和停止条件；
- 开发中发现方向问题，回到对应阶段门，不用新增功能掩盖；
- 一轮验证只确定下一轮最重要的变化；
- 每次范围变化都保留被放弃内容及原因。

## 8. Cowart 中的实现方式

Cowart 是 Product Atlas 的主画布，不是正式产品开发环境。

### 8.1 在产品仓库中的位置

整个 Git 仓库就是产品项目，不为 PRD 再建立一个与产品平级的新项目。Product Atlas 作为项目级产品定义，放在应用代码之外、仓库之内：

├── product-atlas/

│   ├── nodes/

│   └── canvas/

│   └── delivery/

├── packages/                 # 门禁通过后创建
└── services/                 # 门禁通过后创建
~~~

各目录只承担一种职责：

| 位置 | 职责 |
| --- | --- |
| docs/methodology/neo-prd.md | 定义怎样制作 Product Atlas，是跨项目方法论 |
| product-atlas/ | 保存当前产品的语义索引、六张核心图纸、扩展契约和 Cowart 画布 |
| memory-bank/ | 保存当前步骤、实施顺序、真实架构和技术方向 |
| docs/references/ | 保存传统 PRD 与路线等历史输入，默认不进入开发上下文 |
| docs/delivery/ | 定义从产品判断到设计、开发与测试的交付参考 |
| apps/、packages/、services/ | 门禁通过后保存正式产品代码与共享能力 |

这不是维护两份 PRD：

- Cowart 是人类主要阅读、评审和操作的界面；
- atlas-index.yaml 是 Agent 的导航索引，只保存 ID、状态、依赖和文件引用，不复制全部正文；
- evidence、decisions 和 validation 保存需要追溯的原始材料；
- 正式产品代码不放入 canvas，Cowart HTML 也不直接迁入 apps。

### 8.2 无限画布的空间分区

画布不是八张幻灯片横向排开，而是一张有主路、街区和附件的产品地图：

~~~text
                         Evidence Dock
                E01 行为 · E02 替代方案 · E03 反证
                              ↓

A00 入口 → Narrative District → Experience District → Outcome District
             A01—A04              A05—A06               A07
          场景与产品判断          体验与系统           验证与决策
                              ↓

                          Detail Lane
             Dxx 交互详图 · Rxx 风险 · Vxx 验证批次

                                        Decision Parking
                              被放弃方向 · 过期判断 · 重启条件
~~~

空间规则：

- A00—A07 构成唯一主阅读路径；
- 证据位于相关判断上方，形成“证据支撑判断”的视觉关系；
- 交互、系统和风险详图位于核心图纸下方，按需展开；
- 被放弃方案不能删除，移动到 Decision Parking 并记录原因；
- 画布位置帮助人理解，但节点关系必须另有结构化记录，不能让 Agent 依靠坐标猜测。

### 8.3 人类阅读的四个缩放层级

| 缩放层级 | 应该看见什么 | 不应该出现什么 |
| --- | --- | --- |
| 全局 | NEO 三个区域、A00—A07 主路、当前状态 | 段落和原始证据 |
| 街区 | 每张图纸的主问题、结论和相互关系 | 完整规则说明 |
| 图纸 | 场景、图表、流程、证据与关键取舍 | 与本图无关的附件 |
| 详图 | 原始证据、系统契约、Bad case 和验证记录 | 重复的全局介绍 |

用户应能自由缩放探索，也能通过 AI Slides 按 A00—A07 顺序完成线性阅读。

### 8.4 每张核心图纸的固定骨架

~~~text
图号 + 名称 + 状态 + 版本
────────────────────────
这张图纸回答的唯一问题
────────────────────────
场景 / 图表 / 流程 / 可运行体验
────────────────────────
当前产品判断
────────────────────────
证据 ID · 反证 · 未知 · 影响节点 · 下一步
~~~

人类看到的是主问题、视觉关系和产品结论；机器结构不应挤占正文，但稳定 ID、状态和关键依赖必须在图纸上可见。

### 8.5 AI 可读的双层结构

AI 不能只依赖视觉截图或画布坐标理解 Product Atlas。每个核心节点同时拥有：

1. **可见层**：图号、问题、结论、状态、证据编号；
2. **结构层**：Shape metadata 与 atlas-index.yaml 中的依赖对象。

最小节点对象：

~~~yaml
id: A04
type: direction_and_mvp
title: Direction & MVP
status: ASSUMED
version: 0.3
shape_id: shape:product-atlas-a04
page_id: page:ichi-product-atlas

depends_on:
  - A01
  - A02
  - A03

evidence:
  - EVID-003
  - EVID-007

contradictions:
  - EVID-009

affects:
  - A05
  - A06
  - A07

hypothesis: HYP-MVP-001
success_signal: SIG-001
stop_condition: STOP-001
asset_refs:
  - canvas/pages/<page-id>/assets/ai-html/a04-mvp-comparison.html
~~~

Cowart Shape metadata 至少保存 productAtlasId、type、status、version 和 sourceRefs。更完整的证据、依赖和影响关系保存在 atlas-index.yaml。

这样 Agent 可以准确回答：

- 这个功能来自哪个问题现场？
- 当前判断依赖哪些证据，又被哪些反证挑战？
- 修改某个假设会影响哪些流程、规则和指标？
- 哪张图纸已经过期，下一轮应更新什么？

### 8.6 三种表达单元

| 单元 | 用途 |
| --- | --- |
| tldraw 图形 | 场景、关系、依赖、流程和短标注 |
| AI HTML | 可交互图表、概率模拟、状态演示和规则计算 |
| AI Slides | 按图号进行产品评审、决策同步和跨职能交付 |

Cowart 中的 HTML 是可交互的 PRD 图纸，不是正式产品代码。可运行产品单独开发，并从 Product Atlas 链接。

只有真正需要交互的内容才使用 AI HTML：

| 图纸 | 建议的交互 HTML |
| --- | --- |
| A02 | 筛选证据，切换支持、反证和未知，查看来源 |
| A04 | 比较三个方向，查看 MVP 做 / 不做和停止条件 |
| A05 | 演示状态变化、异常路径和人 / AI / 逻辑分工 |
| A07 | 切换验证批次，查看指标和 Continue / Adjust / Stop |

其余图纸优先使用 tldraw 原生 Frame、文本、箭头和图片，避免画布退化为网页拼贴。

### 8.7 两种观看方式

- **Atlas 模式**：缩小画布，检查全局结构、证据依赖和闭环；
- **Slides 模式**：按 A00—A07 阅读，完成评审和决策同步。

两种模式来自同一个项目画布，不维护重复内容。Slides 只保存 presentation_order，不复制图纸。

### 8.8 语义命名

分区、Frame、HTML 卡片和关键节点采用稳定名称：

~~~text
A01_SITUATION
├── A01_META
├── A01_TRIGGER
├── A01_CURRENT_ACTION
├── A01_CONSTRAINTS
├── A01_KNOWN
├── A01_UNKNOWN
├── A01_DECISION
└── A01_CONSEQUENCE
~~~

AI 友好不是增加隐藏长文，而是让可见内容本身拥有稳定 ID、状态、来源和依赖关系。

### 8.9 视觉语言

采用“瑞士国际主义 × 建筑图纸”的基础语言：

- 12 栏网格；
- 黑、白、灰与一个状态强调色；
- 无衬线字体和明确字号反差；
- 直角、细线、图号和坐标式标注；
- 大面积留白承担阅读节奏；
- 图表只服务信息关系；
- 状态颜色必须有文字标签，不能只依赖颜色。

Figma 只在需要高保真 UI、Auto Layout、Variables 或组件交付时进入，不复制整套 Product Atlas。

## 9. 标准制作流程

~~~mermaid
flowchart TD
    A["建立机会假设"] --> B["收集行为、替代方案和反证"]
    B --> C["筛选首选问题"]
    C --> D["建立问题契约"]
    D --> E["比较至少三个方向"]
    E --> F["建立 MVP 契约"]
    F --> G["制作 A00—A04"]
    G --> H["制作体验与系统契约 A05—A06"]
    H --> I["定义指标、护栏和停止条件 A07"]
    I --> J["Cowart Atlas 结构校验"]
    J --> K["跨角色与 Agent 可理解性校验"]
    K --> L["进入设计、开发与任务验证"]
    L --> M["根据证据继续、调整或停止"]
    M --> B
~~~

交付顺序不是从封面开始美化，而是：

1. 先完成机会假设、证据地图和问题契约；
2. 没有比较方向前，不画完整功能总图；
3. 没有 MVP 契约前，不扩写全部页面；
4. 没有失败和停止条件前，不声称方案已验证；
5. 产品包含 AI 时，必须先完成能力契约和兜底；
6. 最后才统一视觉、Slides 顺序和交付体验。

## 10. Product Atlas 质量门

### 10.1 问题与证据

- [ ] 用户、场景和卡点是否具体？
- [ ] 是否记录真实行为、替代方案和成本？
- [ ] 是否同时保留支持证据和反证？
- [ ] 是否把用户提出的方案继续还原为底层任务？
- [ ] 是否明确最大未知？

### 10.2 选择与范围

- [ ] 是否比较至少三个方向？
- [ ] 是否记录选择与放弃的理由？
- [ ] MVP 是否只验证一个核心价值？
- [ ] 是否同时写清“做 / 不做”？
- [ ] 是否存在成功、失败和停止条件？

### 10.3 体验与系统

- [ ] 核心功能是否连接具体场景和验证信号？
- [ ] 是否展示输入、反馈、状态和异常路径？
- [ ] 确定性逻辑、AI 和人的职责是否分开？
- [ ] Bad case、低置信度、确认和降级是否可见？
- [ ] 风险与边界是否进入主流程，而不是藏在附录？

### 10.4 AI 协作

- [ ] 分区、节点、证据和决策是否使用稳定 ID？
- [ ] 事实、陈述、计算、假设、决定和未知是否可区分？
- [ ] Agent 能否从单张图纸理解目标、输入和输出？
- [ ] 修改一个假设后，能否定位受影响的功能、流程和指标？
- [ ] AI 生成的结论是否经过人类审核？

### 10.5 可理解性

- [ ] 新协作者能否快速理解产品命题？
- [ ] 能否沿图号独立理解主要推理？
- [ ] 每张图纸是否只有一个主问题？
- [ ] 视觉、图表和交互是否服务判断？
- [ ] 是否避免虚假完整性和模板化行业语言？

## 11. 现实问题与方法演进

| 编号 | 现实问题 | 当前规则 |
| --- | --- | --- |
| R-001 | 场景被写成虚构故事 | 区分行为证据、用户陈述和假设 |
| R-002 | 无限画布重新变成文字墙 | 限制文字密度和单图主问题 |
| R-003 | 原型只能表现 UI，隐藏规则不可见 | 补充输入、输出、规则和不确定性 |
| R-004 | 画布自由度过高，阅读路径不清 | Atlas 空间结构与 Slides 图号并存 |
| R-005 | AI 容易虚构研究和数据 | 使用来源、状态、反证和人工审核 |
| R-006 | 图纸追求视觉，产品判断变弱 | 每张图纸必须交付一个判断 |
| R-007 | PRD 完整造成“已经验证”的错觉 | 区分假设、决定、支持与反驳状态 |
| R-008 | MVP 被理解为缩小版完整产品 | MVP 必须对应核心假设和停止条件 |
| R-009 | 为了 AI 而使用 AI | 无模型必要时标记 AI_PRODUCT_ROLE: NONE |
| R-010 | 第三方画布默认遥测 | 使用敏感资料前确认关闭、替换或得到授权 |

新增问题必须记录发生场景、观察、影响、当前处理以及是否升级为正式规则。

## 12. 从方法论到 Product Atlas Skill

满足以下条件后，再将方法固化为 product-atlas Skill：

1. 至少完成一套真实 Product Atlas；
2. 完成一次跨角色产品评审和一次 Agent 读取测试；
3. 用它指导一次从问题发现到 MVP 验证的完整循环；
4. 收集产品、设计、研发和使用者反馈；
5. 能区分稳定规则与项目特例；
6. Evidence & Decision Graph 能够支持实际变更追踪。

预计结构：

~~~text
product-atlas/
├── SKILL.md
├── references/
│   ├── discovery-gates.md
│   ├── neo-narrative.md
│   ├── atlas-layouts.md
│   ├── evidence-decision-graph.md
│   ├── ai-system-contract.md
│   └── quality-gates.md
├── assets/
│   └── cowart-atlas-template/
└── scripts/
    └── validate-atlas.*
~~~

Skill 不自动“写一份看起来完整的 PRD”。它应该帮助 Agent：

- 识别未经验证的假设；
- 要求证据与反证；
- 比较方案并收敛 MVP；
- 生成结构化 Product Atlas；
- 检查场景、功能、指标和风险是否闭合；
- 在新证据出现时只更新受影响节点；
- 主动提出遗漏、反例、失败路径和停止条件。
