# 泛用 Web Vibe Coding 工作流：从想法到上线与持续迭代

> **扩展参考。** 当前项目以已安装的 `vibe-coding-standard-workflow` Skill 及根目录 `AGENTS.md` 为执行规范；本文保留更完整的 Web 交付说明。

> 文档类型：泛用 Web 开发工作流  
> 更新日期：2026-08-04  
> 说明：这是一套与具体仓库、业务和框架无关的 Web Coding 工作流。适用于静态网站、SPA、SSR/SSG、PWA 和全栈 Web 应用，不预设 React、Vue、Svelte、Next.js、Nuxt、后端语言、数据库或部署平台。

---

## 一、这套流程解决什么问题

很多 Web Vibe Coding 项目以一句模糊需求开始，随后直接让 AI 写页面或接口。短期看起来很快，但项目稍微变大后，通常会出现以下问题：

- AI 对产品目标的理解和人的真实想法不一致；
- 每轮对话都要重新解释背景；
- 技术选型不断变化；
- 实施顺序没有依赖关系，写到一半才发现基础能力缺失；
- 一个会话同时修改太多内容，难以定位问题；
- 测试失败后，AI 已经继续实现后面的功能；
- 清空上下文或更换 Agent 后，无法恢复之前的工作状态；
- 代码已经变化，但架构和进度文档仍停留在旧状态。
- 页面只在开发者自己的浏览器和视口上可用；
- 视觉看似完成，但键盘操作、语义结构、表单错误和加载状态不可用；
- 前端、API、数据库和认证的契约不一致；
- 环境变量、Cookie、跨域、缓存和部署配置到上线时才暴露问题；
- 没有性能、可访问性、SEO、安全和浏览器兼容性基线。

这套工作流先把需求、设计、技术栈和实施计划逐层写清，再把它们放进一个长期维护的 `memory-bank`，之后一次只开发一个可验证步骤。

完整链路如下：

```text
写初始 PRD
→ 与 AI 反复澄清需求
→ 生成产品设计文档
→ 确定技术栈
→ 生成无代码实施计划
→ 建立 memory-bank
→ 再次澄清和细化计划
→ 一次执行一个步骤
→ 自动检查、真实浏览器验证与人工验收
→ 更新 progress 和 architecture
→ 清理上下文并继续下一步
→ 预发布检查与部署
→ 完成整个 Web 产品
```

这不是“让 AI 一口气做好整个网站”，而是把 AI 当成能够读取项目文档、执行小任务、在真实浏览器中取证、接受验收并维护工程记忆的 Web 开发者。

### 1.1 适用项目

- 营销页、落地页和内容站；
- 管理后台、仪表盘和内部工具；
- 交互式 SPA；
- SSR、SSG 和混合渲染网站；
- 带 API、认证和数据库的全栈 Web 应用；
- PWA 和需要离线能力的 Web 应用；
- 在现有仓库中新增页面、流程或完整功能。

### 1.2 不预设的内容

工作流不默认选择：

- 客户端框架；
- CSS 或组件方案；
- 服务端语言；
- ORM 和数据库；
- 云服务与部署平台；
- 测试框架；
- 是否需要登录、后端或持久化。

这些选择必须从产品、流量、内容、交互、团队、运行环境和维护成本反推。

## 二、开始前的准备

### 2.1 所需工具

本文中的编码 Agent 泛指能够读取和修改项目文件的工具，例如 Claude Code 或 Codex。工具至少需要能够：

- 读取 Markdown 和代码文件；
- 在项目中创建、修改、移动和删除文件；
- 运行构建、测试或检查命令；
- 启动本地 Web 服务并操作真实浏览器；
- 检查页面截图、控制台、网络请求、DOM 和可访问性树；
- 读取 Git 状态；
- 在用户确认后创建提交；
- 通过项目级说明文件持续读取工作规则。

### 2.2 建议的初始目录

在流程真正开始时，项目可以非常简单：

```text
project/
├── PRD.md
└── README.md              # 可选，先记录最小运行说明
```

`PRD.md` 是一份初步需求，不要求一开始就非常专业。它的作用是把脑中的想法变成 AI 可以讨论的文本，而不是直接作为最终工程规范。

### 2.3 整个流程中的文件

工作流最终会形成如下核心结构：

```text
project/
├── AGENTS.md 或 CLAUDE.md
├── memory-bank/
│   ├── design-document.md
│   ├── tech-stack.md
│   ├── implementation-plan.md
│   ├── progress.md
│   └── architecture.md
├── src/                   # 名称随框架变化
├── public/                # 可选静态资产
├── tests/                 # 单测、集成、端到端或视觉测试
└── README.md
```

各文件的职责：

| 文件 | 作用 |
| --- | --- |
| `PRD.md` | 最初的产品想法和粗略需求，用于启动讨论 |
| `design-document.md` | 澄清后的产品设计、功能、流程、状态和约束 |
| `tech-stack.md` | 技术栈、工具、依赖和技术边界 |
| `implementation-plan.md` | AI 可以逐项执行的无代码实施计划 |
| `progress.md` | 已完成步骤、验证情况、当前阻塞和下一步 |
| `architecture.md` | 当前代码架构、目录、模块职责和关键文件用途 |
| `AGENTS.md` / `CLAUDE.md` | Agent 每次工作都应遵守的项目级规则 |

Web 项目还应逐步形成以下“可运行事实”，但不要求第一天一次建全：

- 本地开发、测试、构建和预览命令；
- 支持的浏览器和视口范围；
- 路由与页面清单；
- API、认证、Cookie、缓存和错误契约；
- 环境变量清单及示例文件；
- 数据库迁移与种子数据方式；
- 部署、回滚和上线后验证方式。

## 三、第一步：写一份简明的初始 PRD

第一步不是让 AI 写代码，而是由你先写一份简明的 `PRD.md`。

这份 PRD 至少应回答：

- 产品叫什么；
- 产品为谁服务；
- 用户遇到了什么问题；
- 产品提供哪些核心功能；
- 用户从进入产品到完成核心任务的大致路径；
- 当前明确不做什么；
- 你已经确定的限制或偏好；
- 你暂时还不确定的问题。
- 网站类型：静态、SPA、SSR/SSG、PWA 或全栈；
- 关键页面、路由和转化动作；
- 是否需要搜索引擎收录、登录、支付、上传、实时数据或离线能力；
- 目标设备、浏览器、语言、地区与无障碍要求；
- 性能、安全、隐私和合规底线。

可以使用下面的模板：

```md
# 产品名称

## 1. 产品简介

- 一句话描述：
- 目标用户：
- 核心问题：
- 预期价值：

## 2. 核心功能

1. 功能 A：
2. 功能 B：
3. 功能 C：

## 3. 用户使用路径

用户进入产品
→ 执行某个操作
→ 系统返回结果
→ 用户完成目标

## 4. 本期范围

### 做

- 

### 不做

- 

## 5. 已知约束

- 目标平台：
- 网站形态：静态 / SPA / SSR / SSG / PWA / 全栈
- 核心页面与路由：
- 目标设备与浏览器：
- 是否需要 SEO：
- 是否需要无障碍合规：
- 是否需要登录：
- 是否需要后端：
- 是否需要数据库、上传、支付或实时通信：
- 数据来源：
- 部署环境：
- 其他限制：

## 6. 尚未确定

- 
```

### 第一步的目标

不是写出完美 PRD，而是提供足够具体的讨论起点。即使某些内容仍不确定，也要明确写在“尚未确定”中，不要让 AI 默认猜测。

### 第一步的完成标准

- [ ] 有具体产品名称或工作名；
- [ ] 能说明目标用户和核心问题；
- [ ] 至少列出核心功能；
- [ ] 有一条完整的用户路径；
- [ ] 能说清 Web 形态、关键页面和目标浏览环境；
- [ ] 已标明 SEO、认证、数据、支付、上传等关键能力是否需要；
- [ ] 已知约束和未知问题被分开记录；
- [ ] 文档已保存为 `PRD.md`。

## 四、第二步：让 AI 反向提问，生成产品设计文档

把 `PRD.md` 交给 Claude Code、Codex 或其他编码 Agent。不要立即要求它实现产品，而是要求它先阅读、发现问题并与你讨论。

### 4.1 推荐提示词

```text
请完整阅读 @PRD.md。这是一份初步产品需求。

先不要写代码。请找出其中所有会影响产品设计或实现方向的歧义、缺失和冲突，并逐项向我提问。我们需要通过讨论把需求澄清到可以设计和实施的程度。

当关键问题都确认后，把结论整理成 Markdown 产品设计文档，文件名为 design-document.md。文档要能让后续开发者仅凭它理解产品目标、用户流程、功能、页面、状态、规则、约束和验收标准。
```

### 4.2 AI 可能追问的内容

AI 通常会从以下方向提问：

- 目标用户是否只有一类；
- 首次使用和回访使用是否不同；
- 核心流程的开始和结束分别是什么；
- 是否需要账号、同步和权限；
- 数据从哪里来，谁可以修改；
- 页面需要哪些状态；
- 异常、空数据、加载失败时如何处理；
- 哪些结果由规则计算，哪些由 AI 生成；
- 用户能否撤销或修改操作；
- 是否需要移动端、桌面端或多平台；
- 路由能否直接访问、刷新和前进后退；
- URL、查询参数和页面状态如何对应；
- 响应式布局在哪些视口发生变化；
- 表单的校验、提交中、成功、失败和重复提交如何处理；
- 键盘、焦点、屏幕阅读器和减少动画偏好如何支持；
- 页面标题、描述、结构化数据和分享预览是否需要；
- 加载、缓存、过期、重试和离线状态如何处理；
- Cookie、会话、跨域和权限失败如何处理；
- 核心 Web 指标和可接受的资源体积是多少；
- 是否有隐私、安全、合规或成本限制；
- 什么结果才算功能完成。

### 4.3 如何回答

必须完整回答会改变产品方向的问题。不要只回答“都可以”“你决定”或“用最佳实践”，因为这些回答会把产品决策隐式交给模型。

如果暂时不能决定，可以明确写：

```text
这个问题当前未确定。请列出 2—3 个方案、各自的取舍和你的推荐，但暂时不要写入最终决策。
```

如果 AI 一次提问太多，可以要求：

```text
一次只问一个最重要的问题。根据我的答案更新你的理解，再继续下一个问题。
```

### 4.4 `design-document.md` 应包含什么

完整的产品设计文档至少应包括：

1. 产品目标；
2. 非目标；
3. 目标用户；
4. 用户故事；
5. 核心用户流程；
6. 页面或功能模块；
7. 每个页面的正常、空、加载、错误和边界状态；
8. 业务规则；
9. 数据输入和输出；
10. 权限、登录和身份；
11. 平台与设备范围；
12. 隐私、安全与合规约束；
13. 验收标准；
14. 尚未确定的问题。

对 Web 项目，产品设计还应明确：

15. 信息架构与路由表；
16. 各断点的布局和内容优先级；
17. 表单字段、校验、错误文案和提交语义；
18. 元数据、SEO 和社交分享要求；
19. 键盘路径、焦点顺序、语义标签和无障碍要求；
20. 浏览器兼容范围；
21. 性能预算；
22. 前端可见错误与恢复路径。

### 第二步的完成标准

- [ ] AI 已经提出关键问题；
- [ ] 用户完整回答了会改变设计的内容；
- [ ] 未决问题被明确记录，而不是由 AI 猜测；
- [ ] 已生成 `design-document.md`；
- [ ] 文档可以独立说明产品，而不是只引用聊天记录；
- [ ] 尚未开始编码。

## 五、第三步：基于产品设计确定技术栈

产品设计明确后，再让 AI 推荐技术栈，并保存为 `tech-stack.md`。

技术方案应当简单但健壮。目标不是堆叠新框架，而是选择足够支撑产品、容易维护和验证的方案。

### 5.1 推荐提示词

```text
请阅读 @design-document.md，并检查仓库现状与目标 Web 运行环境。

基于产品目标、平台、功能、数据和非功能要求，推荐一套尽量简单但足够健壮的技术栈。说明每项技术解决什么问题、为什么适合、有哪些风险或限制，以及有哪些备选方案。

把最终结论保存为 tech-stack.md。当前只做技术决策，不要开始实现产品。
```

### 5.2 技术栈文档应覆盖

- 前端框架与语言；
- 渲染方式：CSR、SSR、SSG、ISR 或混合渲染；
- 路由、数据获取与缓存策略；
- UI 和样式方案；
- 后端或服务端方案；
- 数据库与数据模型方向；
- 身份认证；
- 文件或媒体存储；
- 状态管理；
- API 形式；
- 表单、认证、会话、Cookie、CORS 和 CSRF 策略；
- 图片、字体、脚本和其他静态资源策略；
- SEO、元数据和站点地图；
- 可访问性检查；
- 性能预算与监控指标；
- 测试框架；
- 单元、集成、浏览器端到端和视觉回归的边界；
- 构建、部署与运行环境；
- 日志、监控和错误处理；
- 安全、隐私和密钥管理；
- 目标平台兼容性；
- 依赖引入原则；
- 明确不采用的复杂方案。

### 5.3 选型检查问题

- 这个产品真的需要后端吗？
- 真的需要数据库吗？
- 是否能先用单体结构？
- 是否引入了两个功能重复的库？
- 当前场景真的需要客户端全量渲染吗？
- 内容是否需要被搜索引擎和社交平台正确抓取？
- 认证数据应该存放在哪里，是否错误使用了可被脚本读取的持久化？
- 服务端和客户端的信任边界是否明确？
- 是否存在 XSS、CSRF、SSRF、注入、开放重定向或越权风险？
- 依赖是否支持目标平台？
- 页面在慢网、无缓存和禁用部分能力时是否可恢复？
- 图片、字体和 JavaScript 体积是否有预算？
- 测试和部署是否足够简单？
- 如果 AI 生成代码，框架是否有稳定、清晰的范式？
- 技术方案是否解决了真实需求，而不是满足个人偏好？

### 第三步的完成标准

- [ ] 技术栈和产品设计相匹配；
- [ ] 每项关键选择都有理由；
- [ ] 复杂度被控制在必要范围内；
- [ ] 风险和待验证假设已记录；
- [ ] 浏览器、响应式、SEO、无障碍、安全、性能和部署策略已覆盖；
- [ ] 已生成 `tech-stack.md`；
- [ ] 尚未开始编码。

## 六、第四步：处理初始 PRD，并建立 Agent 项目规则

产品设计文档和技术栈完成后，需要明确最初 `PRD.md` 的后续角色。如果它只是临时启动材料，应在有效信息全部迁移后归档或删除，并同步更新相关引用；如果它仍是产品决策来源，则应继续保留并明确优先级。

这一步的核心目的不是“必须删除 PRD”，而是避免项目同时维护多份互相冲突的需求来源。执行时必须先确认 `design-document.md` 已完整承接需要保留的信息。

### 6.1 PRD 处理方式

```text
请检查 design-document.md 和 tech-stack.md 是否已经承接 PRD.md 中仍然有效的信息。

如果信息完整，再删除 PRD.md，并更新项目中所有引用该文件的相关文档。删除前列出将受影响的文件；不要删除尚未迁移的独有内容。
```

> 注意：删除属于不可逆风险较高的操作。实际执行时应先查看 Git 状态、确认文件已被版本控制或已备份，并由用户明确授权。

### 6.2 初始化 Agent 说明文件

在 Claude Code 或 Codex 中执行对应的项目初始化命令，生成：

- Claude Code 使用的 `CLAUDE.md`；或
- Codex 使用的 `AGENTS.md`。

不同工具的初始化命令可能不同。可以使用工具提供的 `/init` 或等价初始化能力，为目标 Web 仓库生成长期说明文件。

### 6.3 在说明文件中加入长期规则

至少加入以下三类规则：

1. 写任何代码前，必须完整阅读 `memory-bank/architecture.md`；
2. 写任何代码前，必须完整阅读 `memory-bank/design-document.md`；
3. 每完成一个重大功能或里程碑后，必须更新 `memory-bank/architecture.md`。

可以整理为：

```md
## 开发前置规则

- 修改任何代码前，完整阅读 `memory-bank/design-document.md`。
- 修改任何代码前，完整阅读 `memory-bank/architecture.md`。
- 按 `memory-bank/implementation-plan.md` 的顺序工作，一次只执行一个步骤。
- 当前步骤通过验证前，不得开始下一步。
- 每完成一个重大功能或里程碑，更新 `memory-bank/architecture.md`。
- 每完成一个已验收步骤，更新 `memory-bank/progress.md`。
- 修改页面后，用真实浏览器验证目标路由、视口、交互、控制台和网络请求。
- 交互控件优先使用语义 HTML，并验证键盘和焦点行为。
- 不把密钥、令牌或仅供服务端使用的配置暴露到浏览器包中。
- 不把客户端校验当成服务端授权或数据校验。
- 未经明确授权，不执行生产部署、数据库破坏性迁移或外部系统写入。
```

### 第四步的完成标准

- [ ] 已确认需求信息只有一个可信来源；
- [ ] 若删除 `PRD.md`，独有信息已迁移且用户已授权；
- [ ] 所有旧路径引用已更新；
- [ ] 已生成 `AGENTS.md` 或 `CLAUDE.md`；
- [ ] 开发前必读文档和更新规则已经写入。

## 七、第五步：生成详细但不含代码的实施计划

让 AI 同时读取 `design-document.md` 和 `tech-stack.md`，生成 `implementation-plan.md`。

这是整个流程最关键的文件之一。它不是概括性的路线图，而是一组给 AI 开发者执行的、小而具体的分步指令。

### 7.1 推荐提示词

```text
请完整阅读 @design-document.md 和 @tech-stack.md。

为这个产品生成一份详细的实施计划，供 AI 开发者逐步执行。计划必须按依赖顺序拆分；每一步要小而具体，并且能够单独完成、测试和验收。

每一步都要包含验证正确性的测试或检查方式。计划中不要写实现代码，只写清晰、具体、可执行的指令。将结果保存为 implementation-plan.md。
```

### 7.2 为什么计划中不能直接写代码

实施计划的作用是稳定“做什么、按什么顺序做、如何证明完成”。如果计划直接包含大量代码：

- 代码会在真正执行前过时；
- AI 容易把计划示例误当成唯一实现；
- 文档难以阅读和修改；
- 产品、技术和实现层会混在一起；
- 测试与完成标准容易被代码细节淹没。

计划可以写文件和模块名称、接口目的、数据流、验证方式，但不要写完整函数实现。

### 7.3 每一步的推荐结构

```md
## Step N：步骤名称

### 目标

完成后能观察到什么结果。

### 前置条件

- 已完成哪些步骤；
- 依赖哪些决策或文件。

### 操作

1. 创建或修改什么模块；
2. 实现什么行为；
3. 处理哪些正常和异常状态；
4. 不要处理哪些后续范围。

### 自动验证

- 类型检查；
- 单元测试；
- 集成测试；
- 浏览器端到端测试；
- 可访问性自动检查；
- 构建；
- 静态检查。

### 人工验收

- 从哪里进入；
- 使用哪个 URL、账号、测试数据、浏览器和视口；
- 做什么操作；
- 应看到什么结果；
- 哪些边界状态需要测试。
- 控制台是否无新增错误；
- 网络请求、重定向、刷新、前进后退是否正确；
- 键盘、焦点和屏幕阅读器语义是否合理；
- 移动端、桌面端和中间宽度是否可用。

### 完成定义

- [ ] 功能完成；
- [ ] 自动检查通过；
- [ ] 真实浏览器验证通过；
- [ ] 人工验收通过；
- [ ] 进度和架构文档更新。
```

### 7.4 拆分粒度

合适的步骤应该：

- 能在一次 Agent 会话中完成；
- 只交付一个主要结果；
- 有清晰的失败信号；
- 不依赖未来尚未实现的功能才能测试；
- 出错时可以定位和回退。

不合适的步骤示例：

- “完成整个前端”；
- “把后端写好”；
- “优化体验”；
- “处理所有边界问题”；
- “完成剩余功能”。

应拆成更具体的步骤，例如：

```text
建立项目骨架
→ 建立数据模型
→ 实现第一个确定性核心函数及测试
→ 实现基础页面壳
→ 接入核心函数
→ 增加空状态和错误状态
→ 完成持久化
→ 完成端到端测试
```

### 7.5 泛用 Web 实施顺序

不同项目会裁剪步骤，但通常按以下依赖顺序规划：

1. **仓库基线**：运行命令、环境变量示例、格式化、静态检查、测试和构建；
2. **应用骨架**：渲染入口、路由、全局错误边界、页面壳和基础样式；
3. **设计基础**：颜色、字体、间距、断点、语义组件和交互状态；
4. **数据契约**：类型、Schema、API 请求/响应、错误码和测试夹具；
5. **服务端基础**：配置、认证、数据库、迁移、授权和日志，仅在需要时建立；
6. **第一条垂直切片**：从页面输入到服务端/本地逻辑再到结果展示的最小闭环；
7. **其余功能切片**：一次一条用户可验收路径；
8. **异常与恢复**：空、加载、失败、超时、重试、离线、权限不足和数据冲突；
9. **响应式与浏览器兼容**：移动、桌面、中间宽度及目标浏览器；
10. **可访问性**：语义、键盘、焦点、标签、对比度、动态内容通知和减少动画；
11. **性能**：关键资源、图片、字体、代码分割、缓存和核心 Web 指标；
12. **安全与隐私**：输入、输出编码、授权、Cookie、CSRF、CORS、上传、日志和密钥；
13. **SEO 与分享**：仅在业务需要时处理元数据、规范链接、站点地图和结构化数据；
14. **预发布与部署**：生产构建、迁移、环境配置、监控、烟雾测试和回滚。

每一步都必须交付可以观察的 Web 行为，不以“新增若干文件”作为唯一完成标准。

随后创建两个空文件：


```text
memory-bank/
├── design-document.md

```

### 8.1 推荐提示词

```text
请创建 memory-bank 目录。

把 design-document.md、tech-stack.md 和 implementation-plan.md 移动到该目录。然后在目录中创建 progress.md 和 architecture.md。

移动完成后，检查项目全部 Markdown 和说明文件中对这些文档的路径引用，并修正为新路径。先报告计划修改的文件，再执行移动和更新。
```

### 8.2 初始化 `progress.md`

`progress.md` 创建后不应长期保持空白。开始执行前应填入基本结构：

```md
# Progress

## 当前状态

- 当前阶段：规划完成，尚未编码
- 当前步骤：等待细化 implementation plan
- 阻塞：无

## 已完成

- [x] 初始需求整理
- [x] 产品设计文档
- [x] 技术栈文档
- [x] 初版实施计划

## 验证记录

暂无。

## 下一步

- 对实施计划做最终澄清。
```

### 8.3 初始化 `architecture.md`

在没有代码时，也可以先记录规划状态：

```md
# Architecture

## 当前状态

项目尚未开始实现，本文件将在建立项目骨架后更新。

## 核心文档

- `design-document.md`：产品与交互设计
- `tech-stack.md`：技术选择
- `implementation-plan.md`：实施顺序和验收
- `progress.md`：执行进度和验证记录

## 更新规则

每完成一个重大功能或里程碑后，记录当前目录、模块职责、数据流和关键文件用途。
```

### 8.4 检查路径

文件移动后必须搜索：

- `design-document.md`；
- `tech-stack.md`；
- `implementation-plan.md`；
- 旧的 `/memory-bank` 或相对路径；

确保引用从：

```text

```

变成类似：

```text

```

- 没有误包含密钥、个人文件或构建产物；
- 工作区中是否有其他人的未提交改动；
- 文件移动后的链接有效；
- 用户明确允许创建提交。

建议提交信息：

```text
docs: establish vibe coding memory bank
```

- [ ] 已生成不含实现代码的详细计划；

- [ ] 三份核心文档已进入 `memory-bank/`；
- [ ] `progress.md` 和 `architecture.md` 已创建；
- [ ] 所有路径引用已更新；
- [ ] 如用户授权，已建立编码前 Git 基线。

## 九、第六步：再次细化实施计划

第一次生成的实施计划往往仍然存在隐含假设。正式编码前，让 AI 完整阅读 Memory Bank，并针对 `implementation-plan.md` 再做一次澄清。

目标是让 AI 对计划中的每一步都达到可以执行的明确程度。

### 9.1 推荐提示词

```text
请完整阅读 memory-bank 中的所有文档。

重点检查 implementation-plan.md：它是否足够清晰、具体、完整，能够让你按顺序执行而无需自行猜测产品或技术决策？

请列出仍需我澄清的问题。优先询问会影响范围、架构、数据、交互、步骤顺序或验收方式的问题。我们讨论完成后，请同步更新所有受影响的 memory-bank 文档。

在计划达到可执行状态前不要写代码。
```

### 9.2 应重点检查的问题

#### 需求方面

- 是否有同名但含义不同的功能；
- 是否缺少角色或权限；
- 是否缺少错误、空状态或撤销行为；
- 是否缺少数据保留和删除规则；
- 验收标准是否可以观察。

#### 技术方面

- 模块依赖顺序是否正确；
- 数据模型是否足以支持后续功能；
- 是否需要迁移、种子数据或测试夹具；
- 是否有第三方服务或密钥；
- 是否有目标平台兼容风险；
- 测试环境是否能够建立。
- 路由直达、刷新、前进后退和 404 是否有明确行为；
- 浏览器端与服务端的代码边界是否清楚；
- API 错误、超时、重试、取消和重复提交是否定义；
- 会话过期、未登录、无权限和跨站请求是否处理；
- 数据库迁移是否向前兼容并可安全回滚；
- 预览环境是否足以复现生产构建；
- 性能、SEO、可访问性和浏览器兼容性是否有验证办法。

#### 实施方面

- 每一步是否过大；
- 每一步是否有独立验证方式；
- 是否存在必须在前一步建立的基础能力；
- 是否把两个无法一起验收的结果塞进同一步；
- 是否会在某一步产生无法恢复的中间状态。

### 9.3 回答后要更新什么

不能只在聊天中回答。答案影响哪个文档，就必须更新哪个文档：

| 回答影响 | 更新文件 |
| --- | --- |
| 产品目标、页面、流程、规则 | `design-document.md` |
| 技术、依赖、架构选择 | `tech-stack.md` |
| 顺序、粒度、测试和验收 | `implementation-plan.md` |
| 当前状态或阻塞 | `progress.md` |

### 第六步的完成标准

- [ ] AI 已完整阅读 Memory Bank；
- [ ] 关键歧义已由用户回答；
- [ ] 所有受影响文档已同步更新；
- [ ] 每一步都能独立执行和验收；
- [ ] Agent 不需要在编码时重新发明产品决策。

## 十、第七步：只执行实施计划的第一步

计划明确后，才开始编码。第一次只执行 `implementation-plan.md` 的 Step 1。

需要提前建立一条硬规则：你负责最终功能测试；在你确认当前步骤通过前，AI 不得开始下一步。

### 10.1 推荐提示词

```text
请完整阅读 memory-bank 中的所有文档，然后只执行 implementation-plan.md 的 Step 1。

严格遵守该步骤的范围和完成定义，不要提前实现 Step 2 或后续内容。完成实现后，运行本步骤要求的自动测试、检查或构建，并报告结果。

我会负责最终的功能测试和验收。在我明确确认当前步骤通过之前，不要开始下一步。

当前步骤验收通过后，请在 progress.md 记录完成内容、验证结果和遗留事项，并在 architecture.md 中补充新的架构信息和关键文件用途。
```

### 10.2 Agent 在当前步骤中应做什么

1. 读取 Memory Bank；
2. 复述 Step 1 的目标和完成定义；
3. 检查当前仓库状态；
4. 只修改当前步骤必要的文件；
5. 运行当前步骤要求的静态检查、测试和构建；
6. 启动或复用本地 Web 服务；
7. 在真实浏览器中打开精确 URL，验证目标视口和交互；
8. 检查控制台错误、失败请求、重定向和页面状态；
9. 对视觉改动保存截图，对交互改动记录操作路径；
10. 报告修改内容和验证证据；
11. 给出用户测试路径；
12. 停止并等待验收。

### 10.3 Web 浏览器验证证据

一次可信的浏览器验证至少说明：

| 项目 | 应记录内容 |
| --- | --- |
| URL | 完整路由与必要查询参数 |
| 构建 | 开发模式、预览构建或部署环境 |
| 浏览器 | 至少记录实际使用的浏览器 |
| 视口 | 宽、高和设备像素比；视觉任务必须固定 |
| 前置数据 | 测试账号、fixture、数据库状态或 mock |
| 操作 | 点击、输入、刷新、返回等实际步骤 |
| 结果 | 页面、URL、数据和状态变化 |
| 控制台 | 是否出现新增 error / warning |
| 网络 | 关键请求状态、失败、取消和重复请求 |
| 截图 | 视觉或响应式变更应保存关键状态截图 |

以下情况不能只靠读取 DOM 或代码宣布完成：

- CSS、布局、动画和响应式变化；
- 浮层、下拉、拖拽、焦点和键盘交互；
- 文件上传、下载和浏览器权限；
- OAuth、Cookie、重定向和跨域流程；
- 虚拟列表、Canvas、富文本编辑器和其他高度交互界面。

### 10.4 用户如何验收

用户不应只问“做完了吗”，而应按照步骤中的验收路径实际测试：

- 能否按预期启动；
- 目标操作是否可完成；
- 输入和输出是否正确；
- 错误状态是否合理；
- 刷新或重启后状态是否符合设计；
- 是否破坏已有功能；
- 视觉和交互是否满足预期。
- 直接打开深层路由、刷新、前进和后退是否正确；
- 移动窄屏、常见桌面宽度和中间宽度是否出现溢出或遮挡；
- 仅用键盘能否完成核心路径，焦点是否可见且顺序合理；
- 表单标签、错误文案和提交反馈是否清楚；
- 慢网、服务失败和会话过期时是否能恢复；
- 页面标题、描述和分享预览是否符合需要；
- 核心请求是否避免泄露密钥或敏感数据。

测试失败时，告诉 AI：

```text
Step 1 尚未通过验收。实际操作路径是：……
预期结果是：……
实际结果是：……
相关错误或截图是：……

请只诊断和修复 Step 1，不要开始 Step 2。修复后重新运行本步骤的检查，并再次给出验收路径。
```

### 10.5 验收通过后更新文档

`progress.md` 至少记录：

- 步骤名称；
- 完成日期；
- 实际完成的行为；
- 新增或修改的关键文件；
- 自动测试结果；
- 人工验收结果；
- 与原计划的偏差；
- 遗留问题；
- 下一步。

`architecture.md` 至少记录：

- 新增目录和模块；
- 每个关键文件的职责；
- 模块依赖关系；
- 数据如何流动；
- 对外接口或边界；
- 已确定的架构决策。

### 第七步的完成标准

- [ ] 只实现 Step 1；
- [ ] 自动检查完成；
- [ ] 用户亲自完成验收；
- [ ] 未通过时没有开始 Step 2；
- [ ] 通过后已更新 `progress.md`；
- [ ] 通过后已更新 `architecture.md`。

## 十一、第八步：清理上下文，循环执行后续步骤

Step 1 通过后，按同样方法执行 Step 2、Step 3，直到最后一步。

开始下一步前先清理上下文，再让新的上下文从 Memory Bank 恢复状态。这样可以减少长对话中的噪声、错误假设和注意力漂移。

在支持斜杠命令的工具中可以使用 `/clear`。若工具没有该命令，可以开启新会话，但必须保留同一个项目和 Memory Bank。

### 11.1 恢复上下文提示词

```text
请先完整阅读 memory-bank 中的所有文档，尤其是 progress.md、architecture.md 和 implementation-plan.md。

根据 progress.md 确认之前已经完成并验收的步骤，再继续执行 implementation-plan.md 的 Step X。不要重复已经验收的工作，也不要开始 Step X+1。

完成 Step X 后运行对应的自动检查并报告结果。我会负责功能测试和验收；在我确认通过前不要继续下一步。验收通过后，更新 progress.md 和 architecture.md。
```

### 11.2 每一步的固定循环

```text
清理或切换上下文
→ 读取全部 memory-bank
→ 根据 progress 确认当前位置
→ 执行 Step X
→ 运行自动验证
→ Agent 汇报证据
→ 用户功能测试
→ 若失败，留在 Step X 修复
→ 若通过，更新 progress 和 architecture
→ 停止
→ 下一轮执行 Step X+1
```

### 11.3 为什么每轮都要读取全部 Memory Bank

- `design-document.md` 防止实现偏离产品；
- `tech-stack.md` 防止随意更换技术；
- `implementation-plan.md` 告诉 Agent 当前任务的范围和顺序；
- `progress.md` 防止重复实现或跳步；
- `architecture.md` 告诉 Agent代码现在真实存在于哪里、各文件负责什么。

仅仅读取 `implementation-plan.md` 不够，因为它描述的是计划，不一定反映实现过程中已经发生的架构变化。

### 11.4 如何防止 Agent 越过验收门

每轮提示词都明确：

- 只执行 Step X；
- 不执行 Step X+1；
- 自动测试不等于人工验收；
- 用户明确说“通过”后才允许更新为完成；
- 当前步骤失败时，只修当前步骤。

如果 Agent 顺手实现了后续范围，应要求它：

```text
这部分属于 Step X+1，不在当前授权范围内。请停止继续扩展，列出越界修改，并提出安全恢复方案；在我确认前不要删除或覆盖文件。
```

### 第八步的完成标准

- [ ] 每轮从 Memory Bank 恢复上下文；
- [ ] `progress.md` 与代码真实状态一致；
- [ ] 每次只推进一个步骤；
- [ ] 每一步都有自动验证和人工验收；
- [ ] 当前步骤不通过时不会继续；
- [ ] 架构发生变化后及时更新文档；
- [ ] 循环一直持续到实施计划最后一步。

## 十二、第九步：完成并享受成果

当 `implementation-plan.md` 的最后一步通过验证后，项目进入完成阶段。

流程完成时，成果不仅是能运行的代码，还包括一套可以继续维护的项目记忆：

- 产品为什么这样设计；
- 技术为什么这样选择；
- 实施按什么顺序完成；
- 每一步如何验证；
- 当前架构是什么；
- 哪些问题仍未解决；
- 下一位开发者如何继续。

### 12.1 预发布质量门

“开发完成”与“可以上线”是两个不同状态。最后一个功能步骤通过后，还要单独执行预发布门禁。

#### 功能与数据

- 核心用户路径在接近生产的构建中通过；
- 空、加载、错误、超时、权限不足和会话过期可恢复；
- 数据迁移已在非生产环境演练；
- 重复提交、刷新、后退和并发操作不会破坏数据；
- 破坏性数据操作有备份、确认和回滚方案。

#### 浏览器与响应式

- 目标浏览器全部通过最小烟雾测试；
- 关键页面覆盖移动、桌面和中间宽度；
- 没有横向溢出、遮挡、不可点击或不可滚动区域；
- 深层 URL、404、刷新、前进和后退正确；
- 浏览器控制台无新增未解释错误。

#### 可访问性

- 页面语言、标题层级和语义区域正确；
- 核心路径可以只用键盘完成；
- 焦点可见，弹窗和浮层能正确进入、约束和返回焦点；
- 表单字段有标签，错误与字段建立关联；
- 图片有合适的替代文本或被标记为装饰；
- 颜色对比、减少动画和动态状态通知符合目标要求；
- 自动检查结果经过人工抽查，不把零自动告警当成完整无障碍证明。

#### 性能

- 生产构建没有意外包含大型调试依赖；
- 图片尺寸、格式和懒加载策略合理；
- 字体加载不会造成明显空白或布局跳动；
- JavaScript 和 CSS 体积符合记录的预算；
- 关键页面在冷缓存和受限网络下仍可使用；
- 核心 Web 指标达到设定目标，或偏差已被明确接受。

#### 安全与隐私

- 服务端对敏感操作重新执行认证、授权和输入校验；
- 输出编码、富文本、URL、文件名和上传内容经过安全处理；
- Cookie、CSRF、CORS、重定向和缓存策略符合实际威胁模型；
- 前端包、Source Map、日志和错误页面不泄露密钥或敏感数据；
- 依赖和生产配置经过必要检查；
- 隐私声明、同意、数据保留和删除行为与产品承诺一致。

#### SEO 与分享（需要时）

- 每个可索引页面有正确的标题和描述；
- 规范 URL、robots、站点地图和重定向正确；
- 分享卡片元数据可被目标平台读取；
- 结构化数据合法且与可见内容一致；
- 不应索引的私有、重复或临时页面已排除。

#### 运维与回滚

- 生产环境变量、域名、证书和第三方回调地址已确认；
- 部署命令和迁移顺序已记录；
- 健康检查、错误监控和关键业务信号已配置；
- 能识别发布是否成功，并能在失败时回滚；
- 上线后烟雾测试包含首页、核心路径、登录、关键 API 和错误监控；
- 生产部署属于外部状态变更，必须得到明确授权。

### 12.2 最终检查

- [ ] 实施计划所有步骤都标记完成；
- [ ] 每一步都有测试或验收证据；
- [ ] 产品设计与实现不存在关键冲突；
- [ ] 技术栈文档与实际依赖一致；
- [ ] `progress.md` 记录最终状态；
- [ ] `architecture.md` 反映当前真实结构；
- [ ] 没有遗留的临时文件、密钥或调试开关；
- [ ] 运行、测试、构建和部署方式已记录；
- [ ] 生产构建已在本地或预览环境验证；
- [ ] 响应式、浏览器、键盘和关键可访问性路径已验证；
- [ ] 控制台、网络、性能、安全和隐私检查已完成；
- [ ] 部署、迁移、监控、烟雾测试和回滚方案已记录；
- [ ] 如需提交或发布，已获得用户授权。

## 十三、完整提示词清单

为了便于实际使用，下面把九步中的关键提示词集中整理。

### Prompt 1：从初始 PRD 生成产品设计

```text
完整阅读 @PRD.md。先不要写代码。找出所有会影响产品设计或实现方向的歧义、缺失和冲突，并逐项向我提问。

我们讨论清楚后，把确认结果整理成 design-document.md。文档应独立说明产品目标、非目标、用户、流程、路由、页面状态、响应式规则、表单、数据、SEO、可访问性、浏览器范围、性能预算、安全边界和验收标准。
```

### Prompt 2：确定技术栈

```text
阅读 @design-document.md、目标仓库和 Web 运行环境，为产品推荐尽量简单但足够健壮的技术栈。覆盖渲染、路由、样式、数据、服务端、认证、测试、浏览器验证、部署、安全、性能和可访问性；说明选择理由、限制、风险、替代方案和待验证假设，保存为 tech-stack.md。不要编码。
```

### Prompt 3：生成实施计划

```text
完整阅读 @design-document.md 和 @tech-stack.md，生成 implementation-plan.md。

按依赖关系把工作拆成小而具体、可单独验证的步骤。每一步包含目标、前置条件、操作、自动测试、真实浏览器验证、人工验收和完成定义。计划中不要包含实现代码。
```

```text
创建 memory-bank 目录，把 design-document.md、tech-stack.md、implementation-plan.md 移入该目录，并创建 progress.md 与 architecture.md。
```

### Prompt 7：执行任意后续步骤

```text
完整阅读 memory-bank 中所有文档，根据 progress.md 确认已完成步骤，然后只执行 implementation-plan.md 的 Step X。

不要重复已验收工作，也不要开始 Step X+1。完成后运行自动检查和真实浏览器验证，提供可复现证据并等待我的功能验收；通过后更新 progress.md 和 architecture.md。
```

```text

核对文档与代码是否一致，说明已完成步骤、当前阻塞和唯一的下一步。不要重复已验收内容；确认无冲突后，只继续下一步。
```

## 十五、常见失败方式

### 15.1 PRD 写得太模糊就开始开发

症状：AI 不断猜测用户、流程和边界。

处理：回到第一、二步，让 AI 反向提问并更新 `design-document.md`。

### 15.2 只在聊天里确认，不更新文件

症状：换会话后，同一个问题再次出现。

处理：任何稳定结论必须进入对应的 Memory Bank 文件。

### 15.3 实施计划粒度过大

症状：一个步骤修改几十个文件，测试失败后难以定位。

处理：把步骤拆成可独立运行、验证和回退的结果。

### 15.4 自动测试通过就直接推进

症状：内部函数正确，但真实用户路径不可用。

处理：自动检查之后必须经过人工功能验收。

### 15.5 AI 自动开始下一步

症状：当前问题尚未解决，后续代码已建立在错误基础上。

处理：每轮提示词都明确“通过前不进入下一步”，越界时立即停止。

### 15.6 `progress.md` 不更新

症状：新会话不知道做到哪里，重复工作或跳步。

处理：每个步骤只有在 `progress.md` 记录验收结果后才算完成。

### 15.7 `architecture.md` 只写理想架构

症状：文档中的目录和真实代码不一致。

处理：架构文档记录当前真实状态，不把未来计划写成已实现事实。

### 15.8 长会话不清理上下文

症状：Agent 混淆旧要求、错误日志和已废弃方案。

处理：一个步骤一个上下文；开始下一步前清理，并从 Memory Bank 恢复。

### 15.9 未确认就执行删除或 Git 操作

症状：丢失用户文件、把无关改动混入提交或覆盖他人工作。

处理：删除、移动、提交、推送和发布前先检查精确范围并获得授权。

### 15.10 只看代码，不看真实浏览器

症状：组件结构看似正确，但页面溢出、浮层被裁切、点击目标错位、控制台报错或请求重复。

处理：所有可见或交互变化都在目标 URL 和视口中验证，并同时检查截图、控制台和网络。

### 15.11 只验证一个视口

症状：桌面端正常，窄屏无法操作；或移动端正常，中间宽度出现断裂。

处理：为每个页面定义至少一个窄屏、一个常见桌面宽度和必要的中间临界宽度；按布局变化点测试，而不是只按设备名称测试。

### 15.12 把自动可访问性检查当成最终证明

症状：扫描没有报错，但键盘无法完成任务、焦点丢失或动态状态没有被读出。

处理：自动扫描后，人工走一遍核心键盘路径，检查焦点、标签、错误关联和动态通知。

### 15.13 把前端校验当成安全边界

症状：隐藏按钮或修改请求即可绕过权限、价格、状态或数据规则。

处理：客户端校验只改善体验；服务端必须重新认证、授权、校验输入并计算敏感结果。

### 15.14 到最后才测试生产构建

症状：开发模式正常，生产构建出现环境变量、路由、静态资源、SSR 水合或缓存问题。

处理：尽早建立生产构建和本地预览步骤，在每个关键里程碑重复验证。

### 15.15 没有部署和回滚闭环

症状：代码通过但无法安全上线，或上线失败后不知道怎样恢复。

处理：实施计划必须包含预览环境、迁移顺序、监控、烟雾测试和明确回滚路径；生产部署需单独授权。

## 十六、核心思想总结

这套 Web Vibe Coding 流程可以归纳为七条规则：

1. **先讨论，再编码。** 初始 PRD 只是讨论入口，产品设计要经过反向提问。
2. **把决策写进文件。** 不依赖聊天记录保存产品和技术结论。
3. **先计划，再执行。** 实施计划要小、具体、无代码且可验证。
4. **一次只做一步。** 当前步骤没有通过自动检查和人工验收，不进入下一步。
5. **持续维护项目记忆。** `progress.md` 记录做到哪里，`architecture.md` 记录项目现在是什么样。
6. **用文档恢复上下文。** 每次清理会话或更换 Agent，都从 Memory Bank 重新建立准确理解。
7. **以真实 Web 行为为证据。** 代码、类型和单测通过后，还要验证浏览器、响应式、键盘、网络、性能、安全和部署结果。

最终的工作方式是：

```text
人负责目标、取舍和验收
AI 负责澄清、计划、实现、检查和记录
文档负责跨会话保存项目事实
测试负责决定是否允许继续
```

当最后一个步骤通过，这个项目留下的不只是一次生成的代码，而是一套能够被继续理解、验证和维护的工程系统。
