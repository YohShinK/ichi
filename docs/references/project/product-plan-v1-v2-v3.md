## 0. 结论先行

ICHI 不在第一版同时承担计算、外部内容聚合和开放社区治理三种风险，而是按三阶段逐步建立产品能力。

| 阶段 | 产品形态 | 主要验证问题 | 明确不做 |
| --- | --- | --- | --- |
| V1 | 一番赏即时计算工具 | 用户是否愿意在连续抽取过程中用点击记录票池，并依据即时反馈作出下一步决策 | 好版地图、公共上传、社群、外部平台抓取 |
| V2 | 好版线索地图 | 合法取得并带来源、时间展示的好版线索，是否能帮助用户更快发现值得核对的版面 | 用户共同维护实时库存、无证据的公共更新 |
| V3 | 可信票池社群 | 玩家能否低摩擦贡献带证据的抽取结果，并形成可追溯、可纠错的公共票池观察 | 把用户自报包装成官方实时库存 |

三阶段的关系是：

```text
V1：现场计算
  ↓ 验证高频使用和状态交互
V2：远程发现
  ↓ 验证合法数据供给、时效和到店转化
V3：公共贡献
  ↓ 用证据审核把私人记录转成公共观察
长期形态：发现版面 → 到店计算 → 集中上传 → 社群状态更新
```

V1 是可以独立成立和持续迭代的真实产品版本，不是一次性原型。V2 或 V3 无法达到启动门槛时，产品仍可保留并深化即时计算能力。

### 0.1 对现有 PRD 的范围变更

本计划根据产品发现重新收敛版本范围。进入开发前，应同步更新现有 PRD 的版本规划和 MVP 验收章节。

| 现有 PRD 方向 | 新路线 | 处理方式 |
| --- | --- | --- |
| 首版同时覆盖计算、识别、愿望、风险、Last、稀有度、地点和成就 | V1 只保留即时计算闭环 | 其余能力按是否增强现场计算逐项评审，不默认进入 V1 |
| 地点能力与计算同时出现 | 好版地图延后到 V2 | V1 不接入外部平台内容 |
| 公共票池作为潜在后续能力 | 社群明确延后到 V3 | V3 启动前另写治理与审核规格 |
| 用户输入可辅助个人判断 | 私人记录与公共状态严格分离 | 未审核点击记录永不直接改变公共版面 |

## 1. 产品机会是怎么发现的

本路线不是从“必须使用 AI”倒推功能，而是经过替代性、使用摩擦和可信度检验后形成。

### 1.1 起点：现场决策需求

用户站在一番赏版面前，需要在较短时间内判断：

- 再抽几次；
- 目标奖的命中概率；
- 是否接近包套条件；
- 继续抽、直接购买还是停止；
- 每次抽取之后，新的票池是否比上一刻更值得继续。

这一场景的关键不是得到一次答案，而是在票池不断变化时持续获得反馈。

### 1.2 与通用聊天产品的替代性检验

我们用下面的问题检验差异：

> 用户能否拍一张照片发给 ChatGPT，再说“我想要 A 赏，帮我算一下”，就完成主要任务？

如果产品只是“拍照—识别—返回一段建议”，答案很可能是可以。ICHI 因此不能把核心价值建立在一次性 AI 回答上，而需要提供：

- 无需组织 Prompt 的结构化输入；
- 一张可直接操作的抽赏版面；
- 每次点击后毫秒级更新的确定性计算；
- 连续抽取期间始终保留的票池、目标和预算状态；
- 可核对的公式和输入，而不是不可解释的模型判断。

### 1.3 Agent 式循环与现场摩擦

理想循环是：

```text
录入票池
→ 设置目标和预算
→ 查看下一批抽数的结果
→ 用户实际抽取
→ 点击记录本轮奖项
→ 更新票池与计算
→ 再次决策
```

它具备状态、目标、反馈和连续决策，具有 Agent 式体验。但如果要求用户每抽一张都拍照、上传并等待审核，现场摩擦会超过价值。

由此形成关键设计决定：

> 抽取过程只做私人点击记录；只有用户主动贡献公共情报时，才集中拍摄本轮赏券并进入审核。

### 1.4 社群可信度问题

最初设想是让用户抽完后直接更新门店公共版面，但发现三个根本问题：

1. 手工点击可以帮助本人计算，却不能证明公共事实；
2. 一张版面照片只能证明拍摄时刻，无法保证几分钟后没人继续抽；
3. 一张撕开赏券的照片只能证明“可能抽到了什么”，不能单独证明来自哪家店、哪套票池和哪个时间。

因此，社群不能把任意上传直接显示为当前库存，必须使用票池身份、前一可信状态、证据审核和版本回退机制。

### 1.5 中文互联网调研与好版线索

通过网页搜索和 Ego 浏览器观察中文互联网，发现用户已经在生产和交换“好版”信息：

1. 百度一番赏吧覆盖晒奖、交易、规则、纠纷和城市交流。[一番赏吧](https://tieba.baidu.com/f?kw=%E4%B8%80%E7%95%AA%E8%B5%8F)
2. 搜索结果中存在城市一番赏微信群招募，说明本地玩家有交换线下信息的需求。[上海一番赏微信群帖子](https://tieba.baidu.com/p/8088063617)
3. 小红书存在“绝世好板”“剩 14 抽”“剩 11 抽可包套”“还有吗”等帖子和评论。

代表案例包括：

- [路过崩铁绝世好板](https://www.xiaohongshu.com/explore/6a3d12d5000000000f02b455)：评论出现“还有吗”“明天去，希望还有”等到店意向。
- [线下崩铁一番赏版面（剩 14 抽）](https://www.xiaohongshu.com/explore/6a608aa0000000002201a4a4)：正文列出余奖、包套成本和地点，并在售罄后更新状态。

这说明好版地图存在值得验证的机会，但它依赖平台授权、内容时效和第三方数据治理，不适合与 V1 计算工具同时开发。因此将其独立为 V2。

### 1.6 三阶段机会定义

1. **V1 现场计算**：把一次性问答变成持续、低摩擦、可复现的票池交互。
2. **V2 远程发现**：把合法取得的零散好版内容变成可按地点、系列和时间筛选的线索。
3. **V3 公共可信状态**：把私人抽取记录经过集中拍照和审核，转化为公共票池观察。

## 2. 全阶段产品原则

1. **一阶段只验证一个核心不确定性**：V1 验证计算交互，V2 验证线索供给，V3 验证公共贡献与信任。
2. **计算和生成分开**：概率、期望、预算、Last 和包套由确定性算法计算；大模型不心算。
3. **私人状态与公共状态分开**：点击记录可以零摩擦，但未经证据审核不得影响社群版面。
4. **数据获取和 AI 分开**：大模型只处理已经合法取得的内容，不能替代数据授权。
5. **观察不是库存**：地图线索和用户证据只证明某个时间发生过什么，不承诺当前实时库存。
6. **来源和时间不可隐藏**：V2、V3 的每条公共信息必须可追溯，并明确观察时间和新鲜度。
7. **错误更新必须可逆**：公共版面以版本链保存，驳回或作废时回到最近可信节点，不覆盖历史。
8. **不评价商家人格或信用**：不提供店铺黑名单、风险分或未经授权的“可信店铺”标签。
9. **保护预算优先**：不使用“冲一把”“马上回本”等刺激性文案，始终提供停止和直接购买比较。

## 3. V1：一番赏即时计算工具

### 3.1 V1 产品目标

V1 只验证一个核心命题：

> 用户是否愿意在连续抽取过程中，用几次点击维护票池，并根据每次即时更新的概率、成本和期望反馈决定下一步？

V1 不依赖账号体系、云端审核、地图数据或大模型 API，也不需要外部平台内容即可完成核心闭环。

### 3.2 核心用户流程

```text
选择系列模板或创建空白票池
→ 核对剩余票数和各奖项余量
→ 设置目标奖、预算和最多抽数
→ 查看抽 k 次的概率、成本和方案比较
→ 实际抽取若干次
→ 点击本轮抽到的奖项
→ 票池与结果即时更新
→ 继续、包套、直接购买或停止
```

用户可以一抽一记，也可以连续抽几张后一次点击多张奖项。记录只服务于本人，不需要拍照或审核。

### 3.3 交互形态

主页面是一张由 ICHI 独立设计的可操作票池：

- A—J、SP、Last 等抽象奖项以格子或卡片表示；
- 点击奖项表示本轮抽出一张，再次点击可增加数量；
- 长按或减号可以撤销误操作；
- 页面始终显示本轮尚未确认的记录；
- 确认本轮后再写入票池历史，支持撤销最近一轮；
- 每次状态变化后，概率和成本在同一页面更新，不跳转到聊天结果页。

界面不得照搬官方版面的 Logo、角色图、奖品图、字体、配色、装饰和整体编排。

### 3.4 输入

- 系列模板或空白票池；
- 剩余总票数 `R`；
- 各奖项剩余数量 `n_i`；
- 单抽价格 `c`；
- 用户目标奖集合；
- 计划抽数 `k`；
- 剩余预算 `B`；
- 可选：用户自己填写的各奖项主观价值 `v_i`；
- 可选：Last 赏及包套条件。

所有识别或模板数据进入计算前都允许用户修改。缺失字段不得由模型猜测。

### 3.5 输出

- 单抽命中目标奖概率；
- 抽 `k` 次至少命中一次的概率；
- 抽 `k` 次命中指定数量的分布；
- 当前票池中目标奖的条件期望抽数；
- 本轮和累计花费；
- 剩余预算可支持的最大抽数；
- 包套所需成本；
- 抽取、包套、直接购买和停止的并列比较；
- 用户自定义价值下的期望净值；
- 输入冲突、票数不守恒或目标奖已抽完等提示。

### 3.6 关键计算

设当前剩余总票数为 `R`，目标奖剩余数量为 `T`，不放回抽取 `k` 次。

单抽命中概率：

```text
P(hit in 1) = T / R
```

抽 `k` 次至少命中一次：

```text
P(hit ≥ 1 in k)
= 1 - C(R - T, k) / C(R, k)
```

命中恰好 `x` 次：

```text
P(X = x)
= C(T, x) × C(R - T, k - x) / C(R, k)
```

用户自定义奖品价值下，单抽奖品价值期望：

```text
EV_prize = Σ(n_i / R × v_i)
EV_net = EV_prize - c
```

条件期望和复杂分布可使用动态规划或精确组合数算法，但同一输入必须始终得到同一结果，并配套测试向量。

### 3.7 “期望”的展示边界

产品必须区分：

- **概率**：命中某奖的机会；
- **期望抽数**：在当前票池和给定条件下的数学平均；
- **奖品价值期望**：只有用户填写或选择价值假设后才能计算；
- **实际结果**：单个用户的一次抽取可能远离期望。

不得把数学期望表达为稳赚、回本、保底或购买建议。所有价值假设都要显示来源，并允许用户修改。

### 3.8 本地状态与历史

```ts
type DrawSession = {
  id: string
  startedAt: string
  initialPool: PrizePool
  currentPool: PrizePool
  targetPrizeIds: string[]
  budget?: number
  spent: number
  rounds: DrawRound[]
}

type DrawRound = {
  id: string
  recordedAt: string
  prizes: Array<{ level: string; count: number }>
  cost: number
  status: 'draft' | 'confirmed' | 'reverted'
}
```

V1 默认本地保存，不自动公开。用户清除记录后应能够彻底删除本地会话。

### 3.9 页面结构

1. **开始页**：选择模板、继续上次记录或创建空白票池。
2. **票池页**：编辑余量、设置目标和预算。
3. **抽取页**：核心交互版面、即时概率和本轮快捷记录。
4. **方案比较层**：抽取、包套、直接购买、停止的并列信息。
5. **历史页**：查看并撤销本次会话的轮次。
6. **方法说明**：公式、假设、隐私和非官方声明。

### 3.10 技术架构

```text
H5 / 微信小程序
├── 票池编辑与状态机
├── TypeScript 确定性计算内核
├── IndexedDB / 本地存储
├── 公式解释与测试向量
└── 可选模板静态资源
```

V1 核心计算不调用大模型 API。未来的拍照识别可以作为独立增强能力，但不得阻塞手动录入和即时计算。

### 3.11 V1 范围

本期做：

- 空白票池和至少 3 个不同奖项结构的模板；
- 票池余量编辑；
- 目标、抽数、预算和主观价值设置；
- 不放回概率、成本、期望和包套计算；
- 连续多轮快捷记录；
- 误操作撤销和票数一致性校验；
- 本地历史；
- 独立视觉设计与响应式页面；
- 公式单元测试和边界测试。

本期不做：

- 好版地图；
- 小红书或其他平台内容采集；
- 公共票池、用户上传和社区审核；
- 店铺评价和实时库存；
- 依赖大模型的核心计算；
- 未经授权的官方角色、奖品图和版面复刻。

### 3.12 V1 验收标准

- 常见手机尺寸下，用户能在 60 秒内建立一个票池并开始计算；
- 从抽到奖项到看到新结果不超过 300 毫秒；
- 用户连续记录 20 轮后，剩余票数和各奖项数量仍保持守恒；
- 最近一轮误操作可以完整撤销；
- 组合概率与预置测试向量一致；
- 目标奖为 0、抽数大于余票、预算不足等边界均有明确反馈；
- 用户能够解释“概率”“期望抽数”和“价值期望”三者差别；
- 完成核心流程不需要登录、上传照片或调用大模型。

### 3.13 V1 指标

核心指标：

- 成功建立票池的会话比例；
- 开始计算后记录至少一轮抽取的比例；
- 单次会话确认轮数中位数；
- 结果参数调整次数；
- 7 日内再次使用率；
- 用户是否根据结果选择继续、包套、直接购买或停止。

护栏指标：

- 计算错误或票数不守恒率；
- 撤销和重建票池比例；
- 用户误解期望为保证结果的比例；
- 使用后超出自设预算的自报比例。

## 4. V2：好版线索地图

### 4.1 启动门槛

只有满足以下条件才启动 V2：

- V1 已证明用户愿意在真实抽取场景持续使用计算工具；
- 通过访谈确认用户会主动搜索好版，并能理解“线索不是库存”；
- 至少找到一条合法、可持续的数据供给路线；
- 完成平台条款、内容版权、个人信息和删除机制评审。

### 4.2 产品目标

> 把合法取得、分散且容易过期的好版信息，整理成带来源和时间的地图线索，帮助用户决定是否值得进一步查看原帖和现场核对。

地图不得使用“实时库存”“现在还有”等未经权威来源证明的表达。

### 4.3 `BoardLead` 数据模型

```ts
type BoardLead = {
  id: string
  sourcePlatform: string
  sourceUrl: string
  sourcePublishedAt?: string
  collectedAt: string
  city?: string
  venueText?: string
  geo?: { lat: number; lng: number }
  series?: string
  remainingTickets?: number
  notablePrizes?: Array<{ level: string; remaining?: number }>
  sourceStatus: 'available' | 'sold_out' | 'deleted' | 'unknown'
  freshness: 'fresh' | 'aging' | 'stale' | 'archived'
  extractionConfidence?: number
  reviewStatus: 'pending' | 'published' | 'rejected' | 'removed'
}
```

每张线索卡必须显示来源平台、原帖时间、收录时间、新鲜度、地点置信度和原帖链接。

### 4.4 数据来源优先级

```text
官方授权 API / 平台合作
→ 原帖作者授权或用户主动提交本人内容
→ 人工策展的最小元数据与普通回链
→ 若以上均不可行，则不做自动聚合
```

V2 不采用个人 Cookie、模拟登录、验证码绕过、签名破解、IP 轮换或其他规避平台技术措施的方式采集内容。

### 4.5 AI 的作用

AI 仅处理已经合法取得的非结构化内容：

- 判断是否与线下一番赏版面相关；
- 抽取系列、地点、余票、大奖和发布时间；
- 识别“已售罄”“昨天看到”等状态表达；
- 生成严格受来源约束的必要事实摘要；
- 标记字段冲突和待人工审核项。

AI 不负责：

- 绕过平台限制获取内容；
- 猜测帖子未提供的地点或余票；
- 判断商家诚信；
- 把旧帖子描述成当前库存；
- 自动生成消费推荐。

### 4.6 时效规则

第一轮验证可采用保守分层，具体阈值由用户研究校准：

| 发布时间 | 默认状态 | 展示方式 |
| --- | --- | --- |
| 0—2 小时 | fresh | 明确显示“发布于 X 分钟前”，仍要求现场确认 |
| 2—12 小时 | aging | 降低排序，提示很可能已经变化 |
| 12—24 小时 | stale | 默认折叠，不用于“附近好版”主排序 |
| 超过 24 小时 | archived | 只保留历史线索或停止展示 |

原帖删除、标记售罄或权利人要求下线时，应同步停止展示。

### 4.7 V2 验收标准

- 每条公开线索均有合法来源记录和可访问回链；
- 低置信地点不会自动上图；
- 用户能够识别线索时间，而不会把它理解为实时库存；
- 原帖删除和退出请求能够在规定时间内完成下线；
- AI 抽取字段经过人工样本评估，关键事实不允许自动补全；
- 地图确实缩短用户找到相关原帖的时间；
- 若内容授权或持续供给不成立，地图不进入公开运营。

## 5. V3：可信票池社群

### 5.1 V3 产品目标

> 用户在抽取过程中可以无证据地快速记录并获得私人计算反馈；只有主动上传公共情报时，才集中拍摄本轮赏券，经票池绑定、证据审核和冲突处理后生成新的公共版面观察。

核心原则可以概括为：

> 随手记，集中验；私人计算零摩擦，公共更新必须有证据。

### 5.2 私人计算层与公共情报层

| 层级 | 用户行为 | 是否需要照片 | 是否影响公共版面 |
| --- | --- | --- | --- |
| 私人计算 | 点击记录本轮抽到的奖项 | 否 | 否 |
| 上传草稿 | 汇总本次会话准备贡献的轮次 | 是 | 否 |
| 待审核 | 系统识别并与点击记录比对 | 是 | 否 |
| 审核通过 | 形成带证据的新观察版本 | 是 | 是 |
| 驳回或作废 | 保留审核记录但不采用 | 是 | 否，继续显示最近可信版本 |

用户抽十次可以只在结束时拍一次，不需要每抽一张就中断操作。

### 5.3 集中上传流程

```text
用户在 V1 式界面完成若干轮私人记录
→ 选择“贡献本轮情报”
→ 系统汇总本次准备提交的奖项与数量
→ 用户在产品内拍摄所有本轮已撕开的赏券
→ 系统识别奖项、数量和疑似敏感代码
→ 自动遮挡活动码、兑换码和完整二维码
→ 将照片识别结果与点击记录对比
→ 用户修正识别，但系统保留修改痕迹
→ 绑定门店、票池、观察时间和前一可信版本
→ 机器审核，必要时进入人工或社区复核
→ 通过后生成新版面观察；失败则维持前一可信版本
```

默认优先使用产品内相机拍摄，并加入当次上传挑战信息，以降低重复使用旧照片的风险。允许从相册上传时应降低证据等级。

### 5.4 照片能够证明什么

撕开赏券的照片可以作为“本轮出现了这些奖项”的证据，但不能单独证明：

- 来自哪家门店；
- 来自哪一套票池；
- 拍摄和抽取的准确时间；
- 拍照后是否还有其他玩家继续抽取；
- 图片是否以前已经用于其他提交；
- 当前整套票池还剩什么。

因此，公共版面更新必须同时绑定：

- 具体门店；
- 可验证的票池身份；
- 上一个经过验证的版面状态；
- 本次观察和服务端接收时间；
- 本轮赏券证据；
- 必要时的现场版面照片、商家确认或官方数据。

若找不到同一票池的可信起点，本次提交最多发布为“抽取结果观察”，不得推导完整剩余版面。

### 5.5 状态演算与版本链

只有满足同一票池、基线未过期且抽取证据通过审核时，才能计算：

```text
上一个可信版面 S(n)
－ 本轮经过验证的抽取结果 Δ
＝ 新的可信版面 S(n+1)
```

公共状态必须使用事件和版本链保存：

```text
可信版面 V1
  ↓ 已验证抽取 A
可信版面 V2
  ↓ 已验证抽取 B
可信版面 V3
  ↓ 虚假或无法绑定的提交 C
提交 C 作废，公共页面继续显示 V3
```

不得直接覆盖或删除旧状态。作废中间版本时，系统必须重新计算其后的依赖版本；无法安全重放时，把后续状态标为冲突并等待新证据。

### 5.6 提交与审核状态

```ts
type ContributionStatus =
  | 'private'
  | 'draft'
  | 'pending_machine_review'
  | 'pending_human_review'
  | 'verified'
  | 'conflict'
  | 'rejected'
  | 'invalidated'
```

| 状态 | 公共行为 |
| --- | --- |
| private / draft | 仅本人可见 |
| pending | 不改变公共版面，可显示为待审核贡献数 |
| verified | 生成新的公共观察版本 |
| conflict | 暂停演算，等待额外证据或更新基线 |
| rejected | 不采用，后台保留原因和反滥用特征 |
| invalidated | 撤销其公共影响并重算依赖版本 |

### 5.7 审核分层

第一层，机器检查：

- OCR 或视觉识别奖项等级和数量；
- 与用户点击记录比较；
- 检查票数守恒和前一版本是否仍有效；
- 检测图片重复、裁剪、明显编辑和跨提交复用；
- 识别并遮挡二维码、活动码和个人信息；
- 检查地点、时间、票池身份是否齐全。

第二层，用户确认：

- 展示模型识别结果；
- 允许用户纠错；
- 保存原识别、修改后字段和差异；
- 修改幅度过大时自动进入人工审核。

第三层，人工或社区复核：

- A 赏、Last 赏等会显著改变版面价值的更新；
- 与同时段其他观察冲突的更新；
- 高价值、异常频率或低质量账号提交；
- 相册旧图、疑似重复证据或票池绑定不清的提交。

机器审核只能判断“证据是否支持提交”，不能宣称绝对真实。公开标签使用“照片支持”“多人确认”“商家确认”或“官方来源”，不用“保证真实”。

### 5.8 票池身份

V3 上线前必须验证：

1. 官方版面编号是否真正一板唯一，还是只标识系列或批次；
2. 票券二维码是否包含活动权益、个人凭证或访问令牌；
3. 门店是否复用编号、拆板、并板或移动票池；
4. 同一套票池是否能用门店、系列、编号和时间窗口稳定绑定；
5. 是否能够获得官方或商家侧的身份确认。

在确认前，不得把任何编号宣称为“官方票池唯一 ID”。推荐的身份等级：

| 身份等级 | 依据 | 可支持的能力 |
| --- | --- | --- |
| 未绑定 | 只有赏券照片 | 个人历史或匿名抽取结果 |
| 弱绑定 | 门店、系列、时间和现场版面照片 | 独立观察，不自动演算公共余量 |
| 强绑定 | 经验证票池编号或连续证据链 | 可从可信基线演算新版面 |
| 权威绑定 | 商家或官方接口 | 可提供更高等级状态，但仍显示更新时间 |

### 5.9 并发与冲突

多人可能基于同一个公共版本同时抽取。系统需要：

- 提交时携带 `baseVersionId`；
- 记录用户观察时间和服务端接收时间；
- 基线已变化时不盲目扣减；
- 检查两次提交的奖项是否可能来自同一连续时间段；
- 无法确定先后顺序时标记冲突，而不是自动选择其中一个；
- 允许新的现场版面照片或权威数据重新建立基线。

### 5.10 反滥用和隐私

- 保存图片感知哈希，检测同一证据重复提交；
- 对异常频率、批量账号和跨城市瞬时提交进行风险标记；
- 高影响提交提高审核门槛；
- 公开图片默认遮挡完整票号、二维码、活动码和个人信息；
- 原始证据与公开证据分开保存并设置保留期限；
- 驳回记录不公开羞辱用户，但保留必要的反滥用信息；
- 提供申诉、纠错、删除和账号退出机制。

type PoolObservation = {

### 5.12 V3 验收标准

- 用户连续抽取十次时，不需要逐张拍照即可完成私人计算；
- 用户能够在抽取结束后一次拍摄并提交本轮全部赏券；
- 未拍照、审核失败或无法绑定票池的提交不会改变公共版面；
- 驳回或作废后，公共页面恢复到最近可信且逻辑一致的版本；
- 重复图片和明显跨票池复用能够被识别或进入人工审核；
- 完整活动码和二维码不会出现在公共页面；
- 并发提交不会造成余量负数或静默覆盖；
- 页面始终显示观察时间、证据等级和“非实时库存”提示。

## 6. 知识产权与数据合规边界

以下判断用于产品规划，不替代目标上线地区律师对最终页面、商标、数据接口和用户协议的审查。

### 6.1 一番赏版面设计

**结论：抽赏规则和事实字段可以重新设计后使用；复刻具体视觉表达和品牌识别存在中高风险。**

[《中华人民共和国著作权法》](https://www.gov.cn/guoqing/2021-10/29/content_5647633.htm)保护具有独创性的美术、摄影、产品设计图、图形作品和软件等具体表达，同时不保护通用数表、通用表格和公式。

| 使用内容 | 暂定风险 | 产品规则 |
| --- | --- | --- |
| A/B/C 等等级、票数、余量、概率和公式 | 低 | 作为事实和规则使用，视觉重新设计 |
| 一张进度版展示各奖项余量的功能思想 | 低至中 | 借鉴信息目标，不照搬官方编排 |
| 官方角色图、奖品照片、海报、字体和背景 | 高 | 未获授权不得内置、复制或描摹 |
| 官方 Logo 和高度近似品牌标识 | 高 | 不用于产品名称、图标或造成官方合作印象的位置 |
| 整体配色、边框、布局和装饰组合 | 中至高 | 使用独立 ICHI 视觉系统 |

[BANDAI SPIRITS 知识产权说明](https://www.bandaispirits.co.jp/site/about_tm/)与[网站使用条件](https://www.bandaispirits.co.jp/site/notice/)均对其图片、文字、角色素材等内容的复制和再利用作出限制。

正式上线前应完成产品名称、图标和核心页面的商标及视觉相似性审查。若使用官方 Logo、角色素材、奖品照片或高度还原的版面，应先获得明确书面授权。

### 6.2 票券编号与二维码

**结论：纯编号的著作权风险通常低，但兑换价值、数据授权、安全和错误绑定风险可能很高。**

官方历史活动页说明，半券上的 `バンプレID` 曾用于 Double Chance 活动。[官方半券 ID 说明](https://sf.1kuji.com/pad3/sp/index.html) 因此，部分号码可能是一次性或具有权益价值的活动码，并非票池身份码。

产品必须区分：

| 类型 | 处理方式 |
| --- | --- |
| 系列号、公开商品编号 | 确认用途后可保存为事实字段 |
| 票池或批次管理号 | 确认可区分具体票池且允许处理后使用，优先保存哈希或必要片段 |
| 活动码、兑换码、个人凭证、访问令牌 | 不公开、不用于票池身份；自动遮挡或仅保存在本地 |

不得通过编号或二维码绕过官方客户端、登录、接口限制或活动规则。

### 6.3 小红书及外部平台数据

**结论：未经授权全站抓取、长期存储、加工并重新展示的综合风险高；公开可见和提供回链不能自动消除风险。**

风险包括：

1. 帖子照片、视频和文字的著作权；
2. 平台合同、接口和数据权益；
3. 作者昵称、头像、位置和轨迹等个人信息；
4. 绕过技术措施带来的不正当竞争乃至进一步法律风险。

[2025 年修订的《反不正当竞争法》](http://www.npc.gov.cn/npc/c2/c30834/202506/t20250627_446247.html)禁止以欺诈、胁迫、避开或破坏技术管理措施等不正当方式获取、使用其他经营者合法持有的数据。[最高人民检察院公开案例](https://www.spp.gov.cn/spp/llyj/202506/t20250603_697192.shtml)也显示，破解加密接口、伪造请求获取非公开平台数据可能产生严重法律后果。

目前检索到的[小红书小程序开放平台](https://miniapp.xiaohongshu.com/home)和[开放平台说明](https://school.xiaohongshu.com/en/open/quick-start/introduction.html)主要提供小程序和商业合作能力，尚未发现面向普通第三方的全站笔记搜索接口。正式接入前需要平台书面确认或律师审查具体数据流。

## 7. 三阶段路线图与决策门

### 7.1 V1 开发顺序

1. 明确计算定义和用户价值输入边界；
2. 完成独立 TypeScript 计算内核与测试向量；
3. 完成票池状态机、本轮草稿和撤销机制；
4. 设计 ICHI 独立视觉的抽赏交互版面；
5. 完成 H5 核心流程，再评估微信小程序适配；
6. 用真实抽取任务进行可用性和理解度测试；
7. 根据使用数据决定模板、识别和账户能力的优先级。

### 7.2 V2 前置验证

1. 收集 30—50 条“好版、剩余、残套、建议包吗”公开案例，只用于研究；
2. 访谈玩家如何搜索、判断过期并决定是否到店；
3. 向平台确认 API、展示、缓存、删除和回链范围；
4. 用授权样本或人工策展验证地图是否优于原平台搜索；
5. 无法建立合法供给时停止自动地图路线。

### 7.3 V3 前置验证

1. 收集 20—30 组真实版面、票券和二维码样本，研究字段用途；
2. 验证集中拍照能否准确识别奖项和数量；
3. 验证用户是否愿意在抽完后完成一次上传；
4. 证明至少一种票池身份可以稳定绑定门店和版本；
5. 建立图片脱敏、重复检测、审核、申诉和版本回退机制；
6. 先做小范围受控贡献，再决定是否开放社群。

### 7.4 关键决策门

| 决策 | 继续条件 | 停止或转向条件 |
| --- | --- | --- |
| V1 是否继续深化 | 用户真实抽取时持续记录，并根据反馈调整行动 | 只在新奇体验时打开，现场记录摩擦高于价值 |
| 是否启动 V2 | 存在合法稳定数据源，线索明显缩短发现时间 | 授权不可得、内容过期过快或用户普遍误解为库存 |
| 是否使用 AI 抽取 | 明显降低整理成本且关键字段准确可审核 | 幻觉率高、成本过高或授权不允许处理 |
| 是否启动 V3 | 集中拍照有贡献意愿，票池身份和审核成本可控 | 无法绑定票池、证据无法验证或绝大多数用户只查看不贡献 |
| 是否接入商家或官方 | 能提供更权威身份和更新时间，且不破坏用户侧中立 | 双边运营成本超过产品价值或形成误导性背书 |

## 8. 仍需回答的问题

### V1

1. 用户更愿意一抽一记，还是几抽后批量记录？
2. 最常用的是目标奖概率、预算控制、包套比较还是主观价值期望？
3. 模板录入和现场修改的最短路径是什么？
4. 用户是否愿意填写奖品价值，还是只需要概率和成本？

### V2

1. 平台是否提供适合本场景的授权内容接口或合作方式？
2. 用户在出发前还是到商场后寻找好版？
3. 多久以前的线索仍有行动价值？
4. 地图会不会加剧抢版、黄牛或非理性消费？

### V3

1. 什么字段能够稳定识别同一套票池？
2. 集中拍摄大量赏券时，识别准确率和拍摄负担如何？
3. 同一门店多人并发抽取时，怎样重建可靠顺序？
4. 高影响提交需要人工审核到什么程度？
5. 如果只有赏券证据而没有可信基线，是否值得展示为独立抽取观察？

## 9. 最终定位

### V1

> 一张会随着每次抽取即时重算的一番赏决策版面。

### V2

> 一张把合法来源、发布时间和过期状态放在首位的好版线索地图。

### V3

> 一个把私人点击记录通过集中拍照、票池绑定和审核版本链转化为公共观察的可信票池社群。

三阶段共同遵守的底线是：数学结果必须可复现，外部内容必须合法取得，私人记录不能直接变成公共事实，用户观察不能被包装为官方实时库存，AI 不得填补缺失事实。
