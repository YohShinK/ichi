## 1. 产品定义

ICHI 是一套面向一番赏玩家的个人决策与可信信息产品。产品从私人即时计算开始，只有前一阶段价值和风险门通过后，才增加公共线索与社群能力。

### 1.1 产品承诺

- 让用户在票池变化时持续看到可复现的数学结果；
- 把预算、目标和停止选项放在与继续抽取同等位置；
- 清楚区分私人记录、外部线索、用户观察和权威库存；
- 让任何公共状态都能追溯来源、时间、证据和版本。

### 1.2 非目标

- 不售票、代抽、交易、支付或托管资金；
- 不做商家后台、库存接口、信用分、黑名单或举报平台；
- 不判断商家是否作弊、藏票、诈骗或违法；
- 不把概率或期望表达为稳赚、回本、保底；
- 不绕过第三方平台限制获取内容；
- 不暗示 ICHI 是品牌方或一番赏官方产品。

## 2. 用户与使用场景

### 2.1 主要用户

| 用户       | 目标                    | 最大摩擦                               |
| ---------- | ----------------------- | -------------------------------------- |
| 目标型玩家 | 获取指定 A/B/SP/Last 奖 | 只看见大奖仍在，不知道继续成本         |
| 预算型玩家 | 控制单次投入和停止点    | 抽取过程中容易失去累计成本感           |
| Last 猎手  | 比较包套与直接购买      | 只凭余票数量判断，忽略其他奖品与预算   |
| 记录型玩家 | 保存多轮变化和复盘      | 票池、目标与抽取结果散落在纸笔或聊天里 |
| 线索型玩家 | 找到值得现场核对的版面  | 外部内容分散、过期，来源和时间不清楚   |
| 贡献型玩家 | 分享可验证的抽取观察    | 手工自报缺少可信度，逐张上传又太麻烦   |

### 2.2 首发场景

V1 首发场景是用户已看到一个具体票池，正在付款或继续抽取前做决定。现场可能是线下门店、快闪店或线上售卖页面，但交互不依赖商家系统。

### 2.3 Jobs to Be Done

1. 当我准备参与一个票池时，我想快速建立当前状态，确认输入能否用于计算。
2. 当我有目标奖和预算时，我想比较不同抽数、包套、直接购买和停止。
3. 当我抽完一轮时，我想用少量点击更新票池，而不是重新录入全部数据。
4. 当我误点或记错时，我想撤销最近 50 抽中的任一连续最近轮次，并恢复所有相关结果。
5. 当我远程寻找版面时，我想先看到来源和发布时间，而不是被“实时库存”误导。
6. 当我贡献公共信息时，我想一次集中上传证据，并清楚知道哪些信息会公开。

## 3. 版本策略

### 3.1 V1：即时计算

核心假设：持续、低摩擦、确定性的票池交互，比一次性概率答案更有价值。

V1-26 最初以低保真页面流启动，但经 V1-29 完整设计、实现与用户验收后，Next.js 手机优先网页现为 V1 小程序全部页面、视觉、内容、组件、动效和交互的完整批准基线；微信小程序是最终产品运行端，后续必须把整套网页一比一照搬为 WXML/WXSS、TypeScript 和微信平台能力。这里的“照搬”只允许 HTML/CSS/JavaScript 到小程序语法以及浏览器 API 到微信 API 的必要平台映射，不允许重新设计、重排、简化、替换字体／字号／图标／间距／动效，也不允许在旧小程序 UI 上继续二次创作。用户通过拍摄或从相册选择一张完整、可读的兑换进度版面建立票池，图像识别只生成可校正的输入草稿。V1 使用随包预置的版面语法与通用组件，不依赖产品版本目录；账号登录、后端保存和云端同步仍在 V2 接入，但完整网页基线已经包含“我的”面板、账号管理、本地记录和我的贡献的 UI 框架与状态占位。“本地记录”是当前用户记录的本机总账，包含未核对／未上传与已核对／已上传记录；“我的贡献”不是第二份独立副本，而是从本地记录中筛选出的已上传子集。已上传贡献预留点赞计数字段，V1 只显示结构与零值占位，不产生或伪造其他用户互动。账号管理只承载账号与设置。未登录时仍可继续本机抽取；未分享记录只视为本地草稿，不代表地图事实。既有微信小程序壳和 Storage 适配器只作为平台工程与验证基座，不是视觉或页面设计基线。

### 3.2 V2：好版线索地图与核对式共享

核心假设：只有来源、时间、新鲜度和用户本人可核对的抽取证据同时清楚时，地图线索才有价值且不易被误读为实时库存。

V2 前端先实现“收手 → 是否共享 → 集中拍摄已抽赏票与地点备注 → 提交核对”的完整流程；用户提交后不再进入核对结果或待发布预览页面。每次完成一张导入版面的确认时生成唯一 `boardId`；同一 `boardId` 的再次提交以最新抽取记录和当前票位覆盖原待核对草稿，不创建第二条贡献。提交确认先保留在一番赏版面上，以中央状态框显示“已提交”和“后台正在核对本次提交”，并提供“继续”（关闭状态框留在版面）与“退出”（返回导入版面）。核对、当前版面状态计算、私有保存和发布完全由后台处理。该阶段不能执行真实上传。后续才在合法数据供给、证据保存、删除权和审核规则通过后接入相机、OCR、云端打包与地图发布。

### 3.3 V3：可信票池社群

核心假设：私人点击保持零摩擦，公共贡献集中举证，配合票池身份、审核和版本链，可以形成可信但非官方的公共观察。

V3 必须经过受控试验，不直接开放公共写入。

## 4. V1 功能设计

### 4.1 信息架构

| 页面／区域       | 主要职责                                                                                                                                                                                                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 开始与拍摄页     | 顶部固定显示紧凑的“导入版面照片”主行动卡，点击后进入版面取景框；下方独立滚动区显示用户主动保存但尚未分享的本机抽赏草稿，点击草稿可恢复对应版面和抽取状态；未核对且未上传的草稿可左滑揭示删除操作，删除后同步从本地记录总账移除；不显示泛化的本地保存说明卡，也不增加照片用途确认页                                                     |
| 识别结果页       | 以一番赏式可编辑版面展示识别出的奖级、票位、Last、总票数和已贴票数；用户直接在对应奖级下修改总票数与已贴票数，不再进入独立核对页；确认后在当前版面中央显示“正在生成版面”的进度框，完成后自动进入一番赏版面工作台                                                 |
| 目标奖选择       | 用识别出的 A—F 奖级提供多选控件，作为完整网页基线中的可访问页面，不插入当前快捷主路径；主流程不要求填写计划抽数、预算或最低概率                                                                                                                                    |
| 一番赏版面工作台 | 用户后续操作的主界面：奖级图标、票位空格、已贴票、三位小数概率、Last 包套成本、抽取记录与撤销；剩余票数／Last 包套成本状态栏固定在顶部安全区下方，局面可能性／撤销／抽取记录固定在视口右侧，“收手”固定悬浮在底部导航上方；滚动奖级票面时这些工作台控件均保持原位 |
| 版面内记录与撤销 | 撕开后在版面上贴回一张票，显示可关闭且自动消失的本次记录浮层；最近 50 抽可连续撤销，撤销与记录列表以右下角快捷按钮打开，不再跳转独立页面                                                                                                                         |
| 方法与隐私页     | 公式、假设、数据保存、删除和非官方声明                                                                                                                                                                                                                           |

V1 手机端使用固定底部导航承载三个一级入口：

1. `识别`：进入版面照片导入与识别流程；
2. `好版地图`：为 V2 预留入口。V1 只能展示范围说明，不显示地图、线索、筛选或任何库存暗示；
3. `我的`：进入头像、用户 ID、账号管理、本地记录、我的贡献、提醒设置、隐私与数据和关于 ICHI；账号管理只包含账号与设置；本地记录展示全部本机记录，并让每条记录同时显示核对状态（未核对／已核对）与上传状态（未上传／已上传）；我的贡献只展示上传状态为“已上传”的记录，并为每条记录预留其他用户点赞数；“提醒设置”在 V1 只展示“好版地图提醒”的 V2 功能说明，明确它只整理已核对版面线索、不构成实时库存或推送承诺；V2 再接入真实账号、后端存储、点赞、授权与通知能力。

“我的”的账号管理、本地记录、我的贡献、提醒设置和隐私与数据均属于二级页：顶部安全区必须提供统一返回按钮回到“我的”主页；在任一二级页再次点击底部“我的”也直接回到“我的”主页。该重复点击行为只用于“我的”页族，不改变识别标签的稳定页面恢复规则，也不为地图标签增加额外返回逻辑。

在 `识别`、`好版地图` 与 `我的`之间切换时，系统保留最近一个稳定的识别流程页面：导入页、识别结果、目标奖选择、一番赏版面及统一失败恢复页均可原样返回；拍摄取景与识别／生成等加载态不作为可恢复目的地，返回 `识别`时回到其上一级稳定页面。当前流程从导入页开始时，拍摄页和识别加载页的上一级均为导入页。该规则只恢复页面位置与本机已缓存的版面状态，不伪造识别、生成或上传的后台进度。

### 4.2 识别并创建票池

用户可以：

- 拍摄一张完整、可读的兑换进度版面，或从相册选择该图片；
- 点击“导入版面照片”后先进入版面取景框；取景框以虚线版面和角标提示完整构图，用户点击拍摄后才进入识别；
- 手机端“拍摄版面”使用相机式全屏布局：上半部分为纵向版面取景区，下半部分为独立控制区，只放置圆形拍摄按钮和圆形返回按钮；当前 V1 仅演示网页取景，不请求真实相机权限；
- 正式接入时仅在用户点击拍摄时请求相机权限；V1-D 网页先交付取景框、构图提示和流程，不调用真实相机、相册或上传；
- 直接识别版面上的奖级、每级券位、券位占用状态、价格和辅助区块，并保留它们的二维位置与阅读顺序；
- 按完整网页基线中已预置的通用组件和实际页面结构，根据识别数据条件显示奖级列表、券位、总抽数、价格和 Last 等组件；小程序组件必须一比一照搬其结构、视觉和行为；
- 将识别结果作为草稿，并按大赏、中赏和小赏的版面规则展示；每级同时显示“总票数－已贴票数”、空／实心票位，以及可直接修改的总票数和已贴票数输入框；不再使用表格或独立“修改”页；
- 识别页按“照片接收、奖级与余票读取、价格与 Last 整理”逐项显示进度，完成一项即打勾；读取完成后自动进入“识别结果”，不要求用户手动点击继续；识别判定无法建立票池时自动进入统一的“无法建立票池”恢复页；
- “正在提取版面”的识别进度卡保留现有深色旋转圆环、视觉中心和进度动效；圆环中的旧扫描图标改为用户提供的“单线眼睛＋放大镜”票根吉祥物透明素材，素材自身不随圆环旋转；
- 用户点击“确认并生成版面”后，“版面已确认”生成状态层保留原文案、进度条、弹跳动效、锁定时序和自动进入工作台路径；其黑色魔法棒旧图标改为用户提供的“圆点眼睛＋铅笔”票根吉祥物透明素材；
- 图像质量不足时重拍或重新选图，不得伪造完整结果；
- 单抽价格可能是手写内容；无法可靠识别时将价格字段标记为待填写，不阻塞其他版面元素的识别；
- 从“我的 → 本地记录”查看当前设备上的全部记录及其“核对／上传”双状态；从“我的 → 我的贡献”查看其中已上传的贡献子集及其点赞计数位置；二者引用同一个 `recordId`，不能因进入贡献列表而复制一份记录。“账号管理”只承载账号与设置；不提供复制票池记录。
- 从识别首页直接查看用户在“暂不分享并退出”时保存的本机抽赏草稿；导入主行动卡固定在页面顶部，草稿列表单独滚动，点击任一草稿恢复同一 `boardId` 的版面、抽取记录、累计花费与撤销状态。未核对且未上传的草稿可在识别首页或“我的 → 本地记录”中左滑，揭示黑底白色垃圾桶删除操作；两处操作删除同一 `LocalDrawDraft`，任一处删除后另一处立即不再显示。已核对或已上传记录不生成删除入口。该草稿没有提交核对，不属于贡献或地图事实。

V1 不提供按产品划分的固定模板或产品样本目录。市场上不存在已被证明能覆盖中日全部产品的固定三种版面结构，因此系统采用“版面语法”：一个可复用的奖级组件承载 A—Z，固定辅助组件承载价格、总抽数、Last 等信息，识别数据决定出现哪些组件以及如何排列。

确认前必须具备：剩余总票数、至少一个奖项、每个奖项剩余数量、单抽价格。

可选字段：系列别名、Last 状态、目标奖、预算、计划抽数和直接购买参考价。

通过识别结果的“确认”后，系统先在当前识别版面中央显示“正在生成版面”的短暂进度框；校正后的奖级、票位和 Last 已写入当前浏览器会话缓存，生成完成后自动进入“一番赏版面工作台”。“选择目标奖”保留为完整网页基线中的可访问页面，但不阻塞这条快捷主路径；预算、计划抽数和最低概率不作为进入主工作台的必经输入。进入工作台后，A—F 奖级按图标、概率和票位空格排布；已贴票以实心票位表示。Last 固定在左上角，只显示当前包套成本，不显示概率。

版面识别固定提取普通奖级、每级总／空／已贴／未知票位、票位排布、价格、Last、辅助区块、完整度、置信度和问题原因；票池总数与余票由可靠券位在本地求和，模型不得猜测。大赏／中赏／小赏不交给模型判断：`packages/board-layout` 的 `derivePrizeClassification` 只接受已核对的奖级标签和正整数总票位，A—F 中总票数 `≤ 5` 的奖级用大赏呈现，`6—9` 的奖级用中赏呈现，`≥ 10` 的奖级用小赏呈现；G—Z／OTHER 也用小赏呈现。票数未知、矛盾或不合法时返回未确认，不能建立正式票池。V1-29 的唯一页面壳基线为用户提供的 `网页 ui.html`：它的既有页面信息、文字、布局、色彩和动效不得修改；ICHI 只把原有路由、算法与交互绑定到同名或语义对应的控件。源页面未覆盖的已批准能力才可在同一视觉系统中补齐。三者均保持相同的概率、抽取、累计花费和撤销逻辑。为消除跨页面无意的版式漂移，V1-29 另以 [`docs/design/v1-29-ui-design-tokens.md`](../docs/design/v1-29-ui-design-tokens.md) 固定顶部安全区、内容边距、卡片层级、文字宽度、操作宽度和页面族变体；它只统一设计参数，保留导入视觉资产、地图标识、异常状态等有明确语义的尺寸差异。

#### 4.2.1 版面语法与组件装配

V1 不为每个产品建档，也不把版面归并为三种固定模板。完整网页基线预置以下稳定语法，最终随小程序包发布并由 WXML/WXSS 一比一照搬实现：

| 类别   | 要求                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------- |
| 奖级   | `PrizeTier` 是唯一通用奖级组件，预置 A—Z 标识；识别到的奖级才进入草稿。无法归一化的短标签进入 `OTHER`，显示原文并要求确认 |
| 券位   | 每个奖级包含零个或多个券位；记录总券位、已覆盖券位、空置券位和无法判断券位，保留一维／多行排列                            |
| 计数   | 在完整版面且确认一个券位代表一抽时，普通奖级总券位之和推导初始总抽数；普通奖级剩余券位之和推导余票                        |
| 价格   | 记录识别值、币种、原始文本和置信度；识别失败或疑似手写时必须由用户补填或确认                                              |
| 特殊项 | Last、Double Chance 与其他不代表普通抽券的区块单独建模，默认不计入总抽数                                                  |
| 辅助项 | 标题、系列标识、奖品图、说明、店铺／产品 ID、品牌标识、二维码、版权和未知区块均可出现或省略                               |
| 排布   | 每个识别区块记录归一化矩形、父区块、层级和阅读顺序；手机端可响应式重排，但不丢失原始空间关系                              |
| 置信   | 识别字段带置信度和 `recognized`／`derived`／`manual` 来源；低置信字段必须显式待确认                                       |

总抽数只能在以下条件同时成立时自动确认：版面四边完整、所有普通奖级与券位区均被识别、一个券位代表一抽的规则成立、各级券位计数内部一致。任一条件失败时只显示“推算值”或“待填写”，不得把不完整求和当作事实。Last、Double Chance、说明、二维码、装饰和版权区永不进入普通总抽数。

识别“券位占用状态”只用于从当前完整进度版面初始化剩余数量；V1 不读取贴上去的已使用奖券内容，也不在后续每抽后拍照识别奖券。建池后仍严格采用一抽一记。

网页组件脚本、样式和交互逻辑随 Next.js 完整基线发布；识别服务只返回符合已知 schema 的数据，不下发或执行远程组件代码；未知区块只能以不可执行的占位信息降级显示。V1-29 经用户明确授权，为逐项保真直接托管 `网页 ui.html` 及其已有的字体、图标与 Tailwind 运行时输入；该例外只适用于该用户提供的静态页面壳，不允许识别服务或任何未知数据下发可执行 UI。网页验收通过后，所有页面、组件、内容、视觉和行为必须一比一照搬为随小程序包发布的 WXML/WXSS、TypeScript 与微信平台适配；平台差异不得成为重新设计或简化 UI 的理由。

V1-D 的手机视觉基线由 `apps/web/app/tokens.css` 固定颜色、间距、圆角、导航安全区和模态层级；`apps/web/app/ui/` 提供 `PrizeTile`、`TicketSlots`、`StatusNotice`、`Modal` 和 `BottomTabbar` 等本地 React 组件。tokens 只表达视觉约束，组件只接受已校正的页面数据，不把交互、文字或业务状态图片化。390px 手机视口优先，桌面端只做响应式重排；页面索引在手机端隐藏，三项底部导航始终可达；“识别结果”和“一番赏版面”在底部导航上方至少完整显示 5 个奖级，优先压缩重复页面信息，不缩小奖级票位到影响查看或编辑的程度。

此前 `V1-01A` 建立的产品目录覆盖政策保留为历史决策，但已被本节的新认知取代，不再是 V1 建池或发布门禁。

### 4.3 输入校验

系统输出三种状态：

| 状态     | 条件                                   | 行为                           |
| -------- | -------------------------------------- | ------------------------------ |
| 可计算   | 余票、奖项数量和必填字段完整且守恒     | 允许显示正式计算结果           |
| 信息不足 | 缺少票数、奖项或单价                   | 标出缺失字段，不给正式结果     |
| 存在矛盾 | 奖项余量之和不等于余票，或数量出现负数 | 展示矛盾项，阻止确认和继续计算 |

多次未中奖不是异常信号。V1 不输出藏票、作弊或商家风险结论。

### 4.4 目标与预算

用户可以选择多个目标奖。预算、最大计划抽数、最低可接受目标达成概率、停止条件和直接购买参考价仍是计算内核可接受的可选输入，但不作为当前主工作台入口的填写项：

- 本次会话预算；
- 最大计划抽数；
- 可选的最低可接受目标达成概率；
- 可选停止条件；
- 可选的直接购买参考价。

V1 不采集奖项个人价值，不显示“回本率”、价值期望或净值结论。

### 4.5 确定性计算

设剩余总票数为 R、目标票数量为 T、计划抽数为 k、单抽价格为 c。

| 结果                       | 规则                            |
| -------------------------- | ------------------------------- |
| 下一抽命中率               | T ÷ R                           |
| k 次至少命中一次           | 1 − C(R−T, k) ÷ C(R, k)         |
| k 次命中 x 次              | C(T, x) × C(R−T, k−x) ÷ C(R, k) |
| 目标奖期望数量             | k × T ÷ R                       |
| 首次命中任一目标的期望抽数 | (R+1) ÷ (T+1)                   |
| 包套成本                   | R × c                           |
| 剩余预算最大抽数           | floor(剩余预算 ÷ c)，且不超过 R |

规则要求：

- k 小于 0、R 小于 0、T 大于 R 或 k 大于 R 时不给正式结果；
- T 为 0 时命中概率为 0；
- k 为 0 时命中概率为 0；
- k 等于 R 且 T 大于 0 时至少命中一次概率为 1；
- 复杂多目标计算使用精确组合数或动态规划，不简单相乘；
- 同一输入与公式版本必须得到相同结果；
- 所有结果可查看输入、公式版本和限制。

#### 4.5.1 计算术语与金额表示

V1 固定使用“概率、命中分布、期望抽数、成本与预算、包套、停止”六个术语。概率描述可能性，命中分布描述恰好命中各数量的完整分布，期望抽数只表示长期平均而不是保证、保底或推荐抽数。包套只指取得当前全部余票的确定性方案；停止与抽取、包套、直接购买同级展示并保留会话历史。

所有金额以对应币种的最小货币单位整数保存和计算，不使用二进制浮点数存储金额。预算内最大抽数向下取整且不超过余票。完整输入、输出、限制和文案例子由 `data/calculation-baseline/glossary.json` 固定。

#### 4.5.2 约束内最少抽数方案

V1 可以在精确概率陈述之外提供“约束内方案”，但不得把它表达为中奖保证、消费建议或系统替用户设定的最优抽数。用户必须先自行给出本次预算、最大抽数和最低可接受目标达成概率；系统不提供默认概率门槛，也不以“预算内概率最大化”为目标。

约束内方案定义为：在不超过余票、剩余预算和用户最大抽数的前提下，寻找达到用户所设概率门槛的最少抽数。多目标和指定数量使用精确联合概率。只有输入完整、守恒且全部约束由用户明确给出时才计算；缺少约束时只展示事实，不生成方案。

每个可行方案必须同时展示：

- 最少抽数、对应成本和使用的用户约束；
- 精确目标达成概率，以及同等显著或更显著的未达成概率；
- 证明类型“满足用户约束的最少抽数”、公式版本和输入快照；
- “结果不保证”“系统不会自动放宽预算、最大抽数或概率门槛”“停止始终可选”三项固定披露。

若没有任何抽数满足全部约束，结果必须是“当前没有符合条件的抽选方案”，并显示约束内可达到的最高概率与未达成概率；不得建议增加预算、提高最大抽数、降低概率门槛或追逐既有投入。概率门槛为 0 时最少抽数是 0，不得为了产生消费方案而跳过停止。

Last 只允许表达确定性保证：版面规则经用户确认且取得当前全部余票时，可显示包套成本 `R × c` 和“保证取得 Last”；规则未确认、余票为 0 或抽数小于 R 时不计算或暗示 Last 概率。

### 4.6 抽取记录状态机

一轮只记录一张已抽票的一个奖项，不支持批量轮次。用户在一番赏版面上对对应奖级执行撕开动作；动作完成后，该奖级新增一个已贴票位，所有奖级的概率重新计算，并在版面上方显示本次抽到的奖级、当前剩余票数和累计花费。用户已经在版面中知道单抽价格，因此抽取浮层和抽取记录不重复展示单抽金额，只显示截至本轮的累计花费。每次抽取的事实（抽到什么赏、剩余票数、累计花费）与本次命中的情境提醒必须放在同一个可关闭、自动消失的轻提醒框中，而不是拆成多个弹层。轻提醒保持原页面壳的水平居中规则，其垂直中心与顶部固定状态栏的垂直中心对齐。轻提醒左侧吉祥物按本轮奖级的本地分类切换表情：大赏使用四芒星眼睛，中赏保留现有圆点眼睛，小赏使用眯眼表情；表情只反馈已发生的奖级分类，不改变提示优先级或文案。奖级概率只显示百分比，不显示“下一抽”等前缀，并固定精确到小数点后三位，以便用户在每次抽取后看见票池变化；关闭或自动消失时，该框内全部信息一起消失。V1 不拍摄或识别抽开的奖券。

抽赏记录与版面快照还会作为《情境提醒》的唯一业务输入：每次确认一抽后，系统按目标命中、意外大赏、连续小赏、连续同级中赏、连续多抽、目标达成、撤销和数据不足等情境生成主界面浮层候选。奖项只使用大赏、中赏和小赏三类互斥数量标签：A—F 的 `totalSlots ≤ 5` 为大赏、`6—9` 为中赏、`≥ 10` 为小赏，G—Z／OTHER 为小赏；不影响概率、抽取或目标逻辑。累计花费只作事实展示，不设置或要求用户配置成本提醒节点。每一抽独立生成一个最高优先级提示，不使用跨抽取冷却抑制。规则、优先级和禁止文案见 [`memory-bank/情境提醒.md`](./情境提醒.md)；V1-D 已验收网页以纯规则模块在工作台实现该行为，正式小程序会话接入由 V1-E 一比一照搬并完成平台适配。

一轮记录包含四个状态：

| 状态   | 含义                         | 可执行动作                                                       |
| ------ | ---------------------------- | ---------------------------------------------------------------- |
| 空闲   | 没有本轮草稿                 | 点击奖项开始记录                                                 |
| 草稿   | 本轮唯一奖项已选但未写入票池 | 更换奖项、清空、确认                                             |
| 已确认 | 本轮已扣减票池并计入成本     | 在同一版面继续、撤销最近 50 抽范围内的连续最近一轮、打开记录面板 |
| 已撤销 | 最近一轮影响已反向恢复       | 在同一版面显示“已撤销”浮层；连续撤销不得超过最近 50 抽边界       |

确认本轮时必须原子地更新：奖项余量、剩余总票数、本轮成本、累计花费、历史记录和所有计算结果。

如果本轮数量超过对应奖项余量，禁止确认并指出具体奖项。

### 4.7 撤销

- 支持连续撤销最近 50 抽；不支持跳过中间轮次撤销，避免状态重放复杂度；
- 撤销恢复奖项余量、余票、累计成本和计算结果；
- 被撤销轮次保留在历史中并标记状态；
- 已达到 50 抽边界或没有可撤回轮次时，明确说明，不重复增加余量；
- 用户修改票池结构后，如果无法安全撤销，应明确提示并要求确认新基线。
- 撤销和记录列表由版面右下角的圆形快捷按钮打开，不跳转独立状态页面。

### 4.8 四种方案比较与局面可能性

四种结果保留为可解释的计算数据，不使用单一神秘推荐分；当前一番赏版面工作台不提供单独的“抽取方式比较”页面。工作台在撤销按钮上方提供“局面可能性”快捷按钮，在不离开版面的中央模态框中完整展示当前版面特有的事件概率：已选目标至少出现一次、至少一张大赏、至少一张非小赏／全非小赏，以及两张或以上小赏。它使用固定最多 3 抽的观察窗口（余票不足时取剩余数），只读当前已确认余票、用户目标、奖级本地分类和单抽价格；目标缺失不会阻止展示其余版面事件，票池不可计算时明确不生成条目。局面可能性与抽取记录使用同一张四角完整圆角的工作台模态卡片，卡片自身中心对齐 V1-29 设计规则中的视觉中心；内容超过可用高度时只滚动卡片内部，不能把标题或关闭按钮推出视口。模态框不设置默认概率门槛、不排序或标记“推荐”，不提供“立即抽取”按钮，并固定显示“结果不保证；停止仍可选”。完整事件目录、公式、输入校验、版本与固定案例由 `docs/decisions/v1-board-outlook-algorithm.md` 约束。

| 方案     | 必须显示                                                                                     |
| -------- | -------------------------------------------------------------------------------------------- |
| 抽取     | 用户计划抽数、成本、目标概率、未达成概率、预算占用和限制；约束完整时可附“满足条件的最少抽数” |
| 包套     | 清池成本、确定获得的剩余奖项、Last 条件和预算状态                                            |
| 直接购买 | 用户填写的参考价、与抽取和包套的现金差；无参考价则显示未知                                   |
| 停止     | 已花费、剩余预算、停止条件和可保留的会话记录                                                 |

超出预算时，包套和增加抽数只能显示“不建议”或“不可执行”。约束内方案不得覆盖四种并列选择、不得改变停止的可见性，也不得产生单一排名或推荐分。当 k 小于 R 时，不虚构 Last One 获得概率。

### 4.9 本地存储与删除

V1 保存以下本地实体：

| 实体                | 关键字段                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| PrizePool           | ID、系列别名、余票、奖项集合、单价、Last 状态、更新时间                                                    |
| Prize               | ID、等级、名称、剩余数量                                                                                   |
| DrawSession         | ID、初始票池、当前票池、目标、预算、累计花费、轮次                                                         |
| DrawRound           | ID、时间、奖项与数量、成本、状态                                                                           |
| LocalDrawDraft      | `boardId`、保存时间、当前票位、抽取记录、累计花费和最近撤销状态；同一 `boardId` 再次保存时覆盖旧草稿       |
| ContributionDraft   | `boardId`、最近提交时间、当前票位快照、抽取记录快照、地点备注与核对状态；同一 `boardId` 只保留最新一次提交 |
| FormulaSnapshot     | 公式版本、输入摘要、输出摘要                                                                               |
| BoardDraft          | 图像完整性、奖级、券位观察、价格、辅助区块、二维排布和字段置信度                                           |
| BoardLayoutSnapshot | 使用的版面语法版本、组件注册表版本、用户确认值和推导门禁结果                                               |

要求：

- 网页中间层使用浏览器本地存储适配层验证会话行为；最终产品使用微信小程序 Storage 适配层，二者通过同一领域状态契约对齐；
- V1 网页在正式本地存储接入前，使用当前浏览器会话缓存保留一番赏版面、抽取记录和最近 50 抽撤销栈；离开后重新回到版面可恢复这些临时状态，但不代表云端保存或账号记录；
- V1-D 已验收网页实现在识别确认时生成仅本机可用的 `boardId`，并在每次提交核对时保存当前版面和抽取记录快照；同一版面再次提交覆盖该快照，重新导入并确认的版面才获得新 ID；
- 用户在共享选择中点击“暂不分享并退出”时，系统以同一 `boardId` 在浏览器本地存储中创建或覆盖 `LocalDrawDraft`，然后返回识别首页；“继续抽赏”只关闭共享选择并留在当前一番赏版面。识别首页草稿列表负责恢复这些未分享草稿，不把它们升级为 `ContributionDraft`；只有 `unverified + not-uploaded` 的本机草稿允许左滑删除，删除按 `boardId` 同步更新识别首页和本地记录总账，已核对或已上传记录不可通过该入口删除；
- 用户可以删除单个会话或全部本地数据；
- V1 不进行自动云同步；网页保留账号、私有记录和贡献状态的 UI 框架，真实同步在 V2 接入；
- 本地结构升级必须有迁移版本和失败回退。
- 版面原图不进入会话同步；识别服务的上传、短期处理和删除规则必须对用户可见。

### 4.10 V1 异常与边界

| 情况                               | 预期行为                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------ |
| 目标奖数量为 0                     | 告知目标已无余量，并突出停止或直接购买                                                           |
| 抽数超过余票                       | 将抽数限制为余票或要求修正                                                                       |
| 预算不足一抽                       | 显示不可继续，不隐藏已有历史                                                                     |
| 奖项数量不守恒                     | 阻止正式计算和确认本轮                                                                           |
| 本地保存失败                       | 保留当前内存状态并提示导出或重试                                                                 |
| 页面意外关闭                       | 恢复最近一次成功保存的会话，不虚构未保存草稿                                                     |
| 浏览器存储接近上限                 | 提示清理历史，不静默删除                                                                         |
| 拒绝相机或相册权限                 | 说明用途并提供重新授权或退出路径                                                                 |
| 版面图像不完整、识别失败或数据矛盾 | 统一进入“无法建立票池”页，说明可能原因并提供重新导入、返回核对和返回首页；不补全或猜测未识别事实 |
| 无网络或识别服务失败               | 不能创建新票池；进入统一失败页，仍可查看已保存会话并重试                                         |
| 识别结果低置信或不守恒             | 不能进入正式计算；进入统一失败页后可返回核对                                                     |
| 价格手写、缺失或低置信             | 保留其余识别结果，只要求用户填写或确认价格                                                       |
| 券位区域缺失、遮挡或计数不一致     | 总抽数标为推算或待填写，指出具体奖级，不自动确认                                                 |
| 组合数规模过大                     | 使用稳定算法；无法精确计算时明确失败，不返回近似伪精确值                                         |
| 未设置概率门槛、预算或最大抽数     | 只显示事实与方案比较，不生成约束内抽数方案                                                       |
| 约束内无可行抽数                   | 显示“当前没有符合条件的抽选方案”及约束内最高达成／未达成概率，不劝用户放宽限制                   |
| Last 规则未确认或未包套            | 不显示 Last 概率或保证；只说明保证条件尚未满足                                                   |

### 4.11 V1 文案与视觉约束

- 文案采用克制、清楚且熟悉一番赏场景的语气；“票池”“奖级”“包套”“Last”等词只在准确描述对应事实时使用，不使用拟人化、撒娇式或刺激性表达；
- “导入版面照片”是新建票池的主行动入口；照片导入、识别与用户校正完成后才建立票池，不把未建立的票池称为“票池照片”；
- 用户确认识别结果后在当前版面显示“正在生成版面”的短暂进度状态，并自动进入一番赏版面工作台；不设置“票池已就绪”“抽取方式比较”“本次记录已保存”或“已撤销上一抽”的独立页面；
- 不使用“冲一把”“回本”“再来一次”“欧气”等刺激性 CTA；
- 不使用“推荐抽三张”“最值得”“最佳手气”等主动促抽文案；统一使用“约束内方案”“满足条件的最少抽数”和“仍可能未达成”；
- 成功概率不得脱离失败概率单独突出；确认抽数前必须让用户看到成本、未达成概率和结果不保证提示；
- 不以追损、既有花费或接近目标为理由建议增加投入，用户触发停止条件后不得提示继续抽取；
- 红色只表示错误或预算危险，不表示商家违规；
- 页面优先显示事实、输入与组成项，再显示标签；
- ICHI 使用独立设计系统，不复刻官方海报和角色视觉；
- image2 只用于基于 HTML 布局的视觉方向探索和非交互素材；按钮、输入、文字、状态和业务组件必须回到真实 HTML/React 实现；
- V1 已在 Next.js 手机优先网页完成并验收整套小程序页面设计，同时约束窄屏和桌面浏览器的响应式重排；验收后整套页面一比一照搬为小程序视觉实现；
- 一番赏版面上的奖级概率只显示百分比，统一保留三位小数；每次抽取后按最新余票重新计算并更新显示。
- 颜色不得是唯一状态表达；网页以高对比度、可读文字、足够触控目标、键盘顺序和语义 HTML 为可访问性目标。

## 5. V2 功能设计

### 5.1 数据边界

允许的数据来源按优先级排列：

1. 官方授权 API 或平台合作；
2. 用户主动授权的本人版面、抽取记录和集中拍摄的赏票证据；
3. 人工策展的必要元数据与普通回链；
4. 以上都不成立时，不进行自动聚合。

### 5.2 BoardLead

每条线索至少包含：来源平台或用户授权标记、来源 URL（如有）、发布时间或未知、收录时间、地点文本、可选坐标、系列、可选余票、显著奖项、来源状态、新鲜度、字段置信度、审核状态和证据包引用。

用户证据包只在用户点击“收手”后主动开始，包含初始版面照片、当前版面状况、本机抽取记录、集中拍摄的已抽赏票、位置授权结果和地点备注。OCR 只生成按奖级计数的核对草稿，不能替代记录或直接公开；任一奖级数量不一致、照片不完整、位置不明确或用户取消时，证据包只保留在私人草稿或直接删除，不进入地图。地图最终发布的是核对后的当前版面状态、初始版面照片的授权展示版本、地点、时间和备注，不公开用户逐抽记录、抽中赏级或赏票原图。

### 5.3 共享取证流程

1. 用户在一番赏版面工作台的移动端底部导航上方按住固定悬浮的“决定收手”约 1 秒；胶囊从左到右填充为黑色，填充经过的图标与文字同步反转为白色。未满 1 秒松开或取消手势时，填充归零且不打开弹层；读满后才在同页视觉中心附近打开共享选择。用户可以“愿意并拍摄赏票”、选择“继续抽赏”关闭弹层留在当前版面，或点击底部灰色虚线下划线文字“暂不分享并退出”，把当前状态保存为本机草稿并返回识别首页。后两条路径都不上传任何数据。
2. 勾选后，当前页面内打开相机取证框，而不是跳转到独立相机页；明确提示“请把抽完的赏票全部放在框内拍摄”，并以虚线赏票轮廓提示构图。地点、可选的浏览器定位授权和备注在提交前填写。相机权限只在用户点击拍摄时申请，拒绝后可退出或重试。
3. 用户点击“提交核对”后，服务端以 `boardId` 创建或更新私有、可取消的贡献草稿；同一版面再次提交必须用最新的当前票位和完整抽取记录覆盖原草稿，不能产生第二条贡献。OCR 按 A—Z／OTHER 汇总赏票数量，并与该最新快照逐项比对；前端仍停留在一番赏版面，中央状态框显示“已提交”“后台正在核对本次提交”和“退出后可导入新的版面”，并提供“继续”关闭提示与“退出”返回导入版面；不在前台等待或查看结果页。
4. 后台核对中的记录继续保留在“我的 → 本地记录”，并以“未核对／未上传”显示。OCR 一致且上传完成后，同一条本地记录更新为“已核对／已上传”，同时自动出现在“我的贡献”派生列表；不一致、失败或取消不自动补正、不进入地图，并允许重拍或删除证据。V2 接入社交互动后，点赞数只附着在该条已上传贡献上，不影响核对或上传状态。
5. 服务端只把核对通过且已审核的当前版面状态写入好版地图。地图不公开逐抽记录、抽中赏级或赏票原图；只有通过证据、隐私和新鲜度规则后才显示“已发布”，用户可以请求删除其证据和地图线索。

### 5.4 新鲜度

初始阈值：0—2 小时 fresh，2—12 小时 aging，12—24 小时 stale，超过 24 小时 archived。阈值属于待验证配置，不写死在不可迁移的 UI 逻辑中。

### 5.5 发布与删除

- 低置信地点不得自动上图；
- 每条公开线索必须有来源和回链；
- 原帖删除、售罄或权利人要求下线时停止展示；
- 地图始终提示“线索不是实时库存”；
- AI 只能抽取已合法取得的内容，不猜测缺失地点、余票和时间。

## 6. V3 功能设计

### 6.1 私人与公共分层

| 层               | 证据要求                 | 公共影响             |
| ---------------- | ------------------------ | -------------------- |
| 私人计算         | 无                       | 无                   |
| 上传草稿         | 本轮集中拍摄             | 无                   |
| 待审核           | 证据、票池绑定和前一版本 | 无                   |
| 已验证           | 审核通过                 | 生成新的公共观察版本 |
| 冲突／驳回／作废 | 审核记录保留             | 不改变或回退公共状态 |

### 6.2 贡献流程

私人记录完成后，用户主动选择贡献；系统汇总本轮结果，引导集中拍摄，识别奖项并遮挡敏感信息，再让用户确认差异。提交必须绑定观察时间、地点、票池身份等级和前一可信版本。

### 6.3 票池身份等级

- 未绑定：只有赏券证据，只能保存个人历史或匿名观察；
- 弱绑定：地点、系列、时间和现场版面照片，可形成独立观察；
- 强绑定：经过验证的票池身份或连续证据链，可参与版本演算；
- 权威绑定：商家或官方来源，仍需显示更新时间。

### 6.4 版本与冲突

公共状态使用追加事件和版本链。提交携带基础版本；基础版本已经变化时，不盲目扣减。无法确定顺序时进入冲突状态。作废中间版本时重放后续事件；无法安全重放则暂停公共状态并等待新基线。

### 6.5 隐私与反滥用

- 原图与公开脱敏图分开保存；
- 检测重复图片、明显编辑和跨提交复用；
- 遮挡二维码、活动码、票号和个人信息；
- 高影响提交提高审核等级；
- 提供纠错、申诉、删除和账号退出；
- 驳回不用于公开羞辱用户。

## 7. 网页体验与平台适配

### 7.1 平台边界

- Next.js 手机优先网页是页面行为、内容、组件、视觉和动效的完整批准基线；最终产品 UI 交付为微信小程序，网页验收结果必须整页一比一照搬为 WXML/WXSS、TypeScript 和微信平台适配；
- 网页中间层使用浏览器相机／相册、IndexedDB 或 localStorage 和 Web 分享能力验证交互；小程序端使用相应微信 API，平台差异统一经过适配层；
- 领域逻辑、识别契约、版面语法和会话状态在网页与小程序之间共享，不能把网页专属 API 写入领域层；
- 核心页面已在真实浏览器手机视口和桌面视口验收；照搬后再在微信开发者工具、必要时真机验证平台映射结果与网页基线一致。

### 7.2 识别与私人计算边界

- 图像识别读取完整兑换进度版面，可判断券位为空、已覆盖或未知，但不读取已使用奖券上的内容；
- 识别输出是待确认草稿，确定性计算只接收用户确认且通过守恒检查的结构化输入；
- 识别服务不保存会话历史，不把版面图像发布为公共数据；
- 版面语法和饱和组件注册表随 Next.js 网页包发布，不保存产品版面样本或官方视觉素材；
- 已保存会话的查看、一抽一记、撤销和删除不依赖识别服务。

## 8. 验收策略

### 8.1 自动验证

- 计算公式使用固定向量、枚举小样本和性质测试；约束内方案还必须证明返回抽数满足门槛、前一抽数不满足、从不越过预算／最大抽数／余票，且无解时不放宽约束；
- 状态机覆盖确认、撤销、重复操作和存储恢复；
- 网页覆盖 Next.js 构建、路由、图像权限与上传、本地存储、核心交互和多视口视觉回归；小程序覆盖对应的 WXML/WXSS、微信 API 和平台回归；
- 版面识别使用经授权的固定样本集评估字段准确率、遗漏、低置信、超时和人工校正路径；
- 公共数据版本必须覆盖并发、冲突、回退和删除。

### 8.2 人工验收

- 用户是每个实施区块的默认验收门；同一区块内的 step 各自提供自动验证和人工检查证据，但不互相构成人工解锁门；
- 区块内 step 可以共享尚待区块验收的中间产物；只有整区块通过后，这些产物和新认知才成为后续区块可依赖的已批准基线；
- 每个页面需要在真实手机宽度下审阅；
- V1 用真实抽取任务验证理解度和操作摩擦；
- V2 验证用户是否把线索误解为库存；
- V3 先在受控范围验证贡献意愿、证据质量和审核成本。

## 10. 已确认基线与后续验收

V1 产品基线已于 2026-08-05 通过用户人工验收；其中 UI 主端与交付载体已按 2026-08-06 的用户决策修订：

1. 不使用三种固定模板或产品样本目录；使用 A—Z 奖级、券位和辅助区块组成的通用版面语法，由图像直接生成草稿，先由 Next.js 完整网页基线进行数据驱动渲染，再一比一照搬到微信小程序；
2. 建池时只判断完整进度版面的券位占用，不读取已使用奖券内容；建池后只支持一抽一记，不支持批量轮次；
3. V1 不提供个人价值或价值期望模块；
4. V1 已以 Next.js 手机优先网页完成全部页面、行为、组件、视觉和动效验收，再整套一比一照搬为微信小程序最终 UI；Figma 仅作可选参考，既有小程序壳只提供工程与平台验证基础；
5. V2 只在授权 API、平台合作、本人授权内容或人工策展中建立可下线的合法供给；
6. V3 默认使用门店、系列、时间和现场版面照片的弱绑定；编号或证据链经验证后才可升级为强绑定。

V1-01A 的产品目录覆盖政策已被 2026-08-05 的版面语法认知取代并保留为历史记录，不再承担 V1 发布门禁。识别效果仍需在后续步骤使用少量经授权图片做质量评估，但这些图片不是运行时产品目录。
