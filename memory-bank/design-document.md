## 1. 产品定义

ICHI 是一套面向一番赏玩家的个人决策与可信信息产品。产品从私人即时计算开始，只有前一阶段价值和风险门通过后，才增加公共线索与社群能力。

### 1.1 产品承诺

- 让用户在票池变化时持续看到可复现的数学结果；
- 把预算、目标和停止选项放在与继续抽取同等位置；
- 清楚区分私人记录、外部线索、用户观察和权威库存；
- 让任何公共状态都能追溯来源、时间、证据和版本。

### 1.2 非目标

- 不售票、代抽、交易、支付或托管资金；
- 不做商家后台、库存接口、信用分、黑名单或举报平台；
- 不判断商家是否作弊、藏票、诈骗或违法；
- 不把概率或期望表达为稳赚、回本、保底；
- 不绕过第三方平台限制获取内容；
- 不暗示 ICHI 是品牌方或一番赏官方产品。

## 2. 用户与使用场景

### 2.1 主要用户

| 用户 | 目标 | 最大摩擦 |
| --- | --- | --- |
| 目标型玩家 | 获取指定 A/B/SP/Last 奖 | 只看见大奖仍在，不知道继续成本 |
| 预算型玩家 | 控制单次投入和停止点 | 抽取过程中容易失去累计成本感 |
| Last 猎手 | 比较包套与直接购买 | 只凭余票数量判断，忽略其他奖品与预算 |
| 记录型玩家 | 保存多轮变化和复盘 | 票池、目标与抽取结果散落在纸笔或聊天里 |
| 线索型玩家 | 找到值得现场核对的版面 | 外部内容分散、过期，来源和时间不清楚 |
| 贡献型玩家 | 分享可验证的抽取观察 | 手工自报缺少可信度，逐张上传又太麻烦 |

### 2.2 首发场景

V1 首发场景是用户已看到一个具体票池，正在付款或继续抽取前做决定。现场可能是线下门店、快闪店或线上售卖页面，但交互不依赖商家系统。

### 2.3 Jobs to Be Done

1. 当我准备参与一个票池时，我想快速建立当前状态，确认输入能否用于计算。
2. 当我有目标奖和预算时，我想比较不同抽数、包套、直接购买和停止。
3. 当我抽完一轮时，我想用少量点击更新票池，而不是重新录入全部数据。
4. 当我误点或记错时，我想撤销最近一轮并恢复所有相关结果。
5. 当我远程寻找版面时，我想先看到来源和发布时间，而不是被“实时库存”误导。
6. 当我贡献公共信息时，我想一次集中上传证据，并清楚知道哪些信息会公开。

## 3. 版本策略

### 3.1 V1：即时计算

核心假设：持续、低摩擦、确定性的票池交互，比一次性概率答案更有价值。

V1 完全本地可运行，不要求账号、云服务、图片识别或公共数据。

### 3.2 V2：好版线索地图

核心假设：合法取得且显著展示来源、时间和新鲜度的线索，能缩短发现路径，又不会被理解成实时库存。

V2 必须先证明合法、稳定的数据供给；没有供给就不开发自动地图。

### 3.3 V3：可信票池社群

核心假设：私人点击保持零摩擦，公共贡献集中举证，配合票池身份、审核和版本链，可以形成可信但非官方的公共观察。

V3 必须经过受控试验，不直接开放公共写入。

## 4. V1 功能设计

### 4.1 信息架构

| 页面／区域 | 主要职责 |
| --- | --- |
| 开始页 | 创建空白票池、选择模板、继续本地会话 |
| 票池设置页 | 编辑余票、奖项、单价、Last 状态，运行守恒检查 |
| 目标与预算区 | 设置目标奖、计划抽数、预算、停止条件和可选个人价值 |
| 抽取页 | 展示可操作票池、本轮草稿、即时结果和核心行动 |
| 方案比较层 | 并列比较抽取、包套、直接购买和停止 |
| 历史页 | 查看轮次、累计花费和撤销最近一轮 |
| 方法与隐私页 | 公式、假设、数据保存、删除和非官方声明 |

### 4.2 创建票池

用户可以：

- 从空白票池开始；
- 从至少三种不含受保护视觉素材的结构模板开始；
- 继续最近一次未结束的本地会话；
- 复制一份历史票池作为新会话，但必须生成新 ID 和新开始时间。

必填字段：剩余总票数、至少一个奖项、每个奖项剩余数量、单抽价格。

可选字段：系列别名、Last 状态、目标奖、预算、计划抽数、个人价值和直接购买参考。

### 4.3 输入校验

系统输出三种状态：

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| 可计算 | 余票、奖项数量和必填字段完整且守恒 | 允许显示正式计算结果 |
| 信息不足 | 缺少票数、奖项或单价 | 标出缺失字段，不给正式结果 |
| 存在矛盾 | 奖项余量之和不等于余票，或数量出现负数 | 展示矛盾项，阻止确认和继续计算 |

多次未中奖不是异常信号。V1 不输出藏票、作弊或商家风险结论。

### 4.4 目标与预算

用户可以选择多个目标奖，并为每个目标设置需要数量。预算包括：

- 本次会话预算；
- 最大计划抽数；
- 可选停止条件；
- 可选的奖项个人价值；
- 可选的直接购买参考价。

个人价值只代表用户自己的支付意愿。没有个人价值时，不显示“回本率”或净值结论。

### 4.5 确定性计算

设剩余总票数为 R、目标票数量为 T、计划抽数为 k、单抽价格为 c。

| 结果 | 规则 |
| --- | --- |
| 下一抽命中率 | T ÷ R |
| k 次至少命中一次 | 1 − C(R−T, k) ÷ C(R, k) |
| k 次命中 x 次 | C(T, x) × C(R−T, k−x) ÷ C(R, k) |
| 目标奖期望数量 | k × T ÷ R |
| 首次命中任一目标的期望抽数 | (R+1) ÷ (T+1) |
| 包套成本 | R × c |
| 剩余预算最大抽数 | floor(剩余预算 ÷ c)，且不超过 R |

规则要求：

- k 小于 0、R 小于 0、T 大于 R 或 k 大于 R 时不给正式结果；
- T 为 0 时命中概率为 0；
- k 为 0 时命中概率为 0；
- k 等于 R 且 T 大于 0 时至少命中一次概率为 1；
- 复杂多目标计算使用精确组合数或动态规划，不简单相乘；
- 同一输入与公式版本必须得到相同结果；
- 所有结果可查看输入、公式版本和限制。

### 4.6 抽取记录状态机

一轮记录包含四个状态：

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| 空闲 | 没有本轮草稿 | 点击奖项开始记录 |
| 草稿 | 本轮奖项已选但未写入票池 | 增减数量、清空、确认 |
| 已确认 | 本轮已扣减票池并计入成本 | 开始下一轮、撤销最近一轮 |
| 已撤销 | 最近一轮影响已反向恢复 | 查看历史，不重复撤销 |

确认本轮时必须原子地更新：奖项余量、剩余总票数、本轮成本、累计花费、历史记录和所有计算结果。

如果本轮数量超过对应奖项余量，禁止确认并指出具体奖项。

### 4.7 撤销

- 只支持撤销最近一轮，避免中间状态重放复杂度；
- 撤销恢复奖项余量、余票、累计成本和计算结果；
- 被撤销轮次保留在历史中并标记状态；
- 再次撤销同一轮不会重复增加余量；
- 用户修改票池结构后，如果无法安全撤销，应明确提示并要求确认新基线。

### 4.8 四种方案比较

四种结果同屏并列，不使用单一神秘推荐分：

| 方案 | 必须显示 |
| --- | --- |
| 抽取 | 抽数、成本、目标概率、预算占用和限制 |
| 包套 | 清池成本、确定获得的剩余奖项、Last 条件和预算状态 |
| 直接购买 | 用户填写的参考价、与抽取和包套的现金差；无参考价则显示未知 |
| 停止 | 已花费、剩余预算、停止条件和可保留的会话记录 |

超出预算时，包套和增加抽数只能显示“不建议”或“不可执行”。当 k 小于 R 时，不虚构 Last One 获得概率。

### 4.9 本地存储与删除

V1 保存以下本地实体：

| 实体 | 关键字段 |
| --- | --- |
| PrizePool | ID、系列别名、余票、奖项集合、单价、Last 状态、更新时间 |
| Prize | ID、等级、名称、剩余数量、可选个人价值 |
| DrawSession | ID、初始票池、当前票池、目标、预算、累计花费、轮次 |
| DrawRound | ID、时间、奖项与数量、成本、状态 |
| FormulaSnapshot | 公式版本、输入摘要、输出摘要 |

要求：

- H5 与小程序使用相同领域模型；
- 本地存储通过平台适配层实现；
- 用户可以删除单个会话或全部本地数据；
- V1 不进行自动云同步；
- 本地结构升级必须有迁移版本和失败回退。

### 4.10 V1 异常与边界

| 情况 | 预期行为 |
| --- | --- |
| 目标奖数量为 0 | 告知目标已无余量，并突出停止或直接购买 |
| 抽数超过余票 | 将抽数限制为余票或要求修正 |
| 预算不足一抽 | 显示不可继续，不隐藏已有历史 |
| 奖项数量不守恒 | 阻止正式计算和确认本轮 |
| 本地保存失败 | 保留当前内存状态并提示导出或重试 |
| 页面意外关闭 | 恢复最近一次成功保存的会话，不虚构未保存草稿 |
| H5 无 IndexedDB | 降级到受限本地存储并明确容量风险 |
| 小程序存储接近上限 | 提示清理历史，不静默删除 |
| 组合数规模过大 | 使用稳定算法；无法精确计算时明确失败，不返回近似伪精确值 |

### 4.11 V1 文案与视觉约束

- 不使用“冲一把”“回本”“再来一次”“欧气”等刺激性 CTA；
- 红色只表示错误或预算危险，不表示商家违规；
- 页面优先显示事实、输入与组成项，再显示标签；
- ICHI 使用独立设计系统，不复刻官方海报和角色视觉；
- H5 与小程序保持相同信息层级和组件语义，允许平台导航与分享行为不同；
- 颜色不得是唯一状态表达；H5 以 WCAG 2.2 AA 为目标。

## 5. V2 功能设计

### 5.1 数据边界

允许的数据来源按优先级排列：

1. 官方授权 API 或平台合作；
2. 原帖作者授权或用户提交本人内容；
3. 人工策展的必要元数据与普通回链；
4. 以上都不成立时，不进行自动聚合。

### 5.2 BoardLead

每条线索至少包含：来源平台、来源 URL、发布时间或未知、收录时间、地点文本、可选坐标、系列、可选余票、显著奖项、来源状态、新鲜度、字段置信度和审核状态。

### 5.3 新鲜度

初始阈值：0—2 小时 fresh，2—12 小时 aging，12—24 小时 stale，超过 24 小时 archived。阈值属于待验证配置，不写死在不可迁移的 UI 逻辑中。

### 5.4 发布与删除

- 低置信地点不得自动上图；
- 每条公开线索必须有来源和回链；
- 原帖删除、售罄或权利人要求下线时停止展示；
- 地图始终提示“线索不是实时库存”；
- AI 只能抽取已合法取得的内容，不猜测缺失地点、余票和时间。

## 6. V3 功能设计

### 6.1 私人与公共分层

| 层 | 证据要求 | 公共影响 |
| --- | --- | --- |
| 私人计算 | 无 | 无 |
| 上传草稿 | 本轮集中拍摄 | 无 |
| 待审核 | 证据、票池绑定和前一版本 | 无 |
| 已验证 | 审核通过 | 生成新的公共观察版本 |
| 冲突／驳回／作废 | 审核记录保留 | 不改变或回退公共状态 |

### 6.2 贡献流程

私人记录完成后，用户主动选择贡献；系统汇总本轮结果，引导集中拍摄，识别奖项并遮挡敏感信息，再让用户确认差异。提交必须绑定观察时间、地点、票池身份等级和前一可信版本。

### 6.3 票池身份等级

- 未绑定：只有赏券证据，只能保存个人历史或匿名观察；
- 弱绑定：地点、系列、时间和现场版面照片，可形成独立观察；
- 强绑定：经过验证的票池身份或连续证据链，可参与版本演算；
- 权威绑定：商家或官方来源，仍需显示更新时间。

### 6.4 版本与冲突

公共状态使用追加事件和版本链。提交携带基础版本；基础版本已经变化时，不盲目扣减。无法确定顺序时进入冲突状态。作废中间版本时重放后续事件；无法安全重放则暂停公共状态并等待新基线。

### 6.5 隐私与反滥用

- 原图与公开脱敏图分开保存；
- 检测重复图片、明显编辑和跨提交复用；
- 遮挡二维码、活动码、票号和个人信息；
- 高影响提交提高审核等级；
- 提供纠错、申诉、删除和账号退出；
- 驳回不用于公开羞辱用户。

## 7. 跨端体验

### 7.1 共享

- 领域模型、计算内核、状态规则、文案语义和设计 Token 共享；
- 页面结构与业务组件尽可能共享；
- 同一测试向量在 H5 和小程序必须一致。

### 7.2 平台差异

- H5 使用浏览器历史、IndexedDB 和 Web 分享降级；
- 小程序使用平台导航、Storage、分享和开发者工具验证；
- 页面不得直接散落调用 `window`、`document` 或 `wx.*`，统一经过平台适配层；
- H5 用于快速视觉回归，小程序每完成一个核心页面同步验证。

## 8. 验收策略

### 8.1 自动验证

- 计算公式使用固定向量、枚举小样本和性质测试；
- 状态机覆盖确认、撤销、重复操作和存储恢复；
- H5 覆盖核心流程、响应式、可访问性和视觉回归；
- 小程序覆盖编译、页面栈、Storage 和核心交互；
- 公共数据版本必须覆盖并发、冲突、回退和删除。

### 8.2 人工验收

- 用户是每个实施步骤的默认验收门；
- 每个页面需要在真实手机宽度下审阅；
- V1 用真实抽取任务验证理解度和操作摩擦；
- V2 验证用户是否把线索误解为库存；
- V3 先在受控范围验证贡献意愿、证据质量和审核成本。

## 9. 决策门

| 门 | 进入条件 | 未通过时 |
| --- | --- | --- |
| 开始 V1 编码 | 本文、技术栈和 V1 计划获用户确认 | 继续修改文档，不初始化代码 |
| V1 发布候选 | 双端核心流程、计算和可用性验收通过 | 修复 V1，不进入 V2 |
| V2 启动 | V1 使用价值与合法数据供给同时成立 | 保留并深化 V1 |
| V3 启动 | V2 价值、票池身份和审核模型成立 | 不开放公共写入 |

## 10. 当前待确认

这些问题不阻止文档审阅，但会在对应实施步骤成为验收项：

1. V1 模板的三种默认结构具体采用哪些票数和奖项组合；
2. 一抽一记与批量记录的默认交互；
3. V1 是否展示个人价值期望为默认模块，还是折叠高级项；
4. V1 首发是否同时发布 H5 与小程序，还是先完成 H5 候选再同步上架；
5. V2 的合法数据供给路线；
6. V3 可稳定识别票池身份的字段。
