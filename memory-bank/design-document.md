# ICHI Product Design Document

2026-08-29 V1.0.0 product closure：V1 产品开发、三层架构、7 条产品规则、自动验证、真机 blocker、发布候选、release commit、备案／上架准备与微信送审均已完成并冻结。当前未声称审核通过或正式发布；V1 唯一活动计划是 `V1.0.0 WECHAT SUCCESSFUL PUBLICATION`。审核期间除真实拒绝原因或 production release blocker 外不修改 V1 行为，普通体验／性能优化进入 V1.0.1 backlog，V2 公共地图能力保持未启动。

2026-08-29 V1 PHOTO 技术失败语义：LOCATION 已通过后，Provider HTTP／网络／超时、响应解析、Provider Schema 或服务端暂时异常都属于可重试的 `PROVIDER_FAILED`，不得伪装成表示照片事实不匹配的 `PHOTO_FAILED`。同一 submissionVersion 的 evidence 在既有临时保留窗内必须继续可用于明确的“重新核验”；只有 Provider 成功返回且 schema/normalize 完成后的实体证据无效、未知或 expected-vs-observed exact reconciliation 不一致，才进入对应 PHOTO 业务失败。技术失败不发布、覆盖或删除 Current P1，也不得放宽赏级与实体票精确核验。

2026-08-28 V1 Current Publication 最终契约（取代本文较早的“同一 Board 多 Observation”临时规则）：产品固定为 Local Board、Upload Submission、Current Cloud Publication 三层。`MY_RECORDS` 只投影当前设备 Storage 中以 `boardId` 为身份的 Local Board；`MY_UPLOADS` 与未来 MAP 只投影本人每个 `ownerAccountId + boardId` 最多一条当前云端发布，以稳定 `recordId` 为身份；`drawSubmissions` 与单调 `submissionVersion` 只表达上传尝试。第一次上传建立 P1，后续完整通过 LOCATION／PHOTO／NOTE 的上传只原子更新同一 P1；PENDING、FAILED、Provider／网络异常和迟到旧版本均不得覆盖、隐藏或删除上一版可信 P1。服务端负责 one-current 唯一性，客户端去重只作防御。

删除 Local Board 只删除本机 repository 对象，P1 继续存在；从 `MY_UPLOADS` 明确确认“删除版面线索”后，服务端删除／撤回 P1 及关联上传数据，当前设备只有取得明确删除受理回执后才级联删除对应 Local Board。随机 404、网络失败或未知响应不得删除本机 Board；崩溃恢复使用可持久化 pending marker 重试同一 owner-scoped 删除。显式删除墓碑不得被旧 submission、刷新或 lazy recovery 复活。

新版面入口在账号资料已就绪时必须先使用页面内最近一次权威额度快照：已知 `remaining=0` 时立即显示耗尽态，不重复执行账号 bootstrap、资料读取、记录列表读取、位置或相机门禁；已知可用时只调用 `get-quota-status` 做最小服务端预检，再进入位置／相机门。页面 `onShow` 与用户关闭额度耗尽提示后必须重新读取权威额度，使跨日或管理端合法重置后的旧零值失效；最终预占和扣减仍由 `reserve-recognition`／finalize 服务端事务裁决，客户端快拒绝不替代服务端权威。

2026-08-28 历史说明：较早的“每次成功上传建立独立 Observation、同一 `boardId` 多条记录全部进入 MY_UPLOADS、云端删除后保留 B1 并 lazy recovery”规则已正式废止；本文件只以上方 Current Publication 最终契约为当前行为。仍保留的兼容点只有 NEW upload 备注为空、同一次 NOTE_FAILED attempt 保留原文、never-uploaded／非显式删除的 legacy stale reference 不误删 B1。

2026-08-28 V1-F 记录列表刷新规则：“我的记录”和“我上传的版面”在每次进入时重新读取本机与云端事实；两页即使记录不足一屏或为空，也保持上下边界均可越界后回弹的滚动区域。只有用户在列表顶部继续下拉超过阈值时执行一次互斥刷新，完成后回弹到顶部；列表底部继续上滑只提供越界回弹，不触发刷新。刷新期间不得重复发起同类请求，不得改变记录状态语义或覆盖滑动删除身份。

2026-08-27 V1-F 上线收口规则：第一版生产赏票位置核验半径批准为 `200m`，只允许通过线上 `recognize-draw-tickets` 的 `PRIZE_TICKET_LOCATION_RADIUS_METERS=200` 环境配置提供；源码不得硬编码，配置缺失或非法仍 fail closed。小程序“我上传的版面”必须只按服务端 machine-readable verification status 映射失败体验：`LOCATION_FAILED` 显示“核验失败”且无操作，`PHOTO_FAILED` 显示“照片核验失败”并只允许“重新上传”，`NOTE_FAILED` 显示“备注未通过”并只允许“修改备注”；不得通过 message 文本猜测。PHOTO replacement 继承 LOCATION PASS，NOTE retry 继承 LOCATION/PHOTO PASS；APPROVED 与全部 PENDING 状态不显示失败操作。修改备注弹窗采用紧凑自适应高度，输入框必须在弹窗内水平居中且不溢出，说明文字位于输入框下方，重新核验操作与说明保持清晰的垂直间距；操作按钮与其居中的光晕容器必须使用相同宽度，不得因通用固定按钮宽度向任一侧溢出。用户提交重新核验备注后必须立即关闭弹窗并返回“我上传的版面”，后台结果只能通过列表状态、下拉刷新或再次进入页面观察，不得让弹窗等待核验终态后才关闭。

2026-08-27 V1-F 用户文本安全统一规则：当前进入服务端内容安全审核的用户文本仅有资料昵称 `nickname` 与未来地图备注 `userNote`。两者必须复用同一个服务端文本安全能力，业务 usage 固定为 `PROFILE_NICKNAME` 与 `MAP_NOTE`，并由服务端分别映射微信 `msgSecCheck scene=1`（资料）与 `scene=2`（评论）；客户端不得提交或覆盖 scene。共享能力只返回 `passed=true/false`，只有微信明确 `suggest=pass` 才通过，其余风险、复核、拒绝、未知、异常和不可用全部 fail closed。昵称必须先审核通过再由 owner-scoped `bind-wechat-profile` 写入，失败保持原昵称并返回稳定错误；MAP_NOTE 继续沿用现有 NOTE gate、备注变更失效和只重跑 NOTE 的业务状态机，只替换底层直接 OpenAPI 调用。

2026-08-27 V1-F R2 送审与抽取事实加固：R2 的 `tiers[].remainingTickets` 在用户确认后是不可变的初始未贴票数基线；当前剩余数只能由该基线减去已确认 draw events 确定性投影，`finalSnapshot` 只是可重建的当前投影，不得反向覆盖 `initialSnapshot`。客户端继续以本机 history 承担逐抽与撤销；拍摄赏票送审时，把具有稳定 `eventId` 的完整事件批次提交到服务端事务边界。相同批次和同一 submission version 重试幂等，不同并发批次不能覆盖已提交事实，同一赏级事件合计不得超过初始 R。

赏票送审新增用户原文 `userNote` 必填字段；系统不得生成、续写或改写。服务端门禁固定为 `LOCATION_PENDING → LOCATION_PASSED → PHOTO_PENDING → PHOTO_PASSED → NOTE_PENDING → NOTE_PASSED → APPROVED`，失败分别为 `LOCATION_FAILED`、`PHOTO_FAILED`、`NOTE_FAILED`：地点失败是本次提交终态且前端只显示“核验失败”；照片失败只允许重新上传照片；备注失败只允许修改备注，任何备注文本变化都使旧的备注通过结论失效。地点比较使用版面拍摄位置与赏票拍摄位置；距离阈值必须来自明确配置，未配置时保持待核验并阻止后续门和 `APPROVED`，不得猜测默认值。备注只有真实内容安全服务明确返回通过时才可进入 `NOTE_PASSED`；服务不可用、返回人工复核或结果不明都必须阻止批准。

只有全部三门由服务端核验通过的 R2 正式记录才标记 `APPROVED` 并可供未来地图投影读取；客户端布尔值不构成门禁事实。同一送审版本重试不得创建重复正式记录。正式记录保留结构化 R2 字段、权威 draw events、服务端门禁结果和用户原文备注，但不保存版面图、赏票图、T/P 或 Provider 原始输出；赏票图片仅作当次核验临时输入，终态后按临时对象策略删除。历史 H0/R1 与既有私有记录继续由兼容读取层展示，不做破坏性全量迁移。

2026-08-27 V1-F R2 第二阶段规则：第一阶段冻结的 `r2_direct_remaining` Prompt、Provider Schema、resolver 与 H0 `hybrid_semantic` fallback 均保持不变；本阶段只迁移用户确认后的业务模型。R2 识别结果页只展示并允许修改 IP、主题、用户手填的单抽价格和每个视觉赏级的 `remainingTickets`；价格默认空且不得由图片、IP 或主题推断，`remainingTickets=0` 是合法明确值，`null` 必须保持为空并阻止确认。新 R2 草稿、正式版面与 CloudBase 记录不写 `totalTickets`、`pastedTickets`、`totalTicketsObserved` 或 `pastedTicketsObserved`，也不执行 T/P/R 互推；Provider 的 `visibleNumberRuns` 仅属于识别 trace/debug，不进入地图、抽赏或正式版面依赖。

R2 新流程固定为“拍摄版面 → R2 识别 → 核对识别结果 → 设定大赏 → 形成正式版面 → 抽赏”。“设定大赏”列出包括 `remainingTickets=0` 在内的全部赏级并允许多选；赏级按原有顺序使用两列网格逐行排列（A/B、C/D……，奇数末项留在左列），双列网格需在滚动容器内保留水平安全边距，左右卡片及选中描边均不得被屏幕边缘裁切；提示“总抽数低于 3 抽的就是大赏”只帮助用户判断。程序绝不能以 `remainingTickets<=3`、赏级字母、原始总抽数阈值或旧目标赏规则自动分类。用户勾选项持久化为 `isGrandPrize=true`，其余为 false；最终版面的 Grand／Normal 分区只读取该字段，刷新与恢复后不得丢失。

R2 赏级状态球的初始数量等于用户确认的 `remainingTickets`，初始全部亮起；每条已确认抽取事件只熄灭对应赏级一个球，不能超过初始数量或产生负状态。`remainingTickets=0` 的赏级仍显示“未贴票数 0”且状态球为空。正式版面保存初始 R，抽奖记录继续作为已发生抽取的事实源；刷新、重新进入和赏票核验均由初始 R 加抽取事件重建当前状态，不因后续识别值变化重写历史。记录列表和抽奖工作台只向用户显示“剩余 N 抽”，不显示“剩余/总数”或已贴数。

新云端业务文档版本为 `board-record-r2-1.0.0`，以结构化字段保存 `recognitionVersion=R2`、IP、主题、用户价格、GCJ-02 可查询位置、每赏 `tierCode/rawLabel/remainingTickets/isGrandPrize`、可信服务端创建/更新时间及既有 owner 归属；不得把整个对象 JSON stringify 成字符串。旧 H0/R1 `board-snapshot-1.0.0` 与本机 schema v1 记录仅由 legacy read adapter 读取，可在适配器内沿用可靠的历史 R 计算和旧分类，不做破坏性全量迁移，也不得让旧逻辑进入 R2 writes。未来地图只消费用户确认后的正式记录投影，不解析 Provider 原始 JSON；V2 公开地图、审核和发布门仍保持锁定。

版面识别图片继续遵守已冻结的 ephemeral／不持久化隐私契约，所以本阶段正式 R2 记录不保存 `boardImageFileID`：该字段只有在未来另行批准图片留存、Storage 私有前缀、删除与隐私迁移后才能加入，不能以即将过期的 `recognition-temp/` fileID 伪装为长期原图引用。赏票原始证据的既有私有留存规则不变。

2026-08-27 V1-F R2 第一阶段规则：生产主识别方案改为 `r2_direct_remaining`。Provider 只返回作品／主题、视觉赏级、每个赏级的直接未贴票数 `remainingTickets`，以及可选的可见数字观察对象；CloudBase 不再从 R1 的 T/P/U、序列、方向、最大序号或守恒关系推理 R。Provider 的非 null R（包括 `0`）拥有最高优先级；Provider R 为 null 且存在观察对象时，以观察对象数量作为回退；二者都不存在时保持 null。观察对象即使 `{value:null,rawText:null}` 也计为一项可见证据。第一阶段不伪造总票数或已贴票数：RecognitionContract 中 T/P 保持 null，客户端仅做不崩溃和保留直接 R 的兼容，用户仍需补齐完整票池事实后确认。H0 `hybrid_semantic` 保持字节级冻结并继续作为唯一生产回滚；R1 文件、实现与回归只作为历史基线保留。

2026-08-27 V1-F R1 可见证据生产迁移规则：生产默认识别改为 `r1_remaining`，H0 `hybrid_semantic` 保持字节级冻结并成为唯一回滚模式；旧 `v4 / LEGACY_V4_ROLLBACK` 从运行时选择、部署包和生产配置中移除。普通客户端仍不能选择或传入识别模式。R1 模型只观察 `ipName/ipRawText/themeName/price`、赏级分段、视觉顺序数字运行、可见实体票数与可见叠贴票数，不得返回总票数、已贴票数、未贴票数、候选、方向结论、置信度或推理；CloudBase 以确定性约束求解产生权威 `totalTickets` 与 `remainingTickets`，并且只在二者均为合法整数且 `0 ≤ remaining ≤ total` 时派生 `pastedTickets = total - remaining`。空的可见数字运行绝不等于未贴为零；零值只有在明确、无冲突的耗尽证据通过保守门禁时才可确认。局部不可唯一求解时保留 `null` 和问题码，允许用户核对，不得以猜测补全。

识别结果编辑主语义同步迁移为“总票数 T + 未贴的票数 U”：两者可编辑，已贴的票数 P 只读并由 `T-U` 实时派生；清空严格保持 `null`，合法的 `0` 不得被当作缺失。确认、字段光晕和 Board Builder 门禁只以 T/U 的正整数／非负整数、`U ≤ T` 和派生守恒为准。旧本地草稿只有在 T/P 均为合法整数且 `0 ≤ P ≤ T` 时才迁移为 `U=T-P`；若已有显式 U，则以 T/U 为权威并重新派生 P。Provider 对 A1/A2 等 child label 必须保留原始身份且不得误映射为 SP；现有业务契约仍按已批准规则在确定性规范化阶段聚合到父字母，原始 child 进入可审计 trace。SP1—SP4 继续按视觉独立赏级保留。

2026-08-26 V1-F H0 生产迁移规则：版面识别生产默认已切换为经真实对照冻结的中文 Hybrid Direct-Pasted H0。Qwen 单次整版调用只返回 `ipName/ipRawText/themeName/price/tiers`，每个视觉独立赏级只返回 `rawLabel/prizeName/totalTickets/pastedTickets`；不得返回或重新引入 `ticketPattern`、序号／剩余标签 evidence、remaining、整板合计、置信度或推理。CloudBase 必须先保留每个 raw visual tier，严格保留 null 与 0，再执行范围检查、字母数字 child-first 聚合、重复 child 冲突、特殊赏按视觉顺序映射、remaining 和整板求和，最终仍输出 `RecognitionContract 1.0.0`。无可用赏级和技术失败才整体失败；局部 null、范围冲突和缺失赏级保持可编辑。客户端、Board Builder 不改变，已确认不可变 snapshot 仍是唯一输入；旧 v4 路径只作为服务端 `LEGACY_V4_ROLLBACK` 保留，客户端不能选择识别模式。生产 override token 常态不存在，未授权 override 必须在 Provider、quota 与业务副作用前拒绝。

2026-08-25 V1-F 识别确认与额度修复规则：`ipName` 只表示作品／franchise 主名称，`themeName` 独立表示篇章、系列、周年、Vol 或活动副标题；成熟别名可确定性映射，未知作品不得猜译。用户确认识别结果时必须冻结不可变生成快照并锁定 IP、主题、价格和票数字段；Board Builder 只能消费 snapshot 的最终 `totalTickets/pastedTickets`，余票唯一等于二者之差，不得重新读取 raw 模型 evidence。完整可恢复本地版面落盘后立即进入版面，CloudBase finalize 在可恢复后台原子提交观察与配额；Provider／AJV／Normalize／本地构建／持久化失败不增加 `used`，仍未提交的预占必须释放，同一 recognition job 的重复 finalize 幂等。历史云端 assisted-draw 记录若保留完整初始快照可直接重建本地版面且不再调用模型，不可恢复的空草稿明确标记并保留删除能力。

2026-08-25 V1-F 叠贴回收券计数规则：模型以 `boardCountStyle` 区分编号票位、叠贴回收券、混合或未知，并由每个 raw tier 选择最小 `countMode`。编号前缀只观察容量、序列起点和首个空位；叠贴结构按实体票计数，每个独立露出的赏级票头和每段末端完整长票都各算一张，同赏级跨行／跨段必须合计；明确“あとN枚／残りN枚”只作为剩余数，不是编号空位。CloudBase 负责所有加减、null 与父级聚合。真实 NIKKE 样本若当前固定模型仍漏数，必须保留人工编辑并标记模型视觉限制，不得在 CloudBase 写“可见字母 + 1”或赏级特例。

2026-08-22 V1-F 产品减法覆盖规则：辅助抽赏只保留“实时相机 → 首次拍摄冻结 → 撤回或对勾确认 → 权威配额预占并识别 → 可编辑识别结果 → 直接进入抽赏版面”。独立视觉矫正、四角检测／拖动／透视输出和目标赏级选择均退出产品流程，不得以新的中间页替代。识别结果中的 IP、主题、总票数和已贴数仍可人工修正；新草稿不写入也不要求 `targetTiers`，旧草稿／记录中的目标赏级只做兼容读取。“抽到目标赏级”不再作为新流程可配置情景，其他情景能力及默认值保持不变。

2026-08-23 V1-F 真实识别验收规则：四张授权实体版面构成当前完整 Golden Set；总票数与已贴数必须逐赏 exact match，不能用“差 1”或可编辑草稿替代准确率通过。真实请求必须保存并检查 Qwen `message.content`、Provider AJV、Normalize、RecognitionContract 与客户端结果，首错层必须有证据。当前 `qwen3.7-flash` 单图基线在两张复杂图上仍于 raw 层失败；不允许用文件名／赏级特判、伪造 fixture、恢复视觉校正页、增加目标赏级页或静默换模型掩盖失败。V1-F 继续 `IN_PROGRESS`，识别结果仍须允许用户人工校正。

## 1. 产品定义

ICHI 是一套面向一番赏玩家，并连接经核验线下门店供给者的现场决策与版面发现产品。它从“用户已经站在真实版面前，如何做决策”开始，再将同一个版面在使用中产生、经用户授权与核对的当前状态，用于回答“出发前去哪里找到想抽的 IP 和值得现场核对的版面”。除玩家现场观察外，持有一番赏授权的线下门店及其经核验员工，也可以直接拍摄店内完整当前版面，提供与真实销售场所直接相连的一手现场来源。产品从可独立成立的私人即时计算开始，只有前一阶段价值与风险门通过后，才增加公共线索和多人协作能力。

### 1.1 产品承诺

- 让用户在票池变化时持续看到可复现的数学结果；
- 让用户在出发前按 IP、位置、时间和版面状态，找到附近值得现场再核对的线索；
- 让经核验的授权门店或店员通过一次完整版面拍摄，提供带门店身份、地点和观察时间的一手现场线索；
- 把预算、目标和停止选项放在与继续抽取同等位置；
- 清楚区分私人记录、外部线索、用户观察和权威库存；
- 让任何公共状态都能追溯来源、时间、结构化观察、用户修订和版本。

### 1.2 核心闭环与差异化

ICHI 围绕同一个真实版面构成两个用户场景的闭环：

```text
附近版面发现
→ 到店核对与拍摄
→ 识别、人工核对、概率／成本决策和持续记录
→ 用户主动提交核对证据
→ 审核后的当前版面状态进入地图
→ 新的附近版面发现
```

该用户闭环与另一条一手现场供给路径同时成立：

```text
授权门店或经核验店员拍摄店内完整当前版面
→ 识别与人工核对
→ 门店／任职关系、位置、观察时间和版面证据核验
→ 审核后以“门店直传”或“已核验店员直传”进入地图
```

V2 还允许不参与抽赏的玩家提供一条“玩家现场直传”路径：用户在现场看到完整当前版面后，可以只拍摄、校正 IP／系列、奖级、价格和地点备注并提交核对，不建立抽赏会话、不选择目标奖，也不记录或拍摄已抽赏票。该来源必须显示为玩家现场观察，并经过地点、观察时间、完整版面证据和发布审核后才可进入地图；它不得获得门店直传或已核验店员直传标记。

关键差异不是同时拥有一个工具和一张地图，而是“产生个人决策价值”与“产生可共享版面供给”发生在同一条使用链路中。用户并不需要先为社区无偿录入数据；拍摄、校正和更新版面首先帮助本人完成现场决策，之后才在明确授权、隐私处理、证据核对和审核后成为公共线索。

该“效用驱动的数据闭环 + 门店一手现场供给”模型，有机会同时降低地图供给的冷启动难度、用户额外贡献负担和历史现场信息缺口，但它仍是待验证假设：V1 必须在没有地图的情况下独立产生价值，V2 必须分来源实测玩家贡献转化、门店直传覆盖与更新频率、供给密度、观察时间理解度，以及“发现→到店核对→新贡献”是否真的发生。

### 1.3 非目标

- 不售票、代抽、交易、支付或托管资金；
- 不做商家后台、库存接口、信用分、黑名单或举报平台；
- 不判断商家是否作弊、藏票、诈骗或违法；
- 不把概率或期望表达为稳赚、回本、保底；
- 不绕过第三方平台限制获取内容；
- 不暗示 ICHI 是品牌方或一番赏官方产品。
- V2 账号不扩展为论坛或通用社群：不提供发帖、评论、关注、私信、群组、用户动态流或以社交关系驱动的内容分发。

## 2. 用户与使用场景

### 2.1 主要用户

| 用户       | 目标                    | 最大摩擦                               |
| ---------- | ----------------------- | -------------------------------------- |
| 目标型玩家 | 获取指定 A/B/SP1—SP4/Last 奖 | 只看见大奖仍在，不知道继续成本         |
| 预算型玩家 | 控制单次投入和停止点    | 抽取过程中容易失去累计成本感           |
| Last 猎手  | 比较包套与直接购买      | 只凭余票数量判断，忽略其他奖品与预算   |
| 记录型玩家 | 保存多轮变化和复盘      | 票池、目标与抽取结果散落在纸笔或聊天里 |
| 线索型玩家 | 找到值得现场核对的版面  | 外部内容分散、过期，来源和时间不清楚   |
| 贡献型玩家 | 分享可验证的抽取观察    | 手工自报缺少可信度，逐张上传又太麻烦   |
| 授权门店／店员 | 快速发布店内真实当前版面 | 通用社交发布难以结构化呈现余票、时间和门店身份 |

### 2.2 两个连续场景

1. 出发前的发现场景：用户有明确 IP 或目标奖，需要知道附近哪里有相关版面，该线索在什么时间被观察，当时的余票和显著奖级是什么。地图帮助用户筛选需要到场再核对的线索，不承诺实时库存，也不替用户得出消费结论。
2. 到店后的决策场景：用户已看到一个具体票池，正在付款或继续抽取前做决定。现场可能是线下门店、快闪店或线上售卖页面，但交互不依赖商家系统。

V1 先交付第二个场景的独立价值，V2 再将第一个场景与核对式共享连接成闭环。

### 2.3 Jobs to Be Done

1. 当我准备参与一个票池时，我想快速建立当前状态，确认输入能否用于计算。
2. 当我有目标奖和预算时，我想比较不同抽数、包套、直接购买和停止。
3. 当我抽完一轮时，我想用少量点击更新票池，而不是重新录入全部数据。
4. 当我误点或记错时，我想撤销最近 50 抽中的任一连续最近轮次，并恢复所有相关结果。
5. 当我出发前寻找想抽的 IP 时，我想按附近位置、版面状态和观察时间筛选，而不是在零散信息中反复搜索。
6. 当我查看地图版面时，我想看到来源和明确的观察时间，而不是被“实时库存”误导。
7. 当我已经为自己拍摄、校正并更新了版面时，我想用一次集中举证完成可选共享，并清楚知道哪些信息会公开。
8. 当我是持有一番赏授权的线下门店或店内员工时，我想直接拍摄店内完整当前版面，校正识别结果后提交，不需要先模拟玩家的抽赏或赏票举证流程。
9. 当我的版面贡献进入地图时，我想让它稳定归属于我的账号，以便查看审核状态、保留贡献记录并在需要时撤回或删除，而不需要参与论坛式社交。

## 3. 版本策略

### 3.1 V1：即时计算

#### 2026-08-21 识别协议收口（当前事实）

本轮 V1-F 继续修订为“本地选定单版面后再识别”：第一次快门冻结原始相机照片，用户二次确认后只执行只读额度可用性检查并进入独立版面校正页；只有在校正页点击“确认并识别”时才执行唯一一次权威原子额度预占。进入、返回或放弃校正页均不消耗额度。校正页使用本地缩略图给出四角建议，允许拖拽、方向一致的局部吸附和手工修正；只在最终确认时执行一次透视校正，上传的唯一图片是校正后的单张完整目标版面。模型不再搜索多版面、选择中心版面或返回焦点框。

模型面对的 Provider JSON 只保留视觉观察：`ipName`、`ipRawText`、可选 `themeName`、价格、按视觉阅读顺序返回的 raw tiers、可读奖品名、每个 raw tier 的总容量、`ticketPattern` 及该 pattern 必需的证据。`empty/prefix/full/irregular/unknown` 分别由 CloudBase 确定性计算 pasted；`prefix` 使用 `sequenceStart` 与 `firstOpen`，`irregular` 使用 `pastedDirect`，未知保持 null。模型不得合并 A1/A2、分配 SP、计算 remaining、返回穷举坐标、执行产品映射或决定 UI。每个 raw tier 必须先单独计算 pasted，再按父字母汇总；独立特殊 tier 才按模型视觉顺序分配 SP1、SP2、SP3……。Prompt 示例、实际 Provider JSON 与 AJV Schema 使用同一套显式语义字段，不允许 compact wire protocol 后再隐藏适配。

E/F/G/H 的真实回归基线固定为 `8/2/firstOpen=3`、`13/2/3`、`26/6/7`、`13/3/4`，但不得硬编码图片规则。现有仓库缺少该次调用的 Qwen 原始 `message.content` 与逐层日志，因此当前不能把故障归类为模型感知、证据处理或后续映射；实现必须先补齐 Provider→AJV→Normalize→Contract→客户端→页面的逐层夹具，并在同一真实输入取得证据后分类。

图片输出基线改为长边约 `1800px`、JPEG quality 约 `82`、约 `1.8–2.5MP` 和实际约 `0.5–1.5MiB` 的性能目标；它们不是伪造的平台硬限制。必须把当前有效约 `4.19MP` 与候选约 `2.62MP` 作为同模型、同协议的独立黄金样本实验，比较奖级、总票、已贴、IP、主题、时延和 Provider usage，再决定是否切换。生产模型继续使用 `qwen3.7-flash`、关闭 thinking 和 JSON Object；协议与模型不得同时切换。

当前生产链使用 `ichi-board-vlm-3.0.0-rc1` 与 `board-provider-extraction-3.0.0-rc1`。Prompt、Provider JSON、AJV Schema、Normalize、RecognitionContract 和客户端解析必须使用同一套语义字段；旧 compact/verbose 仅作为一次性历史迁移。`totalSlots` 与 `pastedSlots` 是独立观察值：缺少已贴数保持 null，逐排与聚合冲突置空并发出 `TICKET_COUNT_CONFLICT`，客户端不使用 `Number(null)`、total fallback 或 remaining 反推。识别结果直接包含 `ipName`、`ipRawText`、可选 `themeName`、`totalTickets`、`pastedTickets` 和可靠时才有的 `remainingTickets`。约 8 MiB 是客户端上传性能目标，20 MiB 是当前 Provider 硬边界，超过即拒绝；CloudBase Storage 上传不受错误的 6MB 云函数事件限制约束。识别事件、位置快照与交换契约均只接受 camera 来源，album 不属于生产输入。真实图片准确率、P50/P90/P95 和百炼成本只有在授权黄金样本／真机验收后才能定论。

本节后续早期版面识别段落中的 2.x Prompt/Schema 版本属于历史说明；当前产品与实现基线以本节 3.0 语义协议为准，不能按旧版本部署或验收。

核心假设：持续、低摩擦、确定性的票池交互，比一次性概率答案更有价值。

V1-26 最初以低保真页面流启动，但经 V1-29 完整设计、实现与用户验收后，Next.js 手机优先网页现为 V1 小程序全部页面、视觉、内容、组件、动效和交互的完整批准基线；微信小程序是最终产品运行端，后续必须把整套网页一比一照搬为 WXML/WXSS、TypeScript 和微信平台能力。这里的“照搬”只允许 HTML/CSS/JavaScript 到小程序语法以及浏览器 API 到微信 API 的必要平台映射，不允许重新设计、重排、简化、替换字体／字号／图标／间距／动效，也不允许在旧小程序 UI 上继续二次创作。用户只能通过页内相机拍摄一张完整、可读的兑换进度版面建立票池，不提供相册导入，确保本次位置与现场观察一致；图像识别只生成可校正的输入草稿。V1 使用随包预置的版面语法与通用组件，不依赖产品版本目录。

V1 同期建立最小微信账号与 CloudBase 私有数据底座，用于可信身份、每日识别配额、本人记录归属、删除和 V2 地图冷启动，不建设公共地图、论坛或社交关系。首次账号建立与有效会话恢复必须发生在任何新版面识别之前；已建立的本机抽赏会话仍可离线继续。首次使用小程序且账号资料尚未完成时，页面必须主动进入“使用微信登录”的确认引导；如果用户先点击“辅助抽赏”或“仅上传版面”，任一入口也会触发同一个首次授权门。用户通过微信当前支持的头像选择与昵称填写能力明确授权后，“我的”页面立即显示获准的微信头像与昵称，另一入口及后续启动不重复显示首次引导；页面切换后不得先回落为默认头像再显示已授权头像。再次点击“我的”页头像或用户名会重新打开带返回键的资料授权界面，允许用户更新头像和昵称；更新界面的“确认更新”默认禁用，只有当前昵称与打开界面时的原昵称不同，或用户重新选择了头像，且最终资料仍完整有效时才激活。昵称改回原值且没有选择新头像时必须重新禁用；只改昵称时沿用当前云端头像，只改头像时沿用当前昵称。资料变化不能改变内部账号、ICHI ID、记录归属或配额。账号管理不展示云函数可信上下文等实现说明，也不显示“已绑定”状态文案。微信身份仍由服务端可信上下文决定，昵称、头像与公开编号均不参与鉴权。普通账号默认按北京时间每天最多完成 5 次有效版面识别；辅助抽赏与仅上传版面共用额度，取消、权限拒绝、网络或提供方失败不扣次数。

“我的”资料区中，头像、昵称与 ICHI ID 必须作为一个左对齐资料组，从与下方卡片相同的页面内容区左沿开始排列；不可因为头像为按钮或资料区内容宽度变化而居中、产生异常空隙或向右溢出。已授权头像与公开资料允许保存本地展示缓存，进入页面首帧直接显示；云端资料仍是事实源并在后台完成一致性核对，不得先显示白色空头像再切换为用户头像。

V1 版面识别采用阿里云百炼 `qwen3.7-flash` 的单模型、单次整版多模态观察，固定 `enable_thinking=false`、`temperature=0`、提供方 JSON Object 和约 `4MP` 视觉上限，同时读取文字、理解标题／Logo／角色／奖品图像、定位区块并判断票区与赏级的空间归属。运行提示为 `ichi-board-vlm-2.6.0-rc1`；模型只返回较小的提供方抽取草稿，服务端先以 `board-provider-extraction-2.2.0-rc1` AJV Schema 拒绝额外或非法字段，再通过确定性 Normalize 转换为小程序稳定的 `RecognitionContract 1.0.0`。模型分别返回中文主 IP 与可选版面主题，例如“女神异闻录 / 30周年”“明日方舟 / 来份甜点”；主 IP 必填才能确认，主题可由模型或用户填写且允许为空。提示把实体覆盖票、逐排票位、露出的编号底位和每赏自身的印刷容量作为票位证据：每排返回总数／已贴／空位／unknown，并说明总数来自实体票计数、印刷票容量、最大票位序号、完整槽位布局还是未知；“全 X 款／种”等奖品款式文字绝不能当票位容量。先找首个连续空位 `N` 佐证 `N-1` 已贴；空的坐标证据数组不等于“没有空位”，实体票容量证据也不自动等于整级贴满；只有完整票区和逐排守恒证据共同表明没有 open／unknown 时才允许 `covered=total`。不把相邻赏常见容量套给当前赏。模型已确认数出的 `coveredSlots` 即使同时存在少量 `unknownSlots` 也必须进入可编辑输入框，unknown 只降低置信并阻止直接提交，不得抹掉已确认数值。不把纯 OCR 作为生产主链；识别结果首先是用户可编辑草稿，只要能选出一个连贯版面并提取至少一个可用赏级，低置信、遮挡、缺边、归属冲突或计数不完整都进入用户校正，不得丢弃已经提取的数据。只有完全不是版面、无法选出任何连贯候选、没有可用赏级或图片不可读时才要求重拍。确定性代码负责 A—Z 编号分层合并、SP1—SP4、逐排计数复算、坐标、整数范围、票位状态与守恒，并派生总票数、余票、已抽数、大／中／小赏、概率和提交资格。`qwen3.7-plus` 仅是待验证的困难图片兜底，图像 strict Schema 接口、费用门和真实样本未获批准前不启用第二次模型调用。固定提示词与字段职责见 [`docs/decisions/v1-board-recognition-prompt-contract.md`](../docs/decisions/v1-board-recognition-prompt-contract.md)；模型草稿不得直接沉淀为私有观察或公开事实。

无论开发版、体验版还是正式版，云端识别失败、超时、未配置、返回结构不合法或要求重拍时都必须进入“无法建立票池”异常页，并显示可重试原因；不得自动改用固定演示 IP、价格或票数来伪造识别成功。固定夹具只可用于自动测试，不能出现在用户拍摄流程。

新版面入口与取景拍摄都必须把第一次用户操作完整接住。点击“进入辅助抽赏”或“仅上传版面”后立即进入可见的准备状态，并在同一次操作内依次完成账号和位置门禁；准备期间不允许重复发起并发门禁。相机组件仍在初始化时点击拍摄，系统必须记住这次拍摄意图并在 `initdone` 后自动拍摄，不能静默丢弃第一次点击；第一次快门只冻结取景框内照片并把中央快门改为白色对勾，右侧同时出现撤回按钮；撤回清空照片并重新挂载相机，第二次点击对勾才读取服务端权威额度并开始识别。额度耗尽时保留冻结照片并显示“无法建立票池”同款警告卡，只提供“重新导入照片”。权限拒绝或组件错误才进入明确恢复路径。

版面相机必须做到取景框所见即所得：`takePhoto` 返回的传感器图像按当前实时取景框宽高比和同一中心执行 `aspect-fill` 裁切，上传、识别与用户预览只能使用该裁切结果，不能读取取景框外内容。裁切结果最长边控制在约 `2400px`；原始传感器临时图在裁切成功后立即删除，裁切临时图在识别结束后删除。

一张照片出现多个现实版面时，不能把整张图的文字混在一起读取，也不能因为“多版面”本身就直接判失败。模型先按物理外框、共同标题／页脚和连续设计识别版面候选；同一张版面的内部栏目不得拆成多张。选择时先取最接近画面中心的连贯候选，中心接近时再取可见面积最大者，其余版面、货架价签、商品包装和背景全部排除。只要该候选具有可追踪的共同设计边界并能提取至少一个赏级，就生成一张可编辑草稿；缺边、细节不足、票数不确定或赏级可能遗漏都转为待核对字段。只有无法选出任何连贯候选、没有可用赏级或图像不可读时才要求用户重拍。

票位状态以逐槽可见外观为主证据，允许使用版面印刷的“第几张”序号和贴票边界作为复核证据。模型必须把序号与具体槽位对齐，并先确认编号方向；只有序号连续、从起点到边界的槽位都可见且贴票状态连续时，边界后的首个空位序号才可佐证已贴数量。贴票歪斜可以按其主要覆盖槽位归属，但跳贴、跨槽、遮挡序号、顺序不明或序号与视觉状态冲突时必须保留 `unknown`／冲突并交给用户校正，不能把单个数字直接当作已贴数量。

两条新版面入口都必须在拍摄前请求位置授权，并为每一张版面建立不可拆散的私有观察包：版面证据、校正后的结构化信息、位置快照、位置精度、坐标系、位置取得时间、相机来源和授权文案版本共同引用同一 `recordId`。位置来源固定标记为“拍摄时当前位置”。拒绝位置授权或无法获得有效位置时，不执行新版面识别，但不影响已建本机会话。

每次识别成功并由用户校正确认后，两条路径都把初始结构化版面快照、修订差异和位置快照保存到账号私有后端；版面识别照片只用于当次识别，不能长期保存。辅助抽赏结束后另外保存经用户确认的抽赏事实，并由服务端以确定性减法生成最终版面快照。首次赏票 camera evidence 是后台核验与技术重试所需的本人私有原始证据，必须连同首次 capturedAt 等真实性 metadata 保留；后续相册 replacement evidence 以新的 submissionVersion 保存，不能覆盖首次证据。私有沉淀不等于审核通过或公开发布。V2 上线时，符合账号授权、地点、完整度、重复／冲突与审核要求的 V1 历史观察可以进入地图，不因记录时间较早而自动失效或隐藏；地图必须始终显示该事实是在什么时间被观察到，并明确不代表当前库存。

图片传输使用客户端二进制直传私有 `recognition-temp/`，同步云函数事件只携带任务绑定 `fileID` 与元数据。客户端在保护小字的前提下把长边控制在约 `2400px`、JPEG quality 约 `85`，超 `6 MiB` 才继续降至 `2048px/82`。识别云函数只通过 `getTempFileURL` 生成约 `5` 分钟的临时 HTTPS URL并作为百炼 `image_url`，不得下载 Buffer、转 Base64 或构造 Data URL。对象和本机临时文件在当次调用结束后立即双重删除；不得把二进制、临时 URL、签名、Data URL 或提供方原文写入日志、数据库和审计。

当前实现覆写本段早期记录：约 `8 MiB` 是客户端性能目标，`20 MiB` 是 Provider 硬边界，超过即拒绝；不得把云函数事件的 `6 MiB` 限制套到 CloudBase Storage 上传。

“本地记录”在 V1-F 改名为“我的记录”，因为该页面同时包含本机抽赏草稿与本人云端私有记录；“我的贡献／我的版面线索”统一改名为“我上传的版面”，只展示用户明确执行“仅上传版面”或提交赏票核对的记录，不把辅助抽赏的初始私有观察伪装为上传成果。赏票提交与后台核验是两个阶段：客户端先保存首次相机照片到系统相册、按像素预算生成轻量识别图并上传 Storage；服务端 PENDING submission 持久化后，拍摄页立即退出并在“我上传的版面”显示“待核对”。可信抽赏历史同步、短时 URL、Qwen、AJV 与 reconciliation 都属于可恢复后台核验，不得阻塞或伪装成图片上传失败。VERIFIED 显示“核验成功”，MISMATCH／INVALID_EVIDENCE 显示“核验失败”并允许相册新版本重传，NEEDS_REVIEW／PROVIDER_FAILED 显示“核验异常”并优先复用原图重新核验。技术故障不得伪装为真实性不一致，也不得把最终结果回送已离开的拍摄页。未完成识别确认或用户选择暂不分享的抽赏草稿可以只留在本机；已经确认并触发私有沉淀的观察由服务端账号归属和规范 `recordId` 管理。昵称、头像和公开 `ICHI ID` 不参与鉴权，六位记录码也不承担所有权或访问权限。V1 不产生或伪造其他用户互动。既有微信小程序壳和 Storage 适配器只作为平台工程与验证基座，不是视觉或页面设计基线。

### 3.2 V2：好版线索地图与核对式共享

核心假设：地图可以由两类一手现场供给共同支撑。第一类是决策工具中已为玩家本人产生价值的真实版面，在不要求重复录入的前提下，经主动授权、集中举证、隐私处理和审核转化为地图线索。第二类是经核验的授权门店或店员，直接拍摄店内完整现场版面，经身份／任职关系、位置、时间、版面证据和审核后发布。只有来源类型、来源核验状态、观察时间和证据状态同时清楚时，线索才有价值且不易被误读为实时库存。

V2 的两条供给主路径是“版面决策使用 → 玩家本人授权贡献 → 核对审核 → 地图发布”和“授权门店／经核验店员直接拍摄 → 识别校正 → 来源与版面审核 → 地图发布”；官方 API、平台合作或人工策展仍可作为其他合法补充。V2 复用 V1 已建立的账号、私有观察候选、规范记录和删除能力，在此基础上增加公共地图、来源核验、审核、现实版面匹配、版本和发布。用户可以不登录浏览地图或继续使用本机抽赏能力，但玩家贡献、玩家现场直传、门店／店员直传都必须由既有认证会话绑定 `ownerAccountId`；客户端短码不得决定归属。账号不承担论坛、发帖、评论、关注、私信、群组或动态流。

V2 前端扩展玩家的“收手 → 是否共享 → 集中拍摄已抽赏票与地点备注 → 提交核对”流程，以及门店供给者的“核验来源身份 → 拍摄完整当前版面 → 校正识别结果 → 提交审核”流程。玩家提交后不再进入核对结果或待发布预览页面。每次完成一张导入版面的确认时生成唯一 `boardId`；同一账号对同一 `boardId` 的再次提交以最新抽取记录和当前票位覆盖原待核对草稿，不创建第二条贡献。提交确认先保留在一番赏版面上，以中央状态框显示“已提交”和“后台正在核对本次提交”，并提供“继续”（关闭状态框留在版面）与“退出”（返回导入版面）。V1 负责账号绑定、初始结构化版面快照、抽赏后结构化差量与位置观察的私有保存；来源审核、现实版面合并和地图发布仍由 V2 在合法供给、删除权与审核规则通过后接入。

### 3.3 V3：可信票池协作

核心假设：V2 已验证的单次版面贡献，可以在不破坏私人记录零摩擦的前提下，通过票池身份、审核和版本链扩展为可追溯、可纠错的多人公共观察。

V3 必须经过受控试验，不直接开放公共写入。

V1 手机端使用固定底部导航承载三个一级入口：

1. `识别`：进入版面照片导入与识别流程；
2. `好版地图`：为 V2 预留入口。V1 只能展示范围说明，不显示地图、线索、筛选或任何库存暗示；
3. `我的`：进入头像、用户 ID、账号管理、我的记录、我上传的版面、提醒设置、隐私与数据和关于 ICHI；V1-F 接入最小微信账号、本人私有记录状态与删除入口，账号管理不扩张为社交主页；“我的记录”同时容纳本机草稿和本人云端私有观察，卡片统一使用与识别首页抽赏草稿相同的三行结构和字体；“我上传的版面”只显示用户明确执行“仅上传版面”或提交赏票核对的记录。面向用户的状态固定为“待上传／待核对／已上传”：暂不分享退出的辅助抽赏记录保持“待上传”，赏票证据或直接上传已送审后为“待核对”，核对一致后为“已上传”。“我的记录”和“我上传的版面”均把状态徽标固定在卡片右上角；只有“已上传”使用产品玫红色，其他待处理或异常状态保持黑色。两页引用同一规范 `recordId`，不能复制记录；“已上传”只表示 V1 私有核对完成，不表示已经在 V2 地图公开。“提醒设置”在 V1 只展示“好版地图提醒”的 V2 功能说明，明确它只整理带观察时间的历史版面线索、不构成实时库存或推送承诺；V2 再接入地图匹配订阅提醒、来源审核与公开发布，点赞及其他通知类型另行批准。“隐私与数据”只保留计算方式、照片用途、记录存放、非官方声明和本地数据删除入口，不再展示轻提醒说明卡片。

微信小程序内的全部页面统一避让右上角原生菜单胶囊：普通页面内容、二级页页头和一番赏工作台固定状态栏的上沿均从 `wx.getMenuButtonBoundingClientRect().bottom + 12px` 开始，不再按网页顶部安全区直接贴靠状态栏。固定底部导航在全部页面统一使用设备底部安全区作为下沿，不额外保留网页壳的 `20px` 底部偏移；页面内容高度、底部固定操作和滚动留白均使用同一导航位置计算。

微信小程序内所有纵向可滚动正文统一使用与“局面可能性”正文相同的原生边界弹性：手指越过顶部或底部边界时允许系统阻尼产生短暂延伸，松手后再自然回弹，不得在拖动过程中逐帧回写或钳制 `scroll-top` 造成即时拉回。需要恢复位置的页面只在惯性滚动与边界回弹完全结束后保存稳定位置；固定页头、固定操作和底部导航不参与正文回弹，一番赏横向赏票撕揭仍按自身 Page Curl 手势规则处理。

“我的”的账号管理、我的记录、我上传的版面、提醒设置和隐私与数据均属于二级页：顶部安全区必须提供统一返回按钮回到“我的”主页；在任一二级页再次点击底部“我的”也直接回到“我的”主页。该重复点击行为只用于“我的”页族，不改变识别标签的稳定页面恢复规则，也不为地图标签增加额外返回逻辑。

在 `识别`、`好版地图` 与 `我的`之间切换时，系统保留最近一个稳定的识别流程页面：导入页、识别结果、目标奖选择、一番赏版面及统一失败恢复页均可原样返回；拍摄取景与识别／生成等加载态不作为可恢复目的地，返回 `识别`时回到其上一级稳定页面。当前流程从导入页开始时，拍摄页和识别加载页的上一级均为导入页。该规则只恢复页面位置与本机已缓存的版面状态，不伪造识别、生成或上传的后台进度。

### 4.2 识别并创建票池

用户可以：

- 使用页内实时相机拍摄一张完整、可读的兑换进度版面；
- 在导入 Hero 内选择“进入辅助抽赏”或“仅上传版面”。两个按钮都使用 `20px` 前置图标并与文字保持 `8px` 间距；“仅上传版面”图标固定为黑色圆环内的向上箭头。两者共用同一页内实时相机、二次快门确认、识别进度和识别结果，不提供相册选择；流程模式必须贯穿临时页面和返回恢复，不能在拍摄或识别中途丢失；
- 两条路径在开始任何新识别前都必须先建立可信微信账号，再取得本次位置授权。没有有效账号或本次位置获取失败时不得调用模型；用户拒绝或取消后保留当前本机草稿并提供重试，不得以默认坐标或历史坐标替代。已经建立的本机抽赏会话仍可离线继续抽取、撤销与保存；
- 点击“导入版面照片”后先进入版面取景框；取景框以虚线版面和角标提示完整构图，用户点击拍摄后才进入识别；
- 手机端“拍摄版面”使用相机式全屏布局：上半部分为纵向版面取景区，只显示四个构图角标和位于取景区底部的两行提示“将所需版面放在正中间／并尽量铺满取景框”，引导一次只拍一张主要版面；不显示版面内容占位条、灰色提示遮罩或完整边框。下半部分为灰白渐层控制区，左侧放置圆形返回按钮、中央放置尺寸稳定的黑色圆形快门及粉紫外缘光晕；未拍摄时右侧保留等宽空位，照片冻结后同位置出现圆形撤回按钮。底部导航及其下方保持批准网页的灰白背景，不被取景区黑色背景覆盖；
- 拍摄页顶部状态栏与小程序菜单胶囊所在的安全区保持白色；黑色取景区只能从菜单胶囊下方的内容上沿开始。四个构图角标在该黑色取景区内使用相同的左右内边距，左两角到屏幕左缘与右两角到屏幕右缘必须镜像对称；
- 小程序端在用户进入取景页时挂载微信原生相机组件并申请相机权限，后置摄像头的实时画面必须直接显示在既有黑色取景区内；中央快门通过 `wx.createCameraContext().takePhoto()` 在当前页面内拍照，不得再通过系统相机页面、文件选择器或相册完成输入。传感器原图必须按实时取景框的中心 `aspect-fill` 可见范围裁切，使用户看到的取景范围与实际上传范围一致；第一次快门只冻结裁切图，第二次对勾确认才进入识别。相机权限被拒绝或设备不可用时，取景区内显示可理解的授权／重试恢复，不得出现空白页。图片只用于当次识别：小程序把二进制照片上传到私有 `recognition-temp/` 临时目录，云函数只接收与本次任务绑定的 `fileID`，生成短时访问地址交给千问；成功、失败或超时后客户端和云函数都尝试删除，本机临时文件同步释放，异常遗留最迟由生命周期规则清理。图片不得进入数据库、函数日志、审计、备份或任何长期对象存储引用；识别成功且用户完成校正确认后，只把用户确认的结构化观察、模型／用户差异、版本和独立位置快照保存到本人私有 CloudBase 数据域。位置语义固定为“拍摄时当前位置”。该私有结构化观察默认不公开、不直接进入地图；
- 直接识别版面上的奖级、每级券位、券位占用状态、价格和辅助区块，并保留它们的二维位置与阅读顺序；
- 按完整网页基线中已预置的通用组件和实际页面结构，根据识别数据条件显示奖级列表、券位、总抽数、价格和 Last 等组件；小程序组件必须一比一照搬其结构、视觉和行为；
- 将识别结果作为草稿，并按大赏、中赏和小赏的版面规则展示；每级同时显示“总票数－已贴票数”、空／实心票位，以及可直接修改的总票数和已贴票数输入框；不再使用表格或独立“修改”页；
- 识别结果的低置信字段仍在数据契约中保留，但可编辑奖级卡不再添加紫色边框或“请核对”视觉标记；用户以字段内容本身进行修改。“单抽价格”输入格与“总票数”输入格使用同一灰色底、黑色字与黑色数字风格，不使用黑底白字；
- 识别结果在“单抽价格”之前固定显示“IP”胶囊卡片。其文本框允许未来识别 API 写入结构化草稿，也允许用户覆盖或手动输入；当前未接入真实提供方时保持空白并由用户填写，不伪造识别值。IP 为空时，“确认并生成版面”和“上传版面”均保持灰色原生禁用态且不显示主行动光晕；
- “仅上传版面”分支在“单抽价格”之后增加“地点与备注”胶囊卡片，字段语义与共享取证的地点备注一致。只有主 IP 与地点备注去除首尾空格后都非空，底部“仅上传版面”才变为黑底白字并恢复玫红／紫色边缘光晕；主题始终选填，辅助抽赏分支不显示地点字段，只要求主 IP 非空。两条分支仍必须通过既有价格、奖级和票位守恒校验；
- 仅上传分支点击已激活的“仅上传版面”后，不生成抽赏会话、目标奖页面或一番赏工作台，但必须以本次版面数据生成一条 `recordType = board-upload` 的私有记录，并通过认证服务端将用户确认的结构化快照、修订差异与位置快照幂等保存为本人私有观察候选。弹窗沿用现有提交状态卡的图标、排版和光晕，正文固定为“后台正在核对。本次提交退出后可导入新的版面。”，动作区只有“退出回首页”；该状态只表示记录已私有保存并进入后续核对队列，不伪造地图发布；
- “正在提取版面”使用确定型环形进度条与四个阶段；进行中文案依次为“正在整理照片／版面送去清点中／赏级与余票核算中／正在拼出版面结果”，完成后依次切换为“照片整理完成／版面已送去清点／赏级与余票已核好／版面结果已就绪”。每个节点必须区分未开始、进行中和已完成：进行中使用既有蓝紫主题的柔和呼吸点，只有真实阶段完成才显示勾。进度分段固定为 `0—15 / 15—35 / 35—80 / 80—100`；真实事件只更新允许抵达的目标进度，页面显示进度按帧平滑追赶并动态调速，等待时不得越过当前阶段上限。阶段切换分别由本地照片整理完成、临时 fileID 就绪并发出 CloudBase 请求、CloudBase 返回 Provider 结果、本地 Schema／Normalize／RecognitionContract 解析与票池草稿组装完成驱动；不能依靠固定计时器提前勾完；
- 环形进度条使用一条稳定的浅灰底环和圆头黑色进度弧，外圈按显示进度逐步填黑，100% 时闭合；圆环中的“单线眼睛＋放大镜”票根吉祥物保持静止，不随外圈旋转。识别结果就绪后必须先快速补完显示进度至 `100%`、把第四节点切为已完成，才可通过一次性完成门自动进入识别结果；失败、离页或卸载必须停止并取消动画，不得补到 `100%` 或产生延迟跳转；
- 用户点击“确认并生成版面”后，“版面已确认”生成状态层保留原文案、进度条、弹跳动效、锁定时序和自动进入工作台路径；其黑色魔法棒旧图标改为用户提供的“圆点眼睛＋铅笔”票根吉祥物透明素材；
- 图像质量不足时重拍或重新选图，不得伪造完整结果；
- 单抽价格可能是手写内容；无法可靠识别时将价格字段标记为待填写，不阻塞其他版面元素的识别；
- 从“我的 → 我的记录”查看本机草稿和本人云端私有观察；从“我的 → 我上传的版面”查看主动提交核对的上传子集及未来点赞计数位置；二者引用同一个 `recordId`，不能因进入上传列表而复制一份记录。“账号管理”只承载账号与设置；不提供复制票池记录。
- 每次确认一张拍摄版面时为对应记录生成一个稳定的六位辅助编码，字符集固定为大写 `A—Z` 与数字 `0—9`，格式必须匹配 `^[A-Z0-9]{6}$`。同一条记录保存、恢复、提交核对和进入“我上传的版面”时编码不得改变；旧记录缺少编码时由稳定 `boardId` 确定性派生，不能每次打开随机变化。该短码的目标是在当前记录域内唯一、便于用户查找和辨认；V1-F 必须补充冲突检测与迁移验证。它不替代内部 `boardId`／`recordId`、账号归属、审核身份或安全令牌，也不能单独证明某个用户拥有一个真实版面；
- 从识别首页直接查看用户在“暂不分享并退出”时保存的本机抽赏草稿；导入主行动卡固定在页面顶部，卡片底部只显示简短的“每天有 5 次识别版面的权限”额度提示，不显示临时上传链路说明。“抽赏草稿”分区页头不依赖草稿数量，零条记录时仍显示标题与 `0 份`，只有下方列表为空。草稿列表使用独立原生纵向滚动容器：纵向拖动必须由容器自由惯性滚动并保留边界阻尼回弹，不能被卡片左滑删除手势或逐帧全列表状态回写截获；只有先判定为横向的手势才驱动当前卡片的左滑。点击任一草稿直接进入同一 `boardId` 的一番赏工作台，恢复版面、抽取记录、累计花费与撤销状态，不渲染任何草稿摘要或继续确认中转页。“草稿·仅本机”可在识别首页或“我的 → 我的记录”中左滑，揭示黑底白色垃圾桶删除操作；删除操作展开后，下一次独立的屏幕点击无论落在按钮还是页面空白处，都会先把所有草稿行复位到遮住垃圾桶的闭合状态，左滑手势结束时产生的同一轮点击不得让删除操作一闪即收。两处操作删除同一 `LocalDrawDraft`，任一处删除后另一处立即不再显示。已经进入云端私有域的记录使用独立删除确认，不生成本机左滑删除入口。该草稿没有提交核对，不属于线索或地图事实。

V1 不提供按产品划分的固定模板或产品样本目录。市场上不存在已被证明能覆盖中日全部产品的固定三种版面结构，因此系统采用“版面语法”：一个可复用的奖级组件承载 A—Z、SP1—SP4 与用户确认的其他特殊赏级，固定辅助组件承载价格、总抽数、Last 等信息，识别数据决定出现哪些组件以及如何排列。

V1-F 本轮确认的覆盖规则如下；如与本节较早的“相册／版面线索／单 IP 输入”描述冲突，以本组规则为准：

- 两条版面入口都只允许当前相机拍摄，不再提供相册来源。用户点击“进入辅助抽赏”或“仅上传版面”时，先只读刷新服务端每日额度；额度耗尽立即显示“无法建立票池”，动作是“我知道了”，且不得请求位置、相机权限、进入拍摄页、创建 reservation 或调用模型。额度可用才继续位置／相机门禁。第一次点击快门只冻结当前取景框内照片并把快门中心改为白色对勾，右侧原相册位置改为撤回；撤回恢复实时相机和普通快门。第二次点击带对勾的快门才创建唯一权威 reservation 并送入识别。入口检查不消耗额度；只有识别成功、完整可恢复版面已建立并由 `finalize-board-observation` 提交时才增加 `used`。普通识别失败页仍提供重新拍摄入口。
- 识别结果的 IP 卡改为“必填主 IP / 选填主题”两个可编辑文本框。模型优先返回用户可读的规范中文主 IP（例如“女神异闻录”），主题只提取该版面独有的周年、篇章、系列副标题或活动名（例如“30 周年”“来份甜点”），不得重复主 IP；主题为空不阻塞确认。
- 直接上传入口、识别结果主行动及相关说明统一命名为“仅上传版面”；“我的版面线索”统一命名为“我上传的版面”。只完成识别、开始辅助抽赏或暂不上传退出的记录属于“我的记录／本机待上传”，不得进入上传列表；直接上传版面或提交赏票证据后才进入“待核对”，核对完成后显示“已上传”。V1 的“已上传”不表示已经在 V2 地图公开。
- 模型提供的完整 `slotRows` 是票位计数的最高优先级。空的 `openPositions` 数组只表示没有提供可定位的空位证据，不能证明没有空位，也不能把已贴票数覆盖成总票数。只有完整逐行证据明确满足 `covered = total` 且 `open = unknown = 0` 时才能判定全贴满；`physical_ticket_count` 本身不得自动触发全贴满。

确认前必须具备：剩余总票数、至少一个奖项、每个奖项剩余数量、单抽价格。

可选字段：系列别名、Last 状态、目标奖、预算、计划抽数和直接购买参考价。

通过识别结果的“确认”后，系统先在当前识别版面中央显示“正在生成版面”的短暂进度框；校正后的奖级、票位和 Last 已写入当前浏览器会话缓存，生成完成后自动进入“一番赏版面工作台”。“选择目标奖”保留为完整网页基线中的可访问页面，但不阻塞这条快捷主路径；预算、计划抽数和最低概率不作为进入主工作台的必经输入。进入工作台后，A—F 奖级按图标、概率和票位空格排布；已贴票以实心票位表示。Last 固定在左上角，只显示当前包套成本，不显示概率。

目标奖多选页只以选项前的圆形勾选是否出现对勾表达选中状态；选中与未选中卡片共用完全相同的胶囊背景、边框、阴影和内边距，不添加紫色描边、额外光晕或透出页面底色。工作台中的目标赏票同样不使用紫色描边。

版面识别固定提取图像质量与版面边界、普通奖级、奖品名、每级票区归属、每行 open／covered／unknown 票位状态、印刷总数、票位排布、价格、Last、Double Chance、辅助区块、归一化边界框、可见性、置信度和问题原因。A1／A2 等编号奖项是同一个 A 赏内部的奖品款式；物理上独立的特殊赏声明按版面几何阅读顺序规范化为 `SP1`—`SP4`，保留原始印刷标签，不得归并为 `S赏`。第 5 个及后续特殊赏进入 `OTHER` 并要求用户确认。IP 允许综合明确标题、Logo／美术字、角色图像、角色／奖品名称与整体画面推断，最多保留三个带证据候选；证据不足时必须为空。每个票区最多属于一个赏级，空间关系不明确时保持未归属，不得硬分配。程序必须从逐行票位状态重新计数，并把印刷总数与视觉计数分开保存；冲突时要求用户核对。模型不得输出隐藏思维链，只能给出简短的可见证据。票池总数与余票由可靠券位在本地求和，模型不得猜测。完整职责、固定 User Message、提示注入边界、置信度和黄金样本门见 [`docs/decisions/v1-board-recognition-prompt-contract.md`](../docs/decisions/v1-board-recognition-prompt-contract.md)。大赏／中赏／小赏不交给模型判断：`packages/board-layout` 的 `derivePrizeClassification` 只接受已核对的奖级标签和正整数总票位，A—F、SP1—SP4 与用户确认后的其他特殊赏级中，总票数 `≤ 5` 的奖级用大赏呈现，`6—9` 的奖级用中赏呈现，`≥ 10` 的奖级用小赏呈现；G—Z 用小赏呈现。三类本地分类用于概率、局面事件和轻提醒，但一番赏工作台只显示两个视觉分区：大赏进入 `GRAND PRIZES`，中赏与小赏共同进入 `NORMAL PRIZES`，不得把中赏另拆为第三个工作台分区。`NORMAL PRIZES` 的状态球区域始终至少保留三行版式高度；真实票位不足三行时，余下区域保持空白，不生成状态球、占位票或其他会改变总票数／余票数的领域数据。票数未知、矛盾或不合法时返回未确认，不能建立正式票池。V1-29 的唯一页面壳基线为用户提供的 `网页 ui.html`：它的既有页面信息、文字、布局、色彩和动效不得修改；ICHI 只把原有路由、算法与交互绑定到同名或语义对应的控件。源页面未覆盖的已批准能力才可在同一视觉系统中补齐。三者均保持相同的概率、抽取、累计花费和撤销逻辑。为消除跨页面无意的版式漂移，V1-29 另以 [`docs/design/v1-29-ui-design-tokens.md`](../docs/design/v1-29-ui-design-tokens.md) 固定顶部安全区、内容边距、卡片层级、文字宽度、操作宽度和页面族变体；它只统一设计参数，保留导入视觉资产、地图标识、异常状态等有明确语义的尺寸差异。

#### 4.2.1 版面语法与组件装配

V1 不为每个产品建档，也不把版面归并为三种固定模板。完整网页基线预置以下稳定语法，最终随小程序包发布并由 WXML/WXSS 一比一照搬实现：

| 类别   | 要求                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------- |
| 奖级   | `PrizeTier` 是唯一通用奖级组件，预置 A—Z 与 SP1—SP4 标识；识别到的奖级才进入草稿。所有单字母赏级的编号款式都归入所属字母，例如 A1／A2 → A、B1／B2 → B，依此直到 Z；即使 D1／D2 各有独立奖品区与票位区，仍合并为一个 D 赏并汇总两个票区。只有非字母编号的独立特殊赏才按几何阅读顺序映射到 SP1—SP4，第 5 个及后续进入 `OTHER`，显示原文并要求确认 |

开发版、真机调试、体验版与正式版共用真实识别链路；任何环境都不得在失败时自动载入固定演示 IP、价格或票数。固定识别夹具只存在于自动测试，不进入用户拍摄流程。
| 券位   | 每个奖级包含零个或多个券位；记录总券位、已覆盖券位、空置券位和无法判断券位，保留一维／多行排列                            |
| 计数   | 在完整版面且确认一个券位代表一抽时，普通奖级总券位之和推导初始总抽数；普通奖级剩余券位之和推导余票                        |
| 价格   | 记录识别值、币种、原始文本和置信度；识别失败或疑似手写时必须由用户补填或确认                                              |
| 特殊项 | Last、Double Chance 与其他不代表普通抽券的区块单独建模，默认不计入总抽数                                                  |
| 辅助项 | 标题、系列标识、奖品图、说明、店铺／产品 ID、品牌标识、二维码、版权和未知区块均可出现或省略                               |
| 排布   | 每个识别区块记录归一化矩形、父区块、层级和阅读顺序；手机端可响应式重排，但不丢失原始空间关系                              |
| 置信   | 识别字段带置信度和 `recognized`／`derived`／`manual` 来源；低置信字段必须显式待确认                                       |

总抽数只能在以下条件同时成立时自动确认：版面四边完整、所有普通奖级与券位区均被识别、一个券位代表一抽的规则成立、各级券位计数内部一致。任一条件失败时只显示“推算值”或“待填写”，不得把不完整求和当作事实。Last、Double Chance、说明、二维码、装饰和版权区永不进入普通总抽数。

识别“券位占用状态”只用于从当前完整进度版面初始化剩余数量；V1 不读取贴上去的已使用奖券内容，也不在后续每抽后拍照识别奖券。建池后仍严格采用一抽一记。

网页组件脚本、样式和交互逻辑随 Next.js 完整基线发布；识别服务只返回符合已知 schema 的数据，不下发或执行远程组件代码；未知区块只能以不可执行的占位信息降级显示。V1-29 经用户明确授权，为逐项保真直接托管 `网页 ui.html` 及其已有的字体、图标与 Tailwind 运行时输入；该例外只适用于该用户提供的静态页面壳，不允许识别服务或任何未知数据下发可执行 UI。网页验收通过后，所有页面、组件、内容、视觉和行为必须一比一照搬为随小程序包发布的 WXML/WXSS、TypeScript 与微信平台适配；平台差异不得成为重新设计或简化 UI 的理由。

V1-D 的手机视觉基线由 `apps/web/app/tokens.css` 固定颜色、间距、圆角、导航安全区和模态层级；`apps/web/app/ui/` 提供 `PrizeTile`、`TicketSlots`、`StatusNotice`、`Modal` 和 `BottomTabbar` 等本地 React 组件。tokens 只表达视觉约束，组件只接受已校正的页面数据，不把交互、文字或业务状态图片化。390px 手机视口优先，桌面端只做响应式重排；页面索引在手机端隐藏，三项底部导航始终可达；“识别结果”和“一番赏版面”在底部导航上方至少完整显示 5 个奖级，优先压缩重复页面信息，不缩小奖级票位到影响查看或编辑的程度。

此前 `V1-01A` 建立的产品目录覆盖政策保留为历史决策，但已被本节的新认知取代，不再是 V1 建池或发布门禁。

### 4.3 输入校验

系统输出三种状态：

| 状态     | 条件                                   | 行为                           |
| -------- | -------------------------------------- | ------------------------------ |
| 可计算   | 余票、奖项数量和必填字段完整且守恒     | 允许显示正式计算结果           |
| 信息不足 | 缺少票数、奖项或单价                   | 标出缺失字段，不给正式结果     |
| 存在矛盾 | 奖项余量之和不等于余票，或数量出现负数 | 展示矛盾项，阻止确认和继续计算 |

多次未中奖不是异常信号。V1 不输出藏票、作弊或商家风险结论。

### 4.4 目标与预算

用户可以选择多个目标奖。预算、最大计划抽数、最低可接受目标达成概率、停止条件和直接购买参考价仍是计算内核可接受的可选输入，但不作为当前主工作台入口的填写项：

- 本次会话预算；
- 最大计划抽数；
- 可选的最低可接受目标达成概率；
- 可选停止条件；
- 可选的直接购买参考价。

V1 不采集奖项个人价值，不显示“回本率”、价值期望或净值结论。

### 4.5 确定性计算

设剩余总票数为 R、目标票数量为 T、计划抽数为 k、单抽价格为 c。

| 结果                       | 规则                            |
| -------------------------- | ------------------------------- |
| 下一抽命中率               | T ÷ R                           |
| k 次至少命中一次           | 1 − C(R−T, k) ÷ C(R, k)         |
| k 次命中 x 次              | C(T, x) × C(R−T, k−x) ÷ C(R, k) |
| 目标奖期望数量             | k × T ÷ R                       |
| 首次命中任一目标的期望抽数 | (R+1) ÷ (T+1)                   |
| 包套成本                   | R × c                           |
| 剩余预算最大抽数           | floor(剩余预算 ÷ c)，且不超过 R |

规则要求：

- k 小于 0、R 小于 0、T 大于 R 或 k 大于 R 时不给正式结果；
- T 为 0 时命中概率为 0；
- k 为 0 时命中概率为 0；
- k 等于 R 且 T 大于 0 时至少命中一次概率为 1；
- 复杂多目标计算使用精确组合数或动态规划，不简单相乘；
- 同一输入与公式版本必须得到相同结果；
- 所有结果可查看输入、公式版本和限制。

#### 4.5.1 计算术语与金额表示

V1 固定使用“概率、命中分布、期望抽数、成本与预算、包套、停止”六个术语。概率描述可能性，命中分布描述恰好命中各数量的完整分布，期望抽数只表示长期平均而不是保证、保底或推荐抽数。包套只指取得当前全部余票的确定性方案；停止与抽取、包套、直接购买同级展示并保留会话历史。

所有金额以对应币种的最小货币单位整数保存和计算，不使用二进制浮点数存储金额。预算内最大抽数向下取整且不超过余票。完整输入、输出、限制和文案例子由 `data/calculation-baseline/glossary.json` 固定。

#### 4.5.2 约束内最少抽数方案

V1 可以在精确概率陈述之外提供“约束内方案”，但不得把它表达为中奖保证、消费建议或系统替用户设定的最优抽数。用户必须先自行给出本次预算、最大抽数和最低可接受目标达成概率；系统不提供默认概率门槛，也不以“预算内概率最大化”为目标。

约束内方案定义为：在不超过余票、剩余预算和用户最大抽数的前提下，寻找达到用户所设概率门槛的最少抽数。多目标和指定数量使用精确联合概率。只有输入完整、守恒且全部约束由用户明确给出时才计算；缺少约束时只展示事实，不生成方案。

每个可行方案必须同时展示：

- 最少抽数、对应成本和使用的用户约束；
- 精确目标达成概率，以及同等显著或更显著的未达成概率；
- 证明类型“满足用户约束的最少抽数”、公式版本和输入快照；
- “结果不保证”“系统不会自动放宽预算、最大抽数或概率门槛”“停止始终可选”三项固定披露。

若没有任何抽数满足全部约束，结果必须是“当前没有符合条件的抽选方案”，并显示约束内可达到的最高概率与未达成概率；不得建议增加预算、提高最大抽数、降低概率门槛或追逐既有投入。概率门槛为 0 时最少抽数是 0，不得为了产生消费方案而跳过停止。

Last 只允许表达确定性保证：版面规则经用户确认且取得当前全部余票时，可显示包套成本 `R × c` 和“保证取得 Last”；规则未确认、余票为 0 或抽数小于 R 时不计算或暗示 Last 概率。

### 4.6 抽取记录状态机

一轮只记录一张已抽票的一个奖项，不支持批量轮次。用户在一番赏版面上对对应奖级执行撕开动作；动作完成后，该奖级新增一个已贴票位，所有奖级的概率重新计算，并在版面上方显示本次抽到的奖级、当前剩余票数和累计花费。撕拉视觉采用用户指定的 React Spring 纸张教程模型：右移的裁切窗口逐步隐藏保持原位的前纸，同一窗口内颜色略浅、带投影的纸背随位移增宽；手势位移按滑动速度向前投影，松手后使用阻尼弹簧回弹或继续甩出。撕拉轨道按当前奖票范围裁切，纸背到达本卡边缘后不覆盖相邻奖票；未超过半程且没有足够向右速度时不抽取并回弹。完成甩出并完整露出 `OPENED` 后才提交一抽、显示轻提醒；纸背抵达终点后立即快速渐隐并清理，不再悬停。用户已经在版面中知道单抽价格，因此抽取浮层和抽取记录不重复展示单抽金额，只显示截至本轮的累计花费。每次抽取的事实（抽到什么赏、剩余票数、累计花费）与本次命中的情境提醒必须放在同一个可关闭、自动消失的轻提醒框中，而不是拆成多个弹层。轻提醒保持原页面壳的水平居中规则，其垂直中心与顶部固定状态栏的垂直中心对齐。轻提醒左侧吉祥物按本轮奖级的本地分类切换表情：大赏使用四芒星眼睛，中赏保留现有圆点眼睛，小赏使用眯眼表情；三种吉祥物均使用与中赏一致的轻微倾斜角度，表情只反馈已发生的奖级分类，不改变提示优先级或文案。奖级概率只显示百分比，不显示“下一抽”等前缀，并固定精确到小数点后三位，以便用户在每次抽取后看见票池变化；关闭或自动消失时，该框内全部信息一起消失。V1 不拍摄或识别抽开的奖券。

抽取记录模态内的每一条记录必须沿用批准网页的白底分隔行，不得改成灰色圆角卡片。行左侧水平排列灰色等宽 `#序号` 与黑色粗体“奖级＋赏”；行右侧垂直右对齐，上方用灰色小字显示该轮完成后的“余 N”，下方用玫红粗体显示截至该轮的累计金额 `¥N`。金额不得与赏级交换位置或颜色，记录中不得省略余票；历史余票由当前总余票加上该轮之后发生的抽数确定，不扩展 Storage schema。

抽赏记录与版面快照还会作为《情境提醒》的唯一业务输入：每次确认一抽后，系统按目标命中、意外大赏、连续小赏、连续同级中赏、连续多抽、目标达成、撤销和数据不足等情境生成主界面浮层候选。奖项只使用大赏、中赏和小赏三类互斥数量标签：A—F、SP1—SP4 与用户确认的特殊赏级按 `totalSlots ≤ 5／6—9／≥ 10` 依次为大赏／中赏／小赏，G—Z 为小赏；不影响概率、抽取或目标逻辑。累计花费只作事实展示，不设置或要求用户配置成本提醒节点。每一抽独立生成一个最高优先级提示，不使用跨抽取冷却抑制。规则、优先级和禁止文案见 [`memory-bank/情境提醒.md`](./情境提醒.md)；V1-D 已验收网页以纯规则模块在工作台实现该行为，正式小程序会话接入由 V1-E 一比一照搬并完成平台适配。

一轮记录包含四个状态：

| 状态   | 含义                         | 可执行动作                                                       |
| ------ | ---------------------------- | ---------------------------------------------------------------- |
| 空闲   | 没有本轮草稿                 | 点击奖项开始记录                                                 |
| 草稿   | 本轮唯一奖项已选但未写入票池 | 更换奖项、清空、确认                                             |
| 已确认 | 本轮已扣减票池并计入成本     | 在同一版面继续、撤销最近 50 抽范围内的连续最近一轮、打开记录面板 |
| 已撤销 | 最近一轮影响已反向恢复       | 在同一版面显示“已撤销”浮层；连续撤销不得超过最近 50 抽边界       |

确认本轮时必须原子地更新：奖项余量、剩余总票数、本轮成本、累计花费、历史记录和所有计算结果。

赏票撕揭在当前分阶段实现中先采用单层跟手揭露，不使用 WXS、3D Page Curl、翻片、阴影、抬升或飞离。手指在黑色覆盖层上横向移动约 `96px` 即完成全部行程，黑层按当前手指相对起点的水平距离从左向右平移，使底层白色 `OPENED` 连续露出；手指向起点回滑时，黑层必须反向跟手并重新覆盖对应区域，同一触摸进程可反复前进和后退。松手时行程未超过 `50%`，不产生抽取并在约 `180ms` 内复位；超过 `50%` 但未到底，黑层在约 `180ms` 内自动完成剩余揭露，完整显示 `OPENED` 后才原子提交一抽并显示轻提醒，约 `220ms` 后恢复下一张黑色覆盖层。该阶段只更新当前票面，不得移动页面、滚动容器或其他赏票，也不得触发震动；后续拟物抬升只能建立在此真机可拖动基线上，不能重新引入会阻断抽取的触摸链。

如果本轮数量超过对应奖项余量，禁止确认并指出具体奖项。

### 4.7 撤销

- 支持连续撤销最近 50 抽；不支持跳过中间轮次撤销，避免状态重放复杂度；
- 撤销恢复奖项余量、余票、累计成本和计算结果；
- 被撤销轮次保留在历史中并标记状态；
- 已达到 50 抽边界或没有可撤回轮次时，明确说明，不重复增加余量；
- 用户修改票池结构后，如果无法安全撤销，应明确提示并要求确认新基线。
- 撤销和记录列表由版面右下角的圆形快捷按钮打开，不跳转独立状态页面。

### 4.8 四种方案比较与局面可能性

四种结果保留为可解释的计算数据，不使用单一神秘推荐分；当前一番赏版面工作台不提供单独的“抽取方式比较”页面。工作台在撤销按钮上方提供“局面可能性”快捷按钮，在不离开版面的中央模态框中完整展示当前版面特有的事件概率：已选目标至少出现一次、至少一张大赏、至少一张非小赏／全非小赏，以及两张或以上小赏。它使用固定最多 3 抽的观察窗口（余票不足时取剩余数），只读当前已确认余票、用户目标、奖级本地分类和单抽价格；目标缺失不会阻止展示其余版面事件，票池不可计算时明确不生成条目。局面可能性与抽取记录使用同一张四角完整圆角的工作台模态卡片，卡片自身中心对齐 V1-29 设计规则中的视觉中心；内容超过可用高度时只滚动卡片内部，不能把标题或关闭按钮推出视口。模态框不设置默认概率门槛、不排序或标记“推荐”，不提供“立即抽取”按钮，并固定显示“结果不保证；停止仍可选”。完整事件目录、公式、输入校验、版本与固定案例由 `docs/decisions/v1-board-outlook-algorithm.md` 约束。

| 方案     | 必须显示                                                                                     |
| -------- | -------------------------------------------------------------------------------------------- |
| 抽取     | 用户计划抽数、成本、目标概率、未达成概率、预算占用和限制；约束完整时可附“满足条件的最少抽数” |
| 包套     | 清池成本、确定获得的剩余奖项、Last 条件和预算状态                                            |
| 直接购买 | 用户填写的参考价、与抽取和包套的现金差；无参考价则显示未知                                   |
| 停止     | 已花费、剩余预算、停止条件和可保留的会话记录                                                 |

超出预算时，包套和增加抽数只能显示“不建议”或“不可执行”。约束内方案不得覆盖四种并列选择、不得改变停止的可见性，也不得产生单一排名或推荐分。当 k 小于 R 时，不虚构 Last One 获得概率。

| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| PrizePool           | ID、系列别名、余票、奖项集合、单价、Last 状态、更新时间                                                    |
| Prize               | ID、等级、名称、剩余数量                                                                                   |
| DrawSession         | ID、初始票池、当前票池、目标、预算、累计花费、轮次                                                         |
| DrawRound           | ID、时间、奖项与数量、成本、状态                                                                           |
| LocalDrawDraft      | `boardId`、保存时间、当前票位、抽取记录、累计花费和最近撤销状态；同一 `boardId` 再次保存时覆盖旧草稿       |
| LocalRecordIdentity | `recordId`／`boardId`、六位字母数字辅助编码、记录类型、IP、拍摄时间与可选提交时间；辅助编码是当前记录域内的稳定查找码，不作为鉴权凭证 |
| ContributionDraft   | `boardId`、最近提交时间、当前票位快照、抽取记录快照、地点备注与核对状态；同一 `boardId` 只保留最新一次提交 |

| BoardDraft          | 图像完整性、奖级、券位观察、价格、辅助区块、二维排布和字段置信度                                           |
| BoardLayoutSnapshot | 使用的版面语法版本、组件注册表版本、用户确认值和推导门禁结果                                               |

要求：

- 网页中间层使用浏览器本地存储适配层验证会话行为；最终产品使用微信小程序 Storage 适配层，二者通过同一领域状态契约对齐；
- V1 网页在正式本地存储接入前，使用当前浏览器会话缓存保留一番赏版面、抽取记录和最近 50 抽撤销栈；离开后重新回到版面可恢复这些临时状态，但不代表云端保存或账号记录；
- V1-D 已验收网页实现在识别确认时生成仅本机可用的 `boardId`，并在每次提交核对时保存当前版面和抽取记录快照；同一版面再次提交覆盖该快照，重新导入并确认的版面才获得新 ID；
- 记录身份分为四层，职责不能混用：`boardId` 标识一次版面确认链路并承担同版面草稿的幂等覆盖；`recordId` 在接入服务端后标识跨列表、跨状态的同一条规范记录；六位辅助编码只供用户查找与交流；未来 `ownerAccountId`／来源主体由已认证服务端会话绑定，承担贡献归属。重新导入同一物理版面仍可能获得新的 `boardId`，因此 `boardId` 或六位辅助编码都不等于对现实版面的排他所有权；
- V1 接入账号后，创建者归属必须由服务端从认证会话写入并保持不可由客户端短码改写。未来贡献成就、奖励资格和其他用户点赞都引用规范 `recordId` 与账号归属：点赞附着于同一条已发布贡献，奖励通过可审计事件结算，均不得直接以六位记录码作为账户键或授权依据。成就、奖励与点赞仍属后续待批准能力，V1 只建立可承接它们的身份边界；
- 六位辅助编码只解决记录辨认与归因入口，不单独阻止脏信息进入好版地图。公共信息池必须同时通过来源类型与身份核验、初始版面结构、抽赏事实、字段守恒、多来源重复／冲突检测、审核状态、观察时间披露和版本处理；待上传、待核对、来源不明或仅凭短码关联的记录始终留在私人记录域，不进入地图；
- 识别首页“抽赏草稿”、“我的记录”与“我上传的版面”复用同一三行记录信息架构：第一行为“抽赏记录／版面上传 + 六位辅助编码”，不重复显示 IP；第二行为 `IP: 主 IP / 主题 + 记录时间`，时间精确到日期、小时和分钟，不再显示“拍摄日期”或“上传日期”标签；第三行为余票，抽赏记录继续显示已抽数量，版面上传到余票结束。记录卡不再显示累计花费。保存／核对状态可以作为第一行右侧的紧凑状态，不得挤出这三行主体。抽赏记录的时间表示最后修改时间：首次建档显示初始保存时间；从草稿继续抽赏并新增抽取后再次“暂不分享并退出”时更新为本次退出保存时间，原样打开再退出不更新时间；同一记录的 `boardId`、六位辅助编码和历史保持不变。仅上传版面记录使用提交生成时间，后续核对或状态更新不得改变；
- 用户主动执行“仅上传版面”或提交赏票证据后，同一规范记录立即进入“我上传的版面”并标记“待核对”；模型与小程序抽取历史核对一致后标记“已上传”。未提交赏票、决定收手后暂不分享或仅保存本机草稿的辅助抽赏记录保持“待上传”，不得进入上传列表；两处不能复制第二份记录；
- 用户在共享选择中点击“暂不分享并退出”时，系统以同一 `boardId` 在小程序 Storage 中创建或覆盖 `LocalDrawDraft`，然后返回识别首页；“继续抽赏”只关闭共享选择并留在当前一番赏版面。识别首页草稿列表负责恢复这些未分享草稿，不把它们升级为上传记录；“我的记录”的本机记录与本人云端记录都必须提供明确删除入口，本机记录以左滑垃圾桶删除并按 `boardId` 同步更新识别首页；
- 用户可以删除单个会话或全部本地数据；
- V1 不把完整工作台会话作为跨设备云同步产品；本机草稿继续以 Storage 为离线事实源。云端只保存账号、每日配额、用户确认后的初始结构化版面快照，以及辅助抽赏完成后用于核对和推导新版面状态的结构化抽取历史、赏票事实与必要处理状态；
- 本地结构升级必须有迁移版本和失败回退。
- 版面照片与赏票照片都只用于当次模型识别；允许进入私有临时对象目录作为 `fileID` 传输媒介，但不能进入 CloudBase 数据库、日志、备份、长期任务数据或持久对象引用。正常链路结束立即双端删除，异常遗留最迟 `1` 小时清理；上传用途、临时处理、结构化保存与删除规则必须对用户可见。

V1 另保存以下服务端私有实体，不能把它们与本机会话或未来公共地图集合混为一体：

抽赏结束后的实体赏票真实性核验是独立视觉协议：用户只能通过现场相机拍摄、冻结、确认并上传证据，不能以相册替代。模型只枚举照片中每一张独立实体票及其可读赏级；同票重复文字不重复计数，无法可靠读取的 tier 必须保留 unknown，无法可靠区分实体票数时为无效证据。模型不会收到本次抽取的预期结果、历史或任何业务通过条件。CloudBase 从权威、已持久化的 draw events 重建 expected，再用 deterministic canonicalization/count 对模型 tickets[] 做 exact reconciliation。只有 observed total、所有 expected tier、无 extra tier 且无 unknown 全部一致时才产生 `VERIFIED`；可读但不一致是 `MISMATCH`，unknown 是 `NEEDS_REVIEW`，无有效票是 `INVALID_EVIDENCE`，提供方技术故障是 `PROVIDER_FAILED`。未通过状态不标记记录已核验，也不触发地图发布；技术故障不能被表达为造假。每次重拍以不可变 `submissionVersion` 保存，旧异步响应不得覆盖较新版本。

首次证据提交的 PENDING 持久化必须同时保存该 `submissionVersion` 对应的权威抽取事件、确定性最终版面快照、上传时间和备注；后台核验不得依赖另一个易失败的前置云函数才能取得这些事实。照片相册保存与图片预处理可以并行，但首次相机原图的相册保存尝试必须结束，且 Storage fileID 和可恢复 PENDING 均已成功后，才离开拍摄页进入“我上传的版面”；等待期间提交圆钮保持黑色并以旋转加载指示器替代对勾，相册保存失败则带明确警告继续进入待核对。后台重试复用同一版本的证据与权威事实，不重新上传照片；历史缺失权威事实的 PENDING 可由同一记录的本机抽取历史幂等补齐后继续。`VERIFIED` 对用户显示为“已上传”，并由同一私有记录投影位置、最新最终版面、首次上传时间和备注；`PENDING` 显示“待核对”，技术失败显示“核验异常”。三种状态徽标固定在记录卡右上，重新核验／重新上传作为独立操作固定在右下。

| 实体 | 关键语义 |
| --- | --- |
| Account / WeChatIdentity | 由可信微信身份映射到不可枚举内部 `accountId`；昵称与头像不参与鉴权 |
| RecognitionQuota | `accountId + 北京时间日期` 的原子预占、正式扣除与失败释放；普通账号每日 5 次有效结果 |
| RecognitionJob | 幂等键、模型／提示／Schema 版本、状态、耗时、费用档位、模型原始结构化输出和无图片内容的问题码 |
| ObservationCandidate | `recordId`、`boardId`、六位观察记录码、来源路径、用户确认的初始版面快照、当前最终快照、`observedAt`、`serverReceivedAt`、按实际提交用途取得的可选位置快照和私有处理状态 |
| DrawSubmission | 小程序抽取历史、赏票模型结构化结果、用户修订、来源差异、按奖级确认数量和确定性推导版本 |

要求：

- 微信身份、`ownerAccountId`、配额和六位码最终分配都由服务端决定；客户端自报字段不能改变所有者、额度或规范记录；
- 新识别任务使用 `read-only check → reserve → recognized → commit／release`。入口只读检查不预占、不扣减；Provider 成功只保留可校正结构化结果和 reservation。只有完整可恢复版面／票池已经本地建立并由 `finalize-board-observation` 原子保存时才正式扣一次；失败、取消和卡住超时释放额度；
- 新版面确认由服务端创建新的 `recordId` 和六位码；同一草稿、重复点击与网络重试复用同一幂等结果。多人拍摄同一现实版面时保留各自记录码，未来可共同关联到同一 `boardInstanceId`，不得覆盖或回收旧码；
- V1 客户端只读取本人私有记录与状态，不提供全量候选查询或公共地图读取；所有业务集合默认私有，客户端不能直接写未来公共集合；
- 直接上传路径把用户确认的初始版面快照保存为当前最终快照。辅助抽赏路径另外保存经用户确认的抽赏事实，并按规范奖级执行“最终剩余 = 初始剩余 − 已确认抽中数量”；任一奖级为负、未知、超额或总数不守恒时必须阻止保存；
- 小程序抽取历史与赏票识别事实不一致时进入 `needs_user_confirmation`，不得静默选择一方覆盖。A1/A2、B1/B2 等全部同级分层归并到所属字母赏级，SP1—SP4 保持独立；
- 不保存照片后，结构化观察必须额外保留模型原始结构化输出、用户确认值、字段差异、模型／提示／Schema／归一化／推导版本、问题码、守恒结果、位置与时间。它们支持审计和重算，但不能冒充可回看的原图证据；无法解释的记录应降级、拒绝进入 V2 或要求重新拍摄；
- 相机与位置是两项独立权限。首次进入新版面拍摄前依次完成相机和前台位置授权；已经授权的权限直接复用，不重复弹出系统授权。拒绝任一权限时保持在明确恢复路径，不进入新版面拍摄且不消耗额度。首次使用相机前展示照片临时处理说明，位置授权说明位置保存、私有可见和删除边界，并分别记录同意版本；
- 删除仅本机草稿时立即清除本机数据；删除云端私有记录时立即从本人列表隐藏，并在 `24` 小时内硬删除结构化观察；删除账号时立即撤销访问，在 `7` 天内删除本人全部私有记录，只保留不含位置和业务内容的最小删除审计 `30` 天后清除。删除失败必须重试并可审计，不得只隐藏 UI；
- V1 历史候选进入 V2 前仍检查公开授权、地点、完整度、重复、冲突和隐私处理，但不能只因为观察时间较早而拒绝或删除。所有公开记录必须展示原始观察时间并明确“这是历史现场记录，不代表当前库存”。

### 4.10 V1 异常与边界

V1 的异常页面与阻塞式异常弹窗必须保留各自的状态语义：警告继续使用感叹号，撤销保护继续使用撤回箭头，存储读取异常继续使用数据库，本机记录清空继续使用垃圾桶。它们只统一为 `80px` 黑色圆形底板与白色描线图标，不得为了风格统一把不同状态替换为同一个信息图标。异常卡片的内部垂直节奏以“无法建立票池”为唯一基准，并由 `V1-29 UI Design Tokens` 固定图标、标题、说明、动作组与卡片底边之间的间距；单按钮与双按钮状态可以产生不同卡片高度，但不得改变这些间距。

### 4.11 V1 文案与视觉约束

- “局面可能性”和“抽取记录”共用同一模态页头：页头占满卡片内容宽度，标题位于左侧，圆形叉号关闭按钮位于同一水平线的最右侧、接近卡片右上角；关闭按钮不得随标题内容宽度收缩到卡片中部。
- 文案采用克制、清楚且熟悉一番赏场景的语气；“票池”“奖级”“包套”“Last”等词只在准确描述对应事实时使用，不使用拟人化、撒娇式或刺激性表达；
- “导入版面照片”是新建票池的主行动入口；照片导入、识别与用户校正完成后才建立票池，不把未建立的票池称为“票池照片”；
- 用户确认识别结果后在当前版面显示“正在生成版面”的短暂进度状态，并自动进入一番赏版面工作台；不设置“票池已就绪”“抽取方式比较”“本次记录已保存”或“已撤销上一抽”的独立页面；
- 不使用“冲一把”“回本”“再来一次”“欧气”等刺激性 CTA；
- 不使用“推荐抽三张”“最值得”“最佳手气”等主动促抽文案；统一使用“约束内方案”“满足条件的最少抽数”和“仍可能未达成”；
- 成功概率不得脱离失败概率单独突出；确认抽数前必须让用户看到成本、未达成概率和结果不保证提示；
- 不以追损、既有花费或接近目标为理由建议增加投入，用户触发停止条件后不得提示继续抽取；
- 红色只表示错误或预算危险，不表示商家违规；
- 页面优先显示事实、输入与组成项，再显示标签；
- ICHI 使用独立设计系统，不复刻官方海报和角色视觉；
- image2 只用于基于 HTML 布局的视觉方向探索和非交互素材；按钮、输入、文字、状态和业务组件必须回到真实 HTML/React 实现；
- V1 已在 Next.js 手机优先网页完成并验收整套小程序页面设计，同时约束窄屏和桌面浏览器的响应式重排；验收后整套页面一比一照搬为小程序视觉实现；
- 一番赏版面上的奖级概率只显示百分比，统一保留三位小数；每次抽取后按最新余票重新计算并更新显示。
- 颜色不得是唯一状态表达；网页以高对比度、可读文字、足够触控目标、键盘顺序和语义 HTML 为可访问性目标。

## 5. V2 功能设计

### 5.1 账号扩展与贡献归属

- V1 已建立微信身份、稳定内部 `accountId`、服务端会话、本人私有观察、退出和删除基础；以下公开资料、地图贡献与提醒扩展仍须在 V2-A 人工验收时批准；
- V2 复用并扩展 V1 账号能力，增加公开 `ICHI ID`、资料编辑、地图贡献归属、审核状态同步、本人贡献撤回／删除和公共线索删除链路；
- 小程序以 `wx.login` 获取一次性登录凭证，由可信服务端／云函数换取并校验微信身份，再映射到 ICHI 账号。客户端不得提交 `openid`、`unionid` 或其他自报字段作为登录结果；微信昵称和头像不是身份凭证；
- V1 服务端首次建号时生成不可枚举、不可变的内部 `accountId`，只用于账号、私有观察和删除关系，不向普通用户展示、复制或编辑。V2 启用公开资料时再为既有账号生成全局唯一、可复制且不可编辑的公开 `ICHI ID`，用于用户查找本人账号和必要的贡献者展示；稳定身份不能随昵称、头像或设备变化；
- V1 的昵称和头像由用户通过当前微信小程序支持的显式头像选择与昵称填写能力一次性绑定，不依赖已废弃的自动资料获取。账号建立与鉴权不依赖昵称或头像，拒绝授权时继续使用系统默认资料；绑定成功后页面立即使用服务端返回资料，重新进入时从服务端恢复，V1 不提供自由编辑入口，服务端重复绑定返回现有资料，不允许客户端借资料字段改变所有者；
- 账号数据、身份映射、会话、贡献状态和提醒规则保存在服务端数据库；V1/V2 版面与赏票照片只允许进入识别专用私有临时对象目录，不得形成长期对象或数据库引用，头像等非版面资产若未来使用对象存储必须独立评审权限与生命周期。微信身份凭证、私有结构化记录不得写入公开地图文档；
- 地图浏览、线索筛选和 V1 本机抽赏不要求登录；本机草稿可以在未登录状态继续保存，但任何会创建服务端贡献草稿或可能影响地图的个人提交都必须先完成登录；
- 服务端必须从当前认证会话写入 `ownerAccountId`，忽略或拒绝客户端自行声明的拥有者。`boardId` 只承担同版面草稿幂等，`recordId`／`contributionId` 承担规范记录引用，六位辅助编码只用于查找，三者都不能替代账号认证；
- 玩家贡献、玩家现场直传以及门店／店员直传均保留可审计的账号归属。门店来源标记还必须额外通过门店授权或任职关系核验，普通账号登录不能自动获得门店身份；
- 地图可显示经过隐私规则批准的最小贡献者标识和来源类型，用于说明“这条观察由哪个账号提交”；真实 `accountId`、登录凭据、联系方式和私有记录不公开。是否公开昵称或头像由 V2-00 的隐私决策确定；
- V2 账号系统不建立论坛或通用社交图谱，不提供发帖、评论、关注、私信、群组、用户动态流或公开消费档案。贡献卡可继续预留聚合点赞计数，但真实点赞交互和奖励结算不是 V2 账号上线的必要条件，必须另行批准。

### 5.2 地图关注与微信提醒

- 以下触发与降级方式是待 V2-00／V2-03 批准的推荐基线；最终能力受当时小程序类目、订阅模板审核和平台规则约束；
- 登录用户可以从地图筛选或版面详情保存关注规则，至少包含目标 IP／系列、一个由用户明确选择的地点或地图中心、半径和启用状态；可选显著奖级、观察时间范围与提醒频率在 V2-00 冻结；
- 小程序不承诺在关闭后持续读取用户实时位置，也不以后台地理围栏追踪用户。新线索发布或有效更新时，服务端以用户保存的关注地点和半径执行空间匹配；用户打开小程序时可另用当次前台定位刷新“附近匹配”，但不会把当次位置自动改写为长期关注地点；
- 微信外部提醒使用小程序订阅消息。只有用户在明确的“开启微信提醒”操作中主动授权后才记录可用订阅许可；拒绝、取消、许可耗尽、模板不可用或发送失败时，保留关注规则并降级为小程序内的最近匹配／未读提示，不反复弹窗索取授权；
- 订阅消息只包含目标 IP／系列、距离或地点摘要、版面观察时间与非实时提示，点击进入当前版面详情。已下线、被删除或失去审核资格的线索不得继续发送；较早记录可以展示，但必须保持历史时间语义；
- 同一关注规则与同一版面更新必须去重，并提供频率上限、静默时段、暂停、删除和发送记录。平台是否允许长期订阅必须在 V2-A 按当时类目与模板审核结果确认，计划不能把一次性订阅当作永久推送能力。

### 5.3 分享

- 以下转发与海报路径是待 V2-00／V2-03 批准的推荐基线；目标基础库、客户端与平台审核结果必须在实现前复核；
- V2 统一术语：“提交贡献”指创建私有 `ContributionDraft` 并进入核对／审核；“社交分享”指转发地图详情或导出抽赏海报。两者使用独立按钮、状态和埋点，任何一个动作都不得默认触发另一个；
- 打开已公开地图详情、转发该详情以及从本机抽赏记录生成海报均不要求登录；保存云端关注规则、订阅微信提醒和提交贡献才进入账号门禁；
- 地图版面详情提供微信原生转发入口，分享路径只指向可公开访问的 `BoardLead` 详情。接收者打开时读取当前审核、观察时间和下线状态，不把分享时的旧状态伪装为实时库存；
- 一次抽赏记录结束后，用户可以主动生成固定尺寸的抽赏结果分享海报。海报默认只包含 IP／系列、抽取时间、初始与剩余票数、本轮抽数、用户选择公开的奖级结果、ICHI 品牌与“结果仅代表本次记录”提示；累计花费、精确门店、账号资料和六位记录码默认不进入海报，只有明确选择后才能加入允许公开的字段；
- 分享海报优先在客户端 Canvas 生成，不因生成海报自动上传私人抽取记录。微信好友／群、朋友圈、收藏与下载使用微信当前支持的图片分享面板；发布小红书或其他第三方平台时，先保存到系统相册，再由用户进入对应应用手动发布。小程序不自动代发，也不提供虚假的第三方直发按钮；
- 微信会话／群转发、朋友圈入口、图片分享面板和保存相册分别按平台能力实现并提供降级路径。取消分享、拒绝相册权限或生成失败不改变记录、贡献或地图状态；
- 分享抽赏结果不等于提交地图贡献，分享地图详情也不授予编辑该版面的权限。分享不引入帖子、评论、关注关系或用户动态流。

### 5.4 数据边界

允许的数据来源按产品默认路径与信任边界排列：

1. 持有一番赏授权的线下门店，或已核验与该门店任职关系的店员，在店内直接拍摄并校正的完整当前版面；
2. 玩家在决策工具中已拍摄、校正和更新，并主动授权的本人版面、抽取记录和集中拍摄的赏票证据；
3. 官方授权 API 或平台合作；
4. 人工策展的必要元数据与普通回链；
5. 以上都不成立时，不进行自动聚合。

### 5.5 BoardLead

每条线索至少包含：来源类型（玩家抽赏核对／玩家现场直传／门店直传／已核验店员直传／官方或平台／人工策展）、来源身份核验状态、内部账号归属或外部来源引用、可公开的最小贡献者标识、来源 URL（如有）、`observedAt`、`serverReceivedAt`、地点文本、坐标与精度、IP／系列、该观察时点的已核对余票、显著奖级和票位、来源状态、字段置信度、修订／推导版本和审核状态。地图用这些历史现场事实帮助用户决定是否到场核对，不根据版面产生“值得抽”排名或消费结论，也不把最近一条记录称为实时库存。未经核验的自报门店或店员身份不得显示“门店直传”或“已核验店员直传”标记；没有抽赏会话的普通玩家直传必须明确标记为玩家现场观察。

用户点击“收手”后主动开始抽赏后核对：本机抽取记录与集中拍摄的已抽赏票共同生成按奖级计数的结构化草稿，照片本身不保存。任一奖级数量不一致、照片不完整、位置不明确或用户取消时，记录进入私人冲突状态或直接删除，不进入地图。地图最终只发布核对后的结构化当前版面状态、地点、时间和备注，不公开用户逐抽记录或个人抽中赏级。

V1-F 的赏票送审采用版本化增量合并：每次提交以同一 `recordId + boardId` 和单调递增的 `submissionVersion` 建立不可变送审版本；模型只识别本次照片中的按赏级实体票数，服务端再与该版本绑定的完整本机抽取历史核对。较新版本可以在较旧版本仍待核对时提交，完成结果只允许更新相同或更高版本，旧结果不得覆盖新快照；相同版本重试必须幂等。通过核对后把同一贡献更新为“已上传”，不得生成第二条版面记录。

### 5.6 门店与店员直传流程

1. 上传者登录账号后选择“门店直传”，并提交可供审核的一番赏授权门店身份，或本人与该门店的任职／可上传关系。账号身份与门店身份是两层独立校验；核验所需的证明与个人信息保留在私有审核域，地图只显示通过核验后的来源类型和对应门店。
2. 上传者在店内直接拍摄一张完整、可读的当前版面，系统识别 IP／系列、奖级、票位、价格和观察时间，并由上传者校正。该路径不要求先建立玩家抽赏会话，也不要求集中拍摄已抽赏票。
3. 提交必须绑定已核验门店、地点、拍摄／观察时间、完整版面证据和识别校正结果；位置矛盾、照片不完整、身份过期或审核失败时不进入地图。
4. 审核通过后，线索显示“门店直传”或“已核验店员直传”、对应门店和观察时间。这表示信息来自真实销售现场，不表示 ICHI、品牌方或门店承诺查看时仍为实时库存。

### 5.7 玩家共享取证流程

1. 用户在一番赏版面工作台的移动端底部导航上方按住固定悬浮的“决定收手”`500ms`；胶囊从左到右填充为黑色，填充经过的图标与文字同步反转为白色。未满 `500ms` 松开或取消手势时，填充归零且不打开弹层；读满后才在同页视觉中心附近打开共享选择。用户可以“愿意并拍摄赏票”、选择“继续抽赏”关闭弹层留在当前版面，或点击底部灰色虚线下划线文字“暂不分享并退出”，把当前状态保存为本机草稿并返回识别首页。后两条路径都不上传任何数据。
2. 勾选后，当前页面内打开相机取证框，而不是跳转到独立相机页；进入“拍摄赏票”界面时即在既有取景框内挂载微信原生相机并申请权限，实时画面直接铺满取景框。用户点击取景框下方的“拍摄赏票”胶囊后，由当前页的 `CameraContext.takePhoto()` 完成拍照，不得调用系统相机页或文件选择器。明确提示“请把抽完的赏票全部放在框内拍摄”，并以虚线赏票轮廓提示构图；地点、可选的浏览器定位授权和备注在提交前填写。权限拒绝或设备不可用时在同一取景框内提供设置／重试，不得离开当前页面。
3. 用户点击“提交核对”时，未登录用户先完成账号登录，已登录用户直接继续；取消登录不会丢失本机草稿，也不会创建服务端记录。服务端以认证会话中的 `ownerAccountId` 与 `boardId` 创建或更新私有、可取消的贡献草稿；同一账号对同一版面的再次提交必须用最新的当前票位和完整抽取记录覆盖原草稿，不能产生第二条贡献。OCR 按 A—Z／SP1—SP4／OTHER 汇总赏票数量，并与该最新快照逐项比对；前端仍停留在一番赏版面，中央状态框显示“已提交”“后台正在核对本次提交”和“退出后可导入新的版面”，并提供“继续”关闭提示与“退出”返回导入版面；不在前台等待或查看结果页。

共享取证拍摄页的操作行始终同时显示主操作与右侧圆形“撤回”按钮：主胶囊自身在取景框正下方水平居中，宽度放大至 Design Tokens 规定的 `212px`，文字在胶囊内部双轴居中；撤回按钮固定在主胶囊右侧但不得把主胶囊推离页面中线。未拍摄时主操作文字为“拍摄赏票”，拍摄后变为“已拍摄”；撤回清空拍摄状态并重新挂载取景框内相机。拍摄所得照片使用等比裁切填充整个取景框，四边与取景框四边贴合并由同一圆角裁切，不得以缩略图或小图标形式停留在中央。主胶囊在可用状态始终为纯黑底白字且不显示光晕；只有已拍摄且地点与备注去除首尾空格后非空，右侧提交对勾才变为黑底白图标并显示玫红／紫色外缘光晕，其余时间保持灰色禁用态。已提交状态框使用网页的标准内容节奏，两个底部操作保持 `16px` 组间距且整组位于卡片内容之后，不向卡片底部挤压或留出无意义大块空白。辅助抽赏共享取证与“仅上传版面”的已提交状态卡正文统一为“后台正在核对。本次提交退出后可导入新的版面。”，两条路径不得出现不同说明。
4. 后台核对中的记录继续保留在“我的 → 我的记录”，并显示“待核对”；主动提交核对的记录同时出现在“我的 → 我上传的版面”。赏票与本机抽取历史核对一致后，同一规范记录更新为“已上传”，不能复制第二份记录；不一致、失败或取消不自动补正、不进入地图，并允许账号本人重拍、撤回或删除。V2 后续审核并发布地图时再增加独立“已公开”维度。
5. 服务端只把核对通过且已审核的历史版面观察写入好版地图。地图不公开逐抽记录、抽中赏级或赏票原图；通过证据、隐私和发布规则后才显示“已公开”，用户可以请求删除其证据和地图线索。观察时间早不构成单独拒绝理由，但页面必须明确显示时间并提示不代表当前库存。

### 5.8 历史观察时间

好版地图展示的是带时间戳的历史现场观察，不承诺当前库存。公开候选默认按 `observedAt` 从新到旧排序，但不设置“超过若干小时自动归档”或“过旧不得公开”的产品门禁：

- 不足 `24` 小时显示“`N` 小时前记录”；
- `1—6` 天显示“`N` 天前记录”；
- `7` 天及以上显示“`YYYY-MM-DD HH:mm 记录`”；
- 详情页始终显示精确观察时间、时区和来源，并固定提示“这是历史现场记录，不代表当前库存”；
- 同一现实版面的“最近记录”只表示系统目前掌握的最近一次观察，不得写成“当前版面”或“实时余票”。

### 5.9 发布与删除

- 低置信地点不得自动上图；
- 每条公开线索必须有来源类型和核验状态；外部内容必须提供回链，玩家贡献显示授权与审核状态，门店／店员直传显示对应门店与观察时间；
- 原帖删除、权利人要求下线、证据被撤回或记录经核对不可信时停止展示；售罄可以形成新的历史观察，不自动删除旧记录；
- 地图始终提示“线索不是实时库存”；
- AI 只能抽取已合法取得的内容，不猜测缺失地点、余票和时间。

## 6. V3 多人可信协作设计

### 6.1 私人与公共分层

| 层               | 证据要求                 | 公共影响             |
| ---------------- | ------------------------ | -------------------- |
| 私人计算         | 无                       | 无                   |
| 上传草稿         | 本轮集中拍摄             | 无                   |
| 待审核           | 证据、票池绑定和前一版本 | 无                   |
| 已验证           | 审核通过                 | 生成新的公共观察版本 |
| 冲突／驳回／作废 | 审核记录保留             | 不改变或回退公共状态 |

### 6.2 贡献流程

私人记录完成后，用户主动选择贡献；系统汇总本轮结果，引导集中拍摄，识别奖项并遮挡敏感信息，再让用户确认差异。提交必须绑定观察时间、地点、票池身份等级和前一可信版本。

### 6.3 票池身份等级

- 未绑定：只有赏券证据，只能保存个人历史或匿名观察；
- 弱绑定：地点、系列、时间和现场版面照片，可形成独立观察；
- 强绑定：经过验证的票池身份或连续证据链，可参与版本演算；
- 权威绑定：商家或官方来源，仍需显示更新时间。

### 6.4 版本与冲突

公共状态使用追加事件和版本链。提交携带基础版本；基础版本已经变化时，不盲目扣减。无法确定顺序时进入冲突状态。作废中间版本时重放后续事件；无法安全重放则暂停公共状态并等待新基线。

### 6.5 隐私与反滥用

- 原图与公开脱敏图分开保存；
- 检测重复图片、明显编辑和跨提交复用；
- 遮挡二维码、活动码、票号和个人信息；
- 高影响提交提高审核等级；
- 提供纠错、申诉、删除和账号退出；
- 驳回不用于公开羞辱用户。

## 7. 网页体验与平台适配

### 7.1 平台边界

- Next.js 手机优先网页是页面行为、内容、组件、视觉和动效的完整批准基线；最终产品 UI 交付为微信小程序，网页验收结果必须整页一比一照搬为 WXML/WXSS、TypeScript 和微信平台适配；
- 网页中间层使用浏览器相机／相册、IndexedDB 或 localStorage 和 Web 分享能力验证交互；小程序端使用相应微信 API，平台差异统一经过适配层；
- 领域逻辑、识别契约、版面语法和会话状态在网页与小程序之间共享，不能把网页专属 API 写入领域层；
- 核心页面已在真实浏览器手机视口和桌面视口验收；照搬后再在微信开发者工具、必要时真机验证平台映射结果与网页基线一致。

### 7.2 识别、私有沉淀与私人计算边界

- 图像识别读取完整兑换进度版面，可判断券位为空、已覆盖或未知，但不读取已使用奖券上的内容；
- 识别输出是待确认草稿，确定性计算只接收用户确认且通过守恒检查的结构化输入；
- 识别服务不保存照片，也不把版面图像发布为公共数据；用户确认后只由受控保存流程把初始结构化快照、必要抽赏事实与最终推导观察写入本人私有数据域；
- 版面语法和饱和组件注册表随 Next.js 网页包发布，不保存产品版面样本或官方视觉素材；
- 已保存会话的查看、一抽一记、撤销和删除不依赖识别服务。
- 千问只根据图片和版本化 JSON Schema 生成结构化草稿；提示词保持最小且固定，余票、奖级分类、守恒、配额、归属、版本、合并与发布资格全部由确定性代码决定。

## 8. 验收策略

### 8.1 自动验证

- 计算公式使用固定向量、枚举小样本和性质测试；约束内方案还必须证明返回抽数满足门槛、前一抽数不满足、从不越过预算／最大抽数／余票，且无解时不放宽约束；
- 状态机覆盖确认、撤销、重复操作和存储恢复；
- 网页覆盖 Next.js 构建、路由、图像权限与上传、本地存储、核心交互和多视口视觉回归；小程序覆盖对应的 WXML/WXSS、微信 API 和平台回归；
- 版面识别使用经授权的固定样本集评估字段准确率、遗漏、低置信、超时和人工校正路径；
- V1 后端覆盖微信身份伪造、越权读取、配额并发、幂等重试、失败释放、私有对象权限、删除级联和历史候选不可公开查询；
- 公共数据版本必须覆盖并发、冲突、回退和删除。

### 8.2 人工验收

- 用户是每个实施区块的默认验收门；同一区块内的 step 各自提供自动验证和人工检查证据，但不互相构成人工解锁门；
- 区块内 step 可以共享尚待区块验收的中间产物；只有整区块通过后，这些产物和新认知才成为后续区块可依赖的已批准基线；
- 每个页面需要在真实手机宽度下审阅；
- V1 用真实抽取任务验证理解度和操作摩擦；
- V2 按来源类型分别验证玩家贡献转化、门店／店员直传覆盖和更新频率、供给密度、观察时间理解度、发现到到店核对的转化、新贡献回流，以及用户是否把任一来源线索误解为实时库存；
- V3 先在受控范围验证多人票池绑定、版本冲突、证据质量和审核成本。
