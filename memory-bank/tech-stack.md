# ICHI Technology Stack

> 状态：APPROVED
>
> 版本：1.0
>
> V1-A 精确依赖版本已于 2026-08-05 锁定；后续升级必须更新决策记录和锁文件。

## 1. 选型原则

1. V1 使用最小可运行架构，不为 V2/V3 预建后台。
2. V1 仅交付微信小程序手机端，不为 H5 或桌面端保留交付负担。
3. 确定性计算独立于页面和平台，能够单独测试。
4. 平台能力通过适配层封装，不在页面散落 `wx.*`、`window` 或 `document`。
5. V1 只引入图像识别所需的最小云能力；用户账号、会话云同步、产品目录和公共写入仍延后。
6. 版面图像只用于生成可校正草稿，不作为产品样本库或公共目录长期保存。
7. 版本号、依赖和云资源必须在实施步骤中形成可复现锁文件和决策记录。

## 2. 仓库与工具链

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 工作区 | pnpm workspace | 共享计算包、客户端和测试配置，依赖边界清晰 |
| 语言 | TypeScript strict | 领域模型、计算、版面定义和小程序接口共享 |
| 代码质量 | ESLint + Prettier | 统一静态检查和格式化 |
| 单元测试 | Vitest | 适合纯 TypeScript 计算和状态模块 |
| 提交策略 | 区块人工验收后的检查点提交 | step 保持小而可验证，区块统一收口；仅在用户要求时提交 |

V1-A 锁定 Node.js 24.11、pnpm 11.9.0、TypeScript 6.0.3、Vitest 4.1.10、ESLint 10.8.0、Prettier 3.9.6 与 typescript-eslint 8.66.0。TypeScript 暂不采用 7.x，因为当前 typescript-eslint 的 peer 范围仍小于 6.1；版本证据与升级条件见 `docs/decisions/v1-toolchain-and-recognition.md`。

## 3. V1 客户端

| 层 | 选择 | 职责 |
| --- | --- | --- |
| 客户端 | 微信小程序原生 + TypeScript | V1 只交付小程序，减少跨端抽象和包体负担 |
| 视图与样式 | WXML + WXSS + Design Tokens | 小程序组件化页面、颜色、排版、间距和状态语义 |
| 状态 | 纯 reducer／状态机 | V1-C 已确认 reducer 足以承载单奖项草稿、原子确认和最近轮次撤销，不引入 Zustand |
| 计算 | 独立 `packages/core` | 概率、期望、成本、守恒、预算、四方案比较和用户硬约束下的最少抽数证明；不做概率最大化促抽 |
| 本地存储 | 版本化 JSON 信封 + 小程序 Storage 适配层 | 会话、历史和用户校正结果仅保存本地；`bigint` 使用十进制字符串编码，迁移失败保留最近可用内存状态 |
| 版面语法 | 随包发布的 TypeScript／JSON Schema 注册表 | 预置 A—Z 奖级、券位、价格、特殊项、辅助区块和二维排布；不依赖产品数据 |
| 版面识别 | CloudBase 云函数代理 + 阿里云百炼 `qwen3.5-flash` + 低置信局部 `qwen3.5-ocr` | 主模型以非思考 JSON 模式提取整版结构；OCR 只补价格、短标签和小字，不负责整版语义；不读取已使用奖券内容 |
| 版面渲染 | 随小程序包预置的 WXML/WXSS/TypeScript 组件库 + 本地 schema 渲染器 | 识别只返回数据；客户端按已知类型条件显示本地组件，不下载或执行远程 UI 代码 |
| 图标 | 小程序组件或本地矢量资源 | 避免不可换色的 AI PNG 图标 |
| 小程序测试 | 微信开发者工具 + automator + 真机抽查 | 验证编译、页面栈、拍摄／相册权限、上传、Storage 和核心交互 |

V1-A 锁定微信基础库 3.17.0，CloudBase 普通云函数运行时 `Nodejs24.11`。工程绑定用户提供的小程序 AppID；AppSecret 只允许存在于受控服务端环境变量，不进入仓库或客户端。

识别主模型由用户指定为阿里云百炼 `qwen3.5-flash`，低置信文字局部使用同服务方 `qwen3.5-ocr` 补充。客户端总超时 8 秒、单个上游调用超时 5 秒、主模型与 OCR 各最多一次、最大输出 4096 tokens、费用警戒线 0.03 元；图片不写入 CloudBase Storage、数据库、函数日志或会话。代理仅记录无图片内容的请求 ID、耗时、错误码和费用分类。提供方承诺调用数据不用于训练，但会依法存储调用数据且未公开统一保留时长；上传前必须披露，发布前需确认适用协议与删除请求路径。

V1-C 锁定 Storage schema 1、会话 schema 1 与版面快照 schema 1。当前版面快照只接受随包的版面 schema 1.0.0、组件注册表 `v1-saturated-board-components` 和识别契约 1.0.0；支持旧 V0 本地包装迁移，未知版本或迁移失败时保留最近可用内存／版面快照，不联网拉取兼容代码。

### 3.1 V1 不使用

- 用户账号和云同步；
- 地图和外部内容聚合；
- 商家 API、库存、订单或支付；
- 已使用奖券内容识别、产品样本目录或用户上传的公共版面库；
- 远程组件、远程 WXML／脚本／样式、运行时下载可执行 UI 代码；
- 大型跨端 UI 框架。

## 5. V2 增量技术

V2 只有合法数据源通过决策门后才锁定云资源。

| 层 | 首选方向 | 说明 |
| --- | --- | --- |
| 服务端 | 腾讯云 CloudBase 云函数或等价 Node.js serverless | 贴近小程序生态，先承担线索写入、审核和查询 |
| 数据库 | CloudBase 文档数据库 | BoardLead、来源、审核和删除状态；规模或查询不适用时再评估 PostgreSQL |
| 地图 | 腾讯位置服务／小程序地图能力 | 中国大陆双端一致性优先，必须单独评审许可与隐私 |
| 内容抽取 | 仅对合法取得内容调用多模态模型 | 候选模型在 V2 实施时基于成本、准确率和合规重新评估 |
| 后台 | 最小内部审核页 | 只服务来源审核、字段修正和下线，不建设商家后台 |
| 监控 | 云函数日志、错误告警、删除任务审计 | 重点监控来源、时效、下线和抽取失败 |

## 6. V3 增量技术

V3 对事务、审计和证据存储要求显著提高，启动前重新做架构评审。

| 层 | 推荐方向 | 说明 |
| --- | --- | --- |
| 账户 | 微信登录 + H5 统一身份映射 | 只在公共贡献需要时引入 |
| 事件存储 | PostgreSQL 优先评估 | 版本链、并发控制、审核状态和可重放事件更适合事务数据库 |
| 对象存储 | 私有原图桶 + 公开脱敏图桶 | 生命周期、权限和删除策略分离 |
| 异步任务 | 队列／任务系统 | 图片识别、脱敏、重复检测、审核和版本重放 |
| 图片处理 | OCR／视觉识别 + 敏感信息检测 + 感知哈希 | 模型只生成审核草稿，不直接改变公共状态 |
| 审核 | 机器规则 + 内部人工台 + 可选社区复核 | 高影响提交提高门槛 |
| 可观测 | 审核漏斗、冲突、重放、删除和滥用告警 | 所有公共变更可审计 |

CloudBase 是否继续承担 V3 数据层，不预先决定；在 V3 架构步骤用并发、回退和成本基准评估。

## 7. 规划代码结构

```text
apps/
  client/                 微信小程序原生客户端
  review-console/         V2/V3 才创建的内部审核端
packages/
  core/                   领域模型与确定性计算
  session/                票池会话、轮次和撤销规则
  storage/                小程序本地存储接口
  board-layout/           版面语法 schema、饱和组件注册表和推导门禁
  recognition-contract/   图像识别请求、字段置信、二维区块和校正草稿契约
  design-tokens/          Figma 与代码共享 Token
  ui/                     经过小程序验证的内置基础与版面组件
services/
  cloudbase/              V1 只提供识别代理；V2/V3 能力仍受决策门限制
tests/
  fixtures/               公式与票池固定测试向量
  e2e/                    小程序核心流程
  recognition/            经授权版面样本、字段标注和评估基线
  visual/                 小程序多机型视觉回归基线
docs/
  decisions/              架构和平台决策记录
  qa/                     人工验收证据
```

这里只是规划，不代表目录已经存在。真实状态以 `memory-bank/architecture.md` 为准。

## 8. 发布策略

### V1

- 仅交付微信小程序手机端；
- 每个核心页面在开发者工具和代表性真机验证；
- 版面语法发布需要 schema、A—Z 注册表、推导门禁和回退验证；
- 识别服务失败不影响已建会话的本地记录、撤销和删除。

### V2

- 先使用授权样本或人工策展做封闭试验；
- 删除、下线和来源审计通过后才能公开地图。

### V3

- 先白名单贡献与人工审核；
- 证明身份绑定、冲突和回退可靠后再扩大范围。

## 9. 需要在后续区块锁定的决策

- 取得经授权真实版面图片后，锁定 OCR 的真实准确率基线，以及是否需要更换或增加多模态服务；V1-C 合成契约基线不替代此评估；
- V2 地图服务、数据许可和 CloudBase 环境；
- V2 多模态模型及成本上限；
- V3 是否迁移到 PostgreSQL 与独立对象存储；
- 微信小程序与识别服务的正式发布、监控和回滚流程。
