# ICHI Technology Stack

> 状态：REVIEW
>
> 版本：1.0
>
> 精确依赖版本在对应实施步骤开始时依据官方兼容性锁定。

## 1. 选型原则

1. V1 使用最小可运行架构，不为 V2/V3 预建后台。
2. 微信小程序与 H5 共享领域逻辑、状态规则和设计 Token。
3. 确定性计算独立于页面和平台，能够单独测试。
4. 平台能力通过适配层封装，不在页面散落 `wx.*`、`window` 或 `document`。
5. 公共数据、账号和云服务只在对应版本决策门通过后引入。
6. 版本号、依赖和云资源必须在实施步骤中形成可复现锁文件和决策记录。

## 2. 仓库与工具链

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 工作区 | pnpm workspace | 共享计算包、客户端和测试配置，依赖边界清晰 |
| 语言 | TypeScript strict | 领域模型、计算和跨端接口共享 |
| 代码质量 | ESLint + Prettier | 统一静态检查和格式化 |
| 单元测试 | Vitest | 适合纯 TypeScript 计算和状态模块 |
| 提交策略 | 小步骤人工验收后检查点提交 | 与实施计划的一步一验收一致 |

## 3. V1 客户端

| 层 | 选择 | 职责 |
| --- | --- | --- |
| 跨端框架 | Taro 4 + React | 同一客户端输出微信小程序与 H5 |
| 样式 | SCSS + Design Tokens | 共享颜色、排版、间距和状态语义 |
| 状态 | 纯 reducer／状态机优先，必要时用 Zustand 承载应用状态 | 让轮次确认和撤销可测试，不把业务规则藏在组件中 |
| 计算 | 独立 `packages/core` | 概率、期望、成本、守恒、预算和方案比较 |
| 本地存储 | 平台适配层：小程序 Storage；H5 IndexedDB，必要时降级 | V1 离线、无账号、无后端 |
| 图标 | 跨端图标组件或本地矢量资源 | 避免不可换色的 AI PNG 图标 |
| H5 测试 | Playwright | 核心流程、视口、可访问性和视觉回归 |
| 小程序测试 | 微信开发者工具 + automator + 真机抽查 | 验证编译、页面栈、Storage 和平台差异 |

### 3.1 V1 不使用

- 后端数据库；
- 用户账号和云同步；
- 大模型或 OCR API；
- 地图和外部内容聚合；
- 商家 API、库存、订单或支付；
- 大型跨端 UI 框架，除非单独评审证明必要。

## 4. 设计与视觉流程

| 工具 | 职责 |
| --- | --- |
| Figma | 低保真、组件、变量、Auto Layout、高保真与视觉基线 |
| GPT Image | 插画、背景、纹理和特殊装饰；不生成基础交互组件 |
| Playwright | H5 实际页面截图与视觉回归 |
| 微信开发者工具 | 小程序编译、模拟器、自动化和真机预览 |

设计与代码共享 Token；Figma 是已批准视觉意图源，代码和测试是运行事实。

## 5. V2 增量技术

V2 只有合法数据源通过决策门后才锁定云资源。

| 层 | 首选方向 | 说明 |
| --- | --- | --- |
| 服务端 | 腾讯云 CloudBase 云函数或等价 Node.js serverless | 贴近小程序生态，先承担线索写入、审核和查询 |
| 数据库 | CloudBase 文档数据库 | BoardLead、来源、审核和删除状态；规模或查询不适用时再评估 PostgreSQL |
| 地图 | 腾讯位置服务／小程序地图能力 | 中国大陆双端一致性优先，必须单独评审许可与隐私 |
| 内容抽取 | 仅对合法取得内容调用多模态模型 | 候选模型在 V2 实施时基于成本、准确率和合规重新评估 |
| 后台 | 最小内部审核页 | 只服务来源审核、字段修正和下线，不建设商家后台 |
| 监控 | 云函数日志、错误告警、删除任务审计 | 重点监控来源、时效、下线和抽取失败 |

## 6. V3 增量技术

V3 对事务、审计和证据存储要求显著提高，启动前重新做架构评审。

| 层 | 推荐方向 | 说明 |
| --- | --- | --- |
| 账户 | 微信登录 + H5 统一身份映射 | 只在公共贡献需要时引入 |
| 事件存储 | PostgreSQL 优先评估 | 版本链、并发控制、审核状态和可重放事件更适合事务数据库 |
| 对象存储 | 私有原图桶 + 公开脱敏图桶 | 生命周期、权限和删除策略分离 |
| 异步任务 | 队列／任务系统 | 图片识别、脱敏、重复检测、审核和版本重放 |
| 图片处理 | OCR／视觉识别 + 敏感信息检测 + 感知哈希 | 模型只生成审核草稿，不直接改变公共状态 |
| 审核 | 机器规则 + 内部人工台 + 可选社区复核 | 高影响提交提高门槛 |
| 可观测 | 审核漏斗、冲突、重放、删除和滥用告警 | 所有公共变更可审计 |

CloudBase 是否继续承担 V3 数据层，不预先决定；在 V3 架构步骤用并发、回退和成本基准评估。

## 7. 规划代码结构

```text
apps/
  client/                 Taro H5 + 微信小程序
  review-console/         V2/V3 才创建的内部审核端
packages/
  core/                   领域模型与确定性计算
  session/                票池会话、轮次和撤销规则
  storage/                跨端本地存储接口
  design-tokens/          Figma 与代码共享 Token
  ui/                     经过双端验证的基础组件
services/
  cloudbase/              V2 通过决策门后创建
tests/
  fixtures/               公式与票池固定测试向量
  e2e/                    H5 核心流程
  visual/                 视觉回归基线
docs/
  decisions/              架构和平台决策记录
  qa/                     人工验收证据
```

这里只是规划，不代表目录已经存在。真实状态以 `memory-bank/architecture.md` 为准。

## 8. 发布策略

### V1

- H5 先用于快速视觉和端到端验证；
- 同一功能步骤在微信开发者工具同步验证；
- 两端通过同一核心测试向量；
- 是否同日公开发布由 V1 发布步骤决定，不影响代码从第一天保持双端兼容。

### V2

- 先使用授权样本或人工策展做封闭试验；
- 删除、下线和来源审计通过后才能公开地图。

### V3

- 先白名单贡献与人工审核；
- 证明身份绑定、冲突和回退可靠后再扩大范围。

## 9. 需要在实施时锁定的决策

- Taro、React、TypeScript、pnpm 和测试工具的精确兼容版本；
- 状态方案是否需要 Zustand，还是 reducer 足够；
- H5 本地存储库及迁移方案；
- V2 地图服务、数据许可和 CloudBase 环境；
- V2 多模态模型及成本上限；
- V3 是否迁移到 PostgreSQL 与独立对象存储；
- H5 和小程序的正式发布、监控和回滚流程。
